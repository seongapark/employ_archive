# 원인탐색 MCP — 기획서 v1.1 (자립형)

> 한 줄 정의: **현상 질문을 받아 → 원인 가설을 펼치고 → 각 가설을 지지/반증할 지표를 여러 출처에서 끌어와 → 메타데이터·방향판정과 함께 근거묶음으로 반환하는 MCP**

---

## 1. 이 프로젝트의 위치

**한 줄**: 고용통계를 "정확히 가져오는" 문제가 아니라, **"왜 그런지를 설명할 데이터를 찾아오는"** 문제를 푼다.

| | 흔한 통계 통합 도구 | 이 프로젝트 |
|---|---|---|
| 확장 방향 | 수직 — 같은 고용통계를 여러 출처에서 정합하게 | **수평 — 고용통계 바깥에서 원인 데이터** |
| 축 | 출처 (KOSIS·EIS·공공데이터포털) | **인과 경로** (수요·공급·제도·구조) |
| 해결 문제 | "같은 수치가 출처마다 다름" | **"왜 그런지가 자체 데이터로 설명 안 됨"** |
| 산출 | 수치 + 메타 + 비교가능 판정 | 가설 + 근거지표 + 방향판정 + **반증지표** |

- 두 층이 다 필요함. **L1 측정층**(표ID·코드표 레지스트리 내장)과 **L2 탐색층**(가설-지표 매핑)을 한 MCP에 얹음
- 기존 통계 MCP(korean-stats·oecd-stats 등)와 겹치지 않는 지점이 **L2**. 넓고 얕은 통계 래퍼는 이미 있고 차별점이 없음

### 설계 전제 1건 — 로컬 MCP는 폐기
- 로컬 stdio MCP는 개인 노트북이 켜져 있어야만 동작 → **폰에서 못 씀**
- "폰에서 쓰는 서비스"가 요건이므로 원격 MCP로 감 → §5

## 2. 핵심 설계 원리 — 자산은 데이터가 아니라 매핑

"질문에 따라 데이터 범위가 달라진다"는 관찰이 설계의 출발점. 소스 목록을 고정으로 박으면 안 되고, **질문이 소스를 호출**하는 3층 구조여야 함.

```
현상(Phenomenon)   "서울 청년 사무직 취업자 감소"
      │ 1:N
가설(Hypothesis)   "AI 도입으로 신입 사무직 채용문 자체가 좁아졌다"
      │ 1:N
지표(Indicator)    "사무직 신규 구인건수" / "AI노출도 상위직종 피보험자 증감"
      │ N:1
어댑터(Adapter)    EIS OPIA / KOSIS DT_1DA7024S ⚠️정정2 / ECOS / OECD / RSS
```

### 이 구조가 해자인 이유
- 데이터 긁는 건 누구나 함. **"청년 사무직 감소를 설명하려면 이 6개 지표를 이 순서로 봐야 한다"**는 지식이 어디에도 문서화돼 있지 않음
- 경력 있는 사무관은 이걸 암묵지로 갖고 있으나, 사람 머릿속에 있는 한 AI가 못 씀
- **이 매핑 테이블이 그 암묵지를 기계가 읽는 형태로 옮긴 것.** 지표 20개를 쌓는 게 아니라 "무엇을 왜 봐야 하는가"를 쌓는 것

### 지표 1건의 필수 메타 (이게 있어야 자동 판정이 됨)
| 필드 | 예시 | 왜 필요한가 |
|---|---|---|
| `정의`·`모집단`·`단위` | 15~29세 / 사무종사자 / 천명 | 인용 가능성 |
| `공표시차` | M+25일 | "최신"이 언제인지 |
| `expected_sign` | `-` (가설이 맞으면 감소) | **가설 지지 여부 자동 판정** |
| `lead_lag` | `선행 6개월` | 원인/결과 순서 판정 |
| `falsifies` | 이 지표가 이렇게 나오면 가설 기각 | **확증편향 방지** |
| `compare_with` | 충돌 주의 지표 목록 | `통계출처_비교` 충돌쌍 재사용 |

## 2-2. 질문 → 출처 라우팅 ★ 현재 설계의 구멍 (2026-09-08 추가)

### 문제: 지금 설계는 "등록된 질문"만 답함
- §2의 3층은 현상이 **이미 등록돼 있을 때의 결정적 조회(lookup)**임. 추론이 아님
- 미등록 질문("건설업 청년은 왜 줄었나")이 들어오면 반환할 게 없음
- 실습 데모에서 심사자가 등록 안 된 질문을 던지는 순간 바로 드러남 → **막고 가야 함**

### 해법: 질문을 슬롯으로 분해해 소스 capability와 대조

| 단계 | 하는 일 | 누가 | 결정적? |
|---|---|---|---|
| **1 분해** | 질문 → 슬롯 6개 추출 | LLM (**스키마 고정**) | ✗ 확률적 |
| **2 매칭** | 슬롯 ↔ 소스 capability 대조 | **코드** | ✓ |
| **3 선택** | 가능 소스 우선순위 정렬 | **코드**(규칙) | ✓ |

- **LLM은 1단계에만 쓸 것.** 2·3을 LLM에 맡기면 같은 질문에 매번 다른 소스를 골라 재현성이 없어짐 → 보고서 근거로 못 씀
- 1단계도 자유 추론이 아니라 **슬롯 스키마를 고정**해 값 채우기만 시킴

**슬롯 6개**: `주제`(취업자/실업률/구인/임금) · `대상집단`(연령×직업 등 축 조합) · `지역입도`(전국/시도/시군구) · `시간입도`(월/분기/연) · `기간` · `분석유형`(추세/비교/분해/원인)

### 소스 capability 선언 — `/registry/capabilities/*.yaml`

```yaml
id: kosis_경활
provides:
  주제: [취업자, 실업률, 고용률, 활동상태]
  집단축: [성, 연령, 교육정도, 종사상지위, 산업, 직업]
  교차제한:                     # ★ 이 파일의 핵심
    - axes: [직업, 연령]
      사유: 공표표 없음 → MDIS 마이크로데이터 필요   # ⚠️정정3 — 실측으로 반증됨
    - axes: [종사상지위, 연령]
      사유: 동일
  지역입도: [전국, 시도]
  시간입도: [월, 분기, 연]
  기간: { from: "1999-01" }
  공표시차: "M+12일"
limits:
  - 유형: 커버리지        # `데이터_한계와대안` 5유형 그대로
    내용: 15세이상 인구 기준, 군인·시설수용자 제외
```

### 라우팅 응답 — "못 한다"가 핵심 출력

```json
{
  "슬롯": { "주제": "취업자", "집단축": ["연령","직업"], "지역": "시도", "시간": "월" },
  "가능": [],
  "부분": [{ "source": "kosis_경활",
             "사유": "직업×연령 교차 미공표 → 각 축 단독으로만 제공" }],
  "불가": [{ "source": "eis_opib",
             "사유": "사업장 식별자 부재로 산업·직종 축 없음" }],
  "우회": [{ "경로": "MDIS 마이크로데이터", "제약": "승인 신청 필요, 자동화 불가" }]
}
```

### capability의 근거는 1차 출처로만 (2026-09-08 확정)

개인 위키·업무 메모를 근거로 삼지 않음. **모든 제약은 아래 셋 중 하나로 직접 검증한 것만 적재.**

| 근거 유형 | 예 | 기록 방식 |
|---|---|---|
| **공표표 실조회** | 경활에 직업×연령 교차표가 실제로 없음 | 조회 URL + 확인일 |
| **API 문서 명시** | EIS `display` 10~10000, 시도코드 0건 | 문서 URL + 확인일 |
| **실호출 결과** | OPIB 응답에 사업장 식별자 부재 | 요청·응답 요약 + 확인일 |

- **미확인 제약은 등재 금지.** 추측이 섞이면 "못 한다"는 답변 자체를 신뢰할 수 없게 됨
- 각 capability 항목에 `근거`·`확인일` 필드를 필수로 둘 것
- 이 규율의 부수효과 2가지 ─ ① 내부 사정·비공개 메모가 서비스에 섞일 여지가 없어짐
  ② 남이 봐도 재검증 가능해져 실습 산출물로서 성립함

→ §2에서 "자산은 데이터가 아니라 매핑"이라 했는데, **매핑이 두 겹**임이 여기서 드러남.
**① 가설↔지표 매핑**(무엇을 봐야 하나) + **② 질문↔소스 capability 매핑**(그걸 볼 수 있나).
둘 다 지금은 어디에도 기계가 읽는 형태로 없음 — 그걸 만드는 게 이 프로젝트임

### 실무 가치 — 답보다 "왜 못 주는지"
- 사무관이 며칠 헤매다 알게 되는 "그 교차표는 공표 안 됨"을 **질문 즉시** 알려줌
- 실습 데모에서 반응이 가장 좋을 기능일 것. 이 바닥에선 **답을 주는 것보다 못 주는 이유를 정확히 대는 게** 더 귀함

- A~D 각각은 공개 데이터. 하지만 **한 번도 같은 테이블에 놓인 적 없음**
- "공개는 됐으나 DB화된 적 없어 사실상 못 쓰는 정보"를 결합하는 것 = 실습이 말하는 재조합
- 특히 **C축(정책 타임라인)이 가장 미개척** — 시행일·개정일이 시계열 위에 겹쳐진 DB는 존재하지 않음. 여기가 차별점

## 4. 소스 추가가 쉬운 구조 — 선언적 어댑터

원칙: **소스 하나 추가 = 파일 하나 추가. 코드는 안 건드림.**

```
/registry
  /phenomena/청년사무직감소.yaml      ← 현상 정의
  /hypotheses/H1_AI대체.yaml          ← 가설 + 지표 참조
  /indicators/IND_사무직신규구인.yaml  ← 지표 정의 + 소스 참조
  /capabilities/kosis_경활.yaml       ← ★ 무엇을 못 하는지 (§2-2)
  /sources/eis_opia.yaml              ← 어댑터 설정
  /sources/ecos.yaml
  /sources/moel_rss.yaml
/adapters
  kosis.ts / eis.ts / rss.ts / oai.ts / sdmx.ts / law.ts / naver.ts / csv.ts  ← kind별 8종
```

### 지표 YAML 예시
```yaml
id: IND_사무직신규구인
name: 사무종사자 신규 구인건수
source: eis_opia
query:
  series: OPIA
  occupation: "02"        # KECO 사무직
  region: "*"             # 전국 = 전 시군구 순회 후 합산 (시도코드는 0건) ⚠️정정5 — 성·연령도 필수
  period: monthly
meta:
  정의: 워크넷 신규 등록 구인 건수(사무종사자)
  모집단: 워크넷 등록 사업장 (민간포털 제외 → 과소)
  단위: 건
  공표시차: M+10일
  커버리지한계: 민간채용포털 미포함 → 수준 비교 금지, 증감률만 사용
```

- 이 스키마 하나만 지키면 **새 데이터 추가는 YAML 붙여넣기**로 끝남

## 5. 아키텍처 — Cloudflare + 정적 HTML 확정 (2026-09-08)

실습 스택은 **백엔드 Cloudflare / 프론트 정적 HTML**. §5 초안 추천과 일치하며, 프론트는 React 없이 HTML 1장으로 더 줄임.

### 5-1. 확정 함정 — 웹 프론트는 MCP를 직접 못 부름

가장 먼저 짚어야 할 것. **MCP는 LLM용 프로토콜이지 웹앱용 API가 아님.**
"MCP 백엔드 + 웹 프론트"를 문자 그대로 만들면 브라우저가 MCP 서버에 붙지 못해 설계가 깨짐(React든 바닐라든 동일).

→ 해법: **코어 1개, 진입점 3개**

```
                        ┌── /mcp      → 원격 MCP (Claude 앱·폰 커넥터)
[D1] ── [core/*.ts] ────┼── /api/*    → REST (정적 HTML이 fetch)
   ↑    조회·판정 로직   └── scheduled → Cron 수집기
   └── 어댑터가 적재
```

- `core/`는 **프로토콜을 모르는 순수 함수 집합** (`getEvidence(hypothesisId, period)` 등)
- `/mcp`는 core를 MCP 툴로 감싼 얇은 래퍼, `/api/*`는 core를 JSON으로 감싼 얇은 래퍼
- **툴 로직을 두 번 짜는 순간 실패함**. core 단일 진실원천 원칙이 이 프로젝트의 1번 규칙

### 5-2. Cloudflare 구성요소 매핑

| 필요 | Cloudflare | 비고 |
|---|---|---|
| 지표 시계열 DB | **D1** (SQLite) | 무료 5GB·읽기 500만행/일·쓰기 10만행/일 |
| 정기 수집 | **Cron Triggers** | `scheduled()` 핸들러 |
| 원격 MCP 서버 | **`agents/mcp/server`의 `createMcpHandler`** | **스테이트리스** — Durable Objects 불필요 |
| 프론트 배포 | **Workers Static Assets** | **정적 HTML 1장** — 빌드 툴체인 없음, 한 Worker에 동거 |
| API 키 보관 | **Secrets** | `wrangler secret put` |
| LLM 호출 | **Gemini API 프록시** (실습 제공 토큰) | 슬롯 분해 전용. **structured output으로 JSON 스키마 강제** |

- Cloudflare가 원격 MCP를 **한 파일로** 세울 수 있게 해줌 → MCP 서버 구축 자체는 실습에서 병목이 아님
- 병목은 §2의 매핑 카탈로그와 §4 어댑터. **거기에 시간을 쓸 것**

#### LLM 사용 범위 — 딱 한 곳 (2026-09-08 확정)
- 실습 제공 **Gemini 토큰**을 Workers Secret에 넣고 `/api/ask`에서만 호출
- 쓰는 자리는 **§2-2의 1단계 슬롯 분해 하나뿐**. 판정·선택·집계는 전부 코드
- **structured output(JSON 스키마 고정)으로 호출할 것** — 자유 서술로 받으면 §2-2의 재현성 원칙이 깨짐
- `/mcp` 경로는 LLM 호출이 아예 없음 (Claude 앱이 LLM 역할) → 토큰 소진은 웹앱에만 발생

### 5-3. 리포 구조

```
/src
  index.ts            # 라우터: /mcp · /api/* · scheduled
  /core               # ★ 프로토콜 무관 순수 로직 (단일 진실원천)
    route.ts          #   질문 슬롯 ↔ 소스 capability 대조 (§2-2)
    resolve.ts        #   자연어 → 현상 후보
    evidence.ts       #   가설 → 지표 시계열 + 방향판정 + 반증
    context.ts        #   정책 타임라인 · 문헌
    comparability.ts  #   비교가능 판정
  /mcp/server.ts      # core를 MCP 툴로 노출 (얇게)
  /api/routes.ts      # core를 REST로 노출 (얇게)
  /adapters           # kosis eis rss oai sdmx law naver csv (8종)
  /cron/collect.ts    # 어댑터 호출 → D1 upsert
/registry             # ★ YAML 카탈로그 (§4)
/public
  index.html          # 검색창 UI — 바닐라 JS fetch('/api/ask'). 빌드 없음
/migrations           # D1 스키마
wrangler.jsonc
```

- **프론트는 정적 HTML 1장으로 확정 (2026-09-08)**. 화면이 「검색창 + 결과 카드」 하나뿐이라 React가 값을 못 함
- 얻는 것: npm 빌드·번들러·node_modules 없음 → `wrangler deploy` 한 방. 실습 중 프론트 툴체인에서 시간 까먹을 일이 사라짐
- 나중에 화면이 늘면(비교뷰·차트) 그때 React 도입해도 `/public`만 갈아끼우면 됨 — core·API는 그대로

### 5-4. wrangler 설정 골자

```jsonc
{
  "name": "cause-finder",
  "main": "./src/index.ts",
  "compatibility_date": "2026-09-06",
  "assets": {
    "directory": "./public/",                // 정적 HTML 1장. 빌드 산출물 아님
    "run_worker_first": ["/api/*", "/mcp"]   // ★ 이거 없으면 정적자산이 API를 삼킴
  },
  "d1_databases": [{ "binding": "DB", "database_name": "cause-finder" }],
  "triggers": { "crons": ["0 20 * * *"] }    // 매일 05:00 KST
}
```

### 5-5. 유지되는 판단 2건

**(1) 폰 경로는 웹앱이 아니라 원격 MCP**
- 커스텀 커넥터는 Anthropic 서버에서 연결을 거는 구조 → **모바일 앱 포함 전 클라이언트 동작**, Free 플랜부터 지원
- 즉 웹 프론트가 늦어져도 폰에서 쓰는 데는 지장 없음. **`/mcp`를 먼저 세울 것**

**(2) 수집은 실시간이 아니라 Cron 스냅샷**
- ① MCP 호출 중 외부 API 타임아웃 나면 답변 자체가 실패
- ② 폰 응답속도 (원 API 왕복 3~10초 → D1 조회 수십 ms)
- ③ 실습 주제가 "직접 DB를 만드는 것" — 스냅샷 적재가 정확히 그것
- D1은 곧 SQLite → 나중에 폐쇄망 반입이 필요해지면 **파일 하나 들고 가면 끝** (지금 미고려지만 공짜로 얻는 옵션)

## 6. MCP 툴 명세 (6개)

| 툴 | 입력 | 출력 | 비고 |
|---|---|---|---|
| `route_question` | 자연어 질문 | 슬롯 6개 + 가능/부분/불가/우회 소스 | **§2-2** 미등록 질문의 유일한 출구 |
| `resolve_phenomenon` | 자연어 질문 | 현상 후보 3개 + 신뢰도 | **LLM 추론에 맡기지 말 것** — 재현성 확보 |
| `get_hypotheses` | 현상 ID | 가설 목록 + 각 가설의 지표 세트 + 대립가설 | |
| `get_evidence` | 가설 ID, 기간 | 지표 시계열 + 메타 + **방향판정** + 반증결과 | **핵심 툴** |
| `get_context` | 현상 ID, 기간 | 정책 타임라인 + 문헌 스니펫(링크·요약만) | C·D축 |
| `check_comparability` | 지표 A, B | 비교가능 판정 + 사유 | `통계출처_비교` 충돌쌍 활용 |

### `get_evidence` 응답 스키마 (답변 품질이 여기서 결정됨)
```json
{
  "hypothesis": "H1_AI대체",
  "verdict": "부분지지",
  "evidence": [
    { "indicator": "IND_사무직신규구인", "expected": "-", "observed": "-14.2%",
      "match": true, "period": "2024-01~2026-06", "lag": "선행 5개월",
      "meta": { "모집단": "...", "커버리지한계": "..." } }
  ],
  "counter_evidence": [
    { "indicator": "IND_전직종신규구인", "observed": "-9.8%",
      "note": "전 직종도 동반 감소 → H1 단독 설명 불충분, H2 경기순환 병행 검토" }
  ],
  "unknown": ["AI 도입률 직접 지표 부재 — 대리지표(IT투자액)로 대체 중"],
  "sources": [ { "id": "eis_opia", "url": "...", "snapshot_date": "2026-09-01" } ]
}
```

- `counter_evidence`와 `unknown`은 **선택 필드 아니라 필수 필드**
- 이유: 사무관 보고서에서 반드시 나오는 "다른 요인은 검토했나?"를 선제 차단. 실무 가치가 여기서 나옴

## 7. 파일럿 워크스루 — "왜 청년 사무직이 줄었나" (전국)

**1차 구현: H1·H2·H3 / 보류: H4·H5·H6 (§10)**

| 가설 | 지표 (예상방향) | 소스 | 반증조건 |
|---|---|---|---|
| ⬛ **H1 AI 대체** | AI노출도 상위직종 피보험자(−) / 사무직 신규구인(−) / 사무직 대비 대인서비스직 구인비(−) | EIS OPIA·OPIB + KECO×AI노출도 매핑(기보유) | 전 직종 동반 감소 시 기각 |
| ⬛ **H2 경기순환** | 서비스업생산지수(−) / BSI 전망(−) / 전직종 신규구인(−) | ECOS·산업활동동향 | 사무직만 유독 크게 감소하면 H2 단독 설명 부족 |
| ⬛ **H3 산업구조** | 사무직 다수고용 산업(금융·도소매·정보서비스) 피보험자(−) / 산업별 사무직 비중 변화 | EIS OPIB + 전국사업체조사 ⚠️정정1 | 산업규모 유지인데 사무직만 감소 시 기각 ⚠️정정4 |
| ⬜ **H4 공급측** | 청년인구(−) / 대학 전공계열 구성 변화 / 청년 비경활 '쉬었음'(+) | 국가데이터처 인구추계·교육통계·경활 | 인구효과 분해 시 고용효과가 대부분이면 기각 → `인구효과_고용효과_분해` |
| ⬜ **H5 제도** | 최저임금 인상률 / 청년일자리사업 예산·시행일 / 관련 법령 개정일 | 국가법령정보 API·고용부 RSS·예산서 | 제도 변곡점과 감소 시점 불일치 시 기각 |
| ⬜ **H6 대체이동** | 청년 플랫폼·프리랜서 추정치 / 전문직 신규취득 | 경활 부가조사·EIS | 타 직종 유입 없으면 순감소 확정 |

- ⬛=1차 구현 / ⬜=v2 보류
- 기보유 자산 재사용: KECO×AI노출도 매핑, 인구효과/고용효과 분해 로직
- **H2가 가장 중요한 가설** — H1을 주장하려면 H2를 먼저 기각해야 함. 반증축이 설계에 박혀 있어야 하는 이유

## 9. 실습 로드맵

| 단계 | 산출물 | 코드량 |
|---|---|---|
| **0. 카탈로그 먼저** | 현상 1(전국) + 가설 **H1·H2·H3** + 지표 약 12 + **capability 4종**(경활·사업체조사·EIS OPIA·KOSIS ECOS) | **코드 0줄** — 여기서 가치 검증 끝남 |
| 1. D1 스키마 + 어댑터 2종 | `migrations/`, `kosis.ts`·`eis.ts` (XML→JSON + 코드표 내장) | 소 |
| 2. Cron 수집 → D1 | `scheduled()`로 지표 시계열 적재 | 소 |
| 3. **core 5함수** | `route`·`resolve`·`evidence`·`context`·`comparability` — 프로토콜 무관 | 중 ★ |
| 4. `/mcp` 래퍼 | `createMcpHandler`로 core를 툴 6개로 노출 | **소** (얇은 래퍼) |
| 5. 폰 연결 | Claude 앱 커스텀 커넥터 등록 → **폰에서 질문** | 0 |
| 6. `/api` 래퍼 + 정적 HTML | core를 REST로 노출 + `public/index.html` 검색창 + Claude API 프록시 | **소** |
| 7. 어댑터 확장 | `rss.ts`(C축) + `sdmx.ts`(D축) | 소 |

- **0단계와 3단계가 전부**임. 4·6은 3단계를 감싸는 얇은 래퍼라 core만 제대로 서면 금방 끝남
- 4단계를 6단계보다 먼저 두는 이유: 폰에서 동작하는 걸 먼저 확보해야 실습 데모가 안전함
- 실습 발표에서 보여줄 것: 폰으로 질문 → 가설 + 지지/반증 판정이 근거·출처와 함께 나오는 화면

### D1 스키마 골자 (3테이블이면 시작 가능)
```sql
CREATE TABLE indicator_meta (          -- registry YAML을 적재한 사본
  id TEXT PRIMARY KEY, name TEXT, source_id TEXT,
  definition TEXT, population TEXT, unit TEXT, lag_days INT,
  coverage_caveat TEXT, updated_at TEXT
);
CREATE TABLE observation (             -- 지표 시계열 (수집기가 upsert)
  indicator_id TEXT, period TEXT, value REAL, snapshot_date TEXT,
  PRIMARY KEY (indicator_id, period)
);
CREATE INDEX idx_obs ON observation(indicator_id, period);
CREATE TABLE event (                   -- C축 정책 타임라인 · D축 문헌
  id TEXT PRIMARY KEY, kind TEXT,      -- law | press | paper
  title TEXT, date TEXT, url TEXT, summary TEXT, tags TEXT
);
```
- `observation`의 PK를 (지표, 기간)으로 잡아 재수집이 자연스럽게 upsert가 되게 할 것
- 인덱스 없으면 D1 무료 티어의 **읽기 행 수**(스캔 기준)를 금방 태움 — 조회량이 아니라 스캔량 과금

| # | 항목 | 확정 | 근거·영향 |

| 1 | **현상 범위** | **전국** | 경활 월별 직업별 공표표가 전국 기준으로 가장 두툼 → 실습 기간 내 완성 확률 우선. 서울 대조는 v2 보류 |

### 확정에 따른 파생 결정
- **지역축이 전국으로 고정**되면서 EIS OPIA의 시군구 필수 파라미터 문제(시도 코드 0건)를 **전 시군구 순회 합산**으로 처리해야 함 → `eis.ts` 어댑터의 첫 과제
- **H3 추가로 소스 1종 증가**: 전국사업체조사 ⚠️정정1(`DT_21002D003` 계열). 조사–공표 2년 격차가 있어 시계열 하한이 H1·H2와 다름 → capability의 `시의성` 한계로 선언
- **C·D·E축은 1차 범위 밖**. 다만 `get_context`(정책 타임라인·문헌)는 툴만 뚫어두고 빈 응답 반환 → 확장 시 YAML만 추가

- 서울 대조
