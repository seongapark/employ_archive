## 5. 네이버 API — 뉴스보다 데이터랩

### 5-1. 뉴스 검색 (`openapi.naver.com/v1/search/news.json`)
| 항목 | 내용 |
|---|---|
| 인증 | `X-Naver-Client-Id` / `X-Naver-Client-Secret` 헤더. **개인 즉시발급, 심사 없음** |
| 한도 | **25,000회/일** (검색 API 합산) |
| 응답 | 제목·링크·**요약(스니펫)**·발행일. **본문 전문 없음** |
| 파라미터 | `query`, `display`(≤100), `start`(≤1000), `sort`(sim/date) |
| **기간 지정** | **없음** ★ |

**한계가 결정적**: 기간 파라미터가 없고 `start+display ≤ 1000`이라 **쿼리당 1,000건이 상한**. 즉 "2024년 3월에 무슨 기사가 있었나"를 물을 수 없음.
→ **과거 시점 원인탐색에는 구조적으로 부적합. 현재 이슈 스캔용으로만.**
→ 다만 **매일 Cron으로 긁어 D1에 적재하면 시간이 지날수록 자체 아카이브가 쌓임**. 우리가 만드는 게 곧 없는 아카이브라는 실습 취지에 부합.
→ 본문 미제공은 오히려 **저작권상 안전**(§8 "링크+요약만 적재" 규율과 일치)

### 5-2. 데이터랩 검색어 트렌드 (`openapi.naver.com/v1/datalab/search`, POST)
| 항목 | 내용 |
|---|---|

### ★ X등급이 오히려 더 값짐
§1에서 **X·C등급으로 판정된 것들**(고용24 기업회원 전용, 고용부 보도자료 RSS 부재, ILO ISCO 2자리 한국 미제출, MDIS 승인 필요)은
버리는 정보가 아니라 **기획서 §2-2 capability 선언의 `limits`·`제공안함` 항목 그 자체**임.

MCP가 "그 질문은 이 데이터로 답할 수 없고, 이유는 이것"이라고 답하려면 **못 하는 목록이 먼저 있어야** 함.
즉 이 조사에서 실패로 기록된 항목이 곧 라우팅의 재료임.

### 아직 안 한 것 — 파일럿 4종 capability 직접 검증
개인 위키를 근거로 쓰지 않기로 확정(기획서 §2-2)했으므로, 아래 4종의 제약을 **1차 출처로 직접 재확인**해야 함.
