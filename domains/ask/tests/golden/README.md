# 골든 질문 세트

유형 6종 × 대표 질문. **슬롯이 고정 입력이라 LLM 없이 돈다** — 1패스를 건너뛰고
`ask({db, llm: null}, {유형, 슬롯})` 으로 core 경로 전체를 결정적으로 돌린다.

`기대` 는 **코드가 만드는 것만** 담는다. LLM 이 쓰는 `답변` 문장은 담지 않는다
(매번 달라지므로 골든이 될 수 없다). 담는 것은 라우팅 판정 · 근거에 실린 지표 id ·
한계 문구 · 배지다.

기대값을 먼저 박고 통과시키는 방향으로 간다. 구현에 맞춰 기대값을 고치면 이 파일의 의미가 사라진다.

러너가 무엇을 단언하는지 (2026-09-09 Task 11 기준):

- **단언한다**: `유형` · `라우팅`(가능·부분·불가) · `한계포함`(부분 문자열) · `배지`(**집합 일치** —
  포함 검사면 `배지: []` 가 아무것도 검사하지 않는다) · `판정` · `현상` · `가설`(포함) ·
  `지지증거_비어있지않음`/`반증증거_비어있음` · `비교가능` · `차이유형` · `답변 === null`.
- **조건부로 단언한다**: `근거지표` — **관측이 실제로 실린 근거가 있을 때만** 대조한다
  (`${근거.지표}:${관측.기간}` 꼴로 조립). `observation` 이 비어 있는 지금은 모든 골든에서
  건너뛰고, 적재기가 붙는 날 저절로 켜진다. 관측이 없는데 단언하면 근거가 0개라 항상 참이
  되는 공허한 검사가 된다.
- **단언하지 않는다**: `한계유형` · `답할수있는질문` — 코드가 그 형태로 내지 않는 문서용 필드다.
- **문구 대신 존재만 단언한다**: `우회경로` — 기대는 소스를 한글 이름으로 적었고
  (`경제활동인구조사 · 고용행정통계`) `route()` 는 소스 id 로 적는다(`eaps·ei`). 문구를 맞추려
  `route` 를 고치면 Task 7 테스트와 부딪히고, 기대를 고치면 골든이 무뎌진다. 그래서 이 기대의
  알맹이("못 준다로 끝내지 않는다")만 단언한다.

## 슬롯은 `classify.normalize()` 가 실제로 내는 모양이어야 한다

`집단축` 만이 아니라 `category` 도 그렇다. `'30대'` 는 축(`연령`)과 값(`30-39`)을 **함께**
낸다 — `수치조회-30대취업자.json` 의 슬롯에 `category` 가 없으면 이름은 "30대취업자" 인데
실제로는 연령 전 구간을 조회하게 되고, `근거지표` 기대와도 어긋난다(2026-09-09 정정).

## 슬롯.주제 는 카탈로그 원어를 쓴다

`슬롯` 은 1패스 LLM 을 건너뛴 **이미 정규화된 입력**이다 — 즉 `classify.normalize()` 가
내놓을 형태와 같아야 한다. `route()` 는 `슬롯.주제` 를 `capability.주제` 배열과
**정확 일치**로 대조하므로(2026-09-08, Task 7 라운드 2), 여기 쓰는 값은 짧은 정규형
(`취업자`)이 아니라 카탈로그 원어(`취업자수`)여야 한다. 실측 카탈로그
(`domains/ask/data/capabilities.json`)의 `주제` 는 지금 `취업자수`(eaps)·`종사자수`(est)·
`상시가입자수`(ei) 세 개뿐이다.

이 규칙 때문에 `수치조회-30대취업자.json` 과 `메타한계-연령별.json` 의 `기대` 가
정정됐다: `30대 취업자` 케이스는 원래 `가능: ["eaps","ei"]` 로 세 출처 중 둘을
묶어 냈지만, `ei` 는 상시가입자수를 재지 취업자수를 재지 않는다 — **다른 것을 재는
통계를 "가능" 이라 답하면 안 된다.** 정정 후 `가능: ["eaps"]` 뿐이고, `est`·`ei`
는 애초에 후보가 아니므로 `불가` 에도 없다. 세 출처를 나란히 보는 것은
`수치조회` 가 아니라 `출처비교` 의 몫이다(`출처비교-경활행정통계.json` 은 `출처`
를 명시적으로 받으므로 이 규칙의 적용 대상이 아니다). **기대값을 구현에 맞춰
고친 게 아니다** — "취업자수를 안 재는 통계를 가능이라 답한다" 는 이전 기대값이
잘못된 동작을 고정하고 있었던 것이고, 그걸 바로잡았다.
