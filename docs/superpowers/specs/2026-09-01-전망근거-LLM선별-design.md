# 전망 근거를 LLM 으로 선별한다 — 설계

선행: `2026-09-01-전망근거-수집-design.md`(규칙 방식, 배포됨 main `5e0608b`)

## 1. 왜 바꾸나

규칙 방식이 실제로 건진 근거는 회차 32개에 **6건**이다. 낮은 것이 버그가 아니라
정확도를 택한 결과였고, 그 벽이 어디인지는 실측으로 안다.

**한국어 보고서는 인과를 조사로 표현한다.** KDI 요약 쪽에는 지표마다 깨끗한 근거가
한 줄씩 있는데 하나만 잡힌다.

| 문장 | 결과 |
|---|---|
| 글로벌 반도체경기 호황에 **힘입어** … 성장할 전망 | 잡힘 |
| 국제유가 상승 및 경기 개선**으로** … 축소될 전망 | 못 잡음 |
| 내수 개선세가 파급되**면서** … 확대될 전망 | 못 잡음 |

`으로` 를 표지로 올리면 `20만명으로 확대`·`2.2%로` 까지 전부 걸린다. 낱말 목록으로는
원리적으로 안 풀리고, 안전하게 풀려면 형태소 분석 수준의 작업이 필요하다.

**둘째로 창을 넓힐 수 없었다.** 근거 서술이 표 ±1 쪽 밖에 있는 기관이 많은데(BOK 는
8·10·11·39·43 쪽에 흩어져 있다) 창을 넓히자 **BOK 집필진 명단**이 근거로 뽑혔다.
`pick` 의 네 조건을 우연히 다 만족했기 때문이다. 그래서 창을 좁힌 채 뒀고, BOK·KDI·
OECD Interim 은 0건으로 남았다.

이 둘은 같은 뿌리다 — 규칙은 문장이 **무엇을 말하는지** 모른다. LLM 은 안다.

## 2. 결정

**LLM 을 선별자로 쓴다. 요약하게 하지 않는다.** 원문에서 문장을 지목하게 하고,
지목한 문자열이 원문에 실재하는지 프로그램으로 대조한다.

**CI 에 넣지 않는다.** `tools/` 아래 사람이 돌리는 도구로 만든다.

근거는 회차당 한 번 정해지면 되는 것이라 매일 돌 이유가 없다. 도구로 두면
"사이트 운영에 지장 없음" 이 약속이 아니라 **구조**가 된다 — `collect-forecast.yml` 을
한 줄도 안 건드리므로 LLM 이 죽든 키가 만료되든 수집과 배포는 그대로 돈다.

규칙 방식과 병행하지 않는다. 둘이 같은 키에 쓰는데 `rationale_store.merge` 가 기존
항목을 덮지 않으므로 **먼저 쓴 쪽이 이긴다** — 규칙 방식이 어정쩡한 문장을 선점하면
LLM 이 고칠 수 없다.

## 3. 경계 — 바뀌는 것과 안 바뀌는 것

바뀌는 것은 "어느 문장을 고를까" 하나다.

| 그대로 | 이유 |
|---|---|
| `rationale_store.py` 전부 | 저장 형식·키·merge 규칙이 방식과 무관 |
| 사람이 고친 문장을 안 덮는 규칙 | 이 도구는 "손이 빠른 사람" 이라 같은 자리에 들어맞는다 |
| `TAG_WORDS` 16종과 `tags_for` | 닫힌 목록이고 문장에 실제로 있는 낱말만 붙는다 |
| 화면(`rationaleFor`, 폴백) | 읽는 파일이 같다 |
| `forecasts.json` 과 수치 수집 전체 | 이 작업은 수치를 건드리지 않는다 |

| 바뀜 | 어떻게 |
|---|---|
| 선별 | `rationale.pick` → LLM 선별 + 검증 |
| 입력 범위 | 표 ±1 쪽 → **보고서 전문** |
| 실행 시점 | 매일 CI → 사람이 필요할 때 |

## 4. 구조

```
tools/rationales.py          도구 진입점 (CLI)
  domains/forecast/pipeline/
    llm_select.py            프롬프트 구성 · 호출 · 응답 파싱
    llm_verify.py            원문 대조 · 기존 방어 재사용
    rationale_store.py       (그대로) 저장
```

`llm_select` 와 `llm_verify` 를 나누는 이유는 **검증이 호출을 몰라야** 하기 때문이다.
검증은 (원문, 후보 문장) 두 문자열만 받는 순수 함수라 네트워크 없이 전부 시험할 수 있고,
LLM 을 바꾸거나 사람이 손으로 넣은 문장에도 같은 검사가 걸린다.

**데이터 흐름**

```
회차 목록 (기존 수집기의 list_issues / EDITIONS 재사용)
  → 보고서 전문 텍스트 (기존 pdf.page_texts · ocr.page_texts 재사용)
  → llm_select: 지표별 후보 문장 + 쪽번호
  → llm_verify: 원문 대조 + 길이·렌더링 방어
  → tags_for(문장)
  → rationale_store.merge → rationales.json
```

수집기의 회차 목록과 본문 획득은 **이미 있는 것을 그대로 쓴다.** 새로 만들지 않는다.

## 5. 검증 — 이 설계의 핵심

화면에는 "한국은행은 이렇게 전망했다" 로 뜬다. LLM 이 매끄럽게 다듬은 문장은
**그럴듯해서 아무도 의심하지 않는** 최악의 실패가 된다. 선행 작업에서 규칙을 계속
조인 이유가 전부 그것이었다.

**규칙: 공백을 지운 후보가 공백을 지운 원문의 부분열이어야 한다.**

```
normalize(s) = s 에서 모든 공백 문자를 제거
accept ⟺ normalize(후보) in normalize(원문쪽)
```

이 한 줄이 두 가지를 동시에 준다.

- 낱말을 하나라도 바꾸거나, 지어내거나, 두 문장을 이어 붙이면 **걸린다**
- `작용하 고,` 처럼 줄 감김이 낱말 안에 넣은 공백을 붙여 쓰는 것은 **허용된다**

두 번째가 중요하다. 선행 작업은 pdfplumber 가 끝 공백을 지워 낱말 중간 감김과 진짜
낱말 경계를 구별할 수 없다는 이유로 그 흔적을 선언하고 남겨 뒀다. 공백을 무시하는
대조는 그 문제를 **검증을 약화시키지 않고** 넘긴다.

같은 이유로 **줄바꿈도 문제가 되지 않는다.** 원문의 한 문장이 세 줄에 걸쳐 있어도
공백을 지우면 이어지므로, LLM 이 이어 붙여 돌려준 문장이 그대로 통과한다. 선행 작업이
문장 분리에 들인 장치 전부(줄 감김 잇기, 불릿 표지 두 벌, 쪽 장식, 각주, 절 번호)를
이 한 줄이 대신한다 — 10장의 삭제 범위가 그만큼 넓은 이유다.

대조에 실패한 후보는 버리고, 무엇이 왔는지 로그에 남긴다. 조용히 넘기지 않는다 —
프롬프트가 잘못됐다는 신호이기 때문이다.

**그 위에 기존 방어를 그대로 얹는다**: 300자 상한, 한글 3연속 동일 음절(BOK 의 굵은
글씨 반복 렌더링), `_FALSE_CONTAINMENT`(`이유가` 안의 `유가` 같은 태그 오탐).
LLM 이 골랐다고 해서 면제되지 않는다.

## 6. 프롬프트 계약

**입력**: 기관·회차 정보, 그 기관이 실제로 전망하는 지표 목록, 보고서 전문(쪽번호 표시).

**요구**: 지표마다 그 전망의 이유를 말하는 문장 **하나**를, 원문에서 **그대로** 옮기고
쪽번호를 함께 낸다. 이유를 말하는 문장이 없으면 그 지표는 비운다.

**출력**: JSON. `[{indicator, text, source_page}]`.

프롬프트에 반드시 싣는 것:

- **한 글자도 바꾸지 말 것.** 다듬거나 요약하면 버려진다.
- **없으면 비울 것.** 빈 칸은 정상이고 지어낸 근거보다 낫다.
- **수치 재진술은 근거가 아니다.** "3.2% 성장할 전망" 은 전망이지 이유가 아니다.
- **표·목차·집필진 명단·각주는 근거가 아니다.** (규칙 방식이 실제로 걸렸던 것들)

지표 목록을 기관마다 다르게 주는 이유는 선행 작업의 결론이다 — KLI 의 성장률 언급이
성장률을 전망하지 않는 기관에 붙으면 안 된다.

## 7. 실패 처리

| 상황 | 동작 |
|---|---|
| 키 없음 | 즉시 중단, 안내 출력. 파일 안 건드림 |
| 호출 실패·타임아웃 | 그 회차만 건너뛰고 계속. 끝에 실패 목록 출력 |
| JSON 파싱 실패 | 그 회차 건너뜀. 받은 응답을 로그에 남김 |
| 원문 대조 실패 | 그 후보만 버림. 무엇이 왔는지 로그에 남김 |
| 어느 것이든 | `forecasts.json` 은 절대 건드리지 않는다 |

기존 항목은 덮지 않는다(사람 수정 보호). 의도적으로 다시 만들려면 `--refresh` 로
대상을 **명시**해야 한다. 인자 없이 전체를 덮는 경로는 만들지 않는다.

## 8. 테스트

**네트워크를 타는 테스트를 만들지 않는다.** 선행 작업의 규칙이 그대로 적용된다.

- LLM 응답을 픽스처로 박제하고 재생한다. 호출부는 주입 가능한 인자로 받는다.
- 검증은 순수 함수라 픽스처만으로 전부 시험한다. 특히 **거부되어야 하는 것들**:
  낱말이 바뀐 후보, 지어낸 후보, 두 문장을 이어 붙인 후보, 300자 초과, 글자 반복.
- 실제 보고서에서 그대로 옮긴 문장을 테스트 파일에 인라인 문자열로 박제해 쓴다 —
  선행 작업처럼 원문 텍스트 파일을 픽스처로 따로 두지 않는다. `verify()` 는
  (후보, 원문 조각) 두 문자열만 받는 순수 함수라, 그 정도 길이의 원문 조각은
  파일로 분리할 이유가 없다.

## 9. 운영

- 키: `ANTHROPIC_API_KEY` 환경변수. KOSIS 선례(`os.environ.get`)와 같은 방식.
  **GitHub Secret 에 넣지 않는다** — CI 가 이 도구를 부르지 않기 때문이다.
- 모델: Sonnet 5. 한국어 인과 판단이 필요하고, 회차가 32개뿐이라 비용이 무시할 수준이다.
- 실행: 새 회차가 나왔을 때 사람이 돌린다. 결과를 눈으로 보고 커밋한다.
- **KEIS 는 전문 OCR 이 필요하다.** 텍스트 레이어가 없어 21쪽을 400dpi 로 읽으면 회차당
  1분 반쯤 걸린다. 매일 도는 것이 아니라 사람이 어쩌다 한 번 돌리는 도구이므로 받아들인다
  (선행 작업이 CI 에서 이 비용을 피하려 표 ±1 쪽으로 좁혔던 제약이 여기서는 없다).
  나머지 다섯 기관은 텍스트 레이어라 즉시 읽힌다.
- 산출물은 `domains/forecast/data/rationales.json` 하나. `tools/build.py` 가 `data/` 를
  통째로 복사하므로 배포에 별도 작업이 없다.

## 10. 규칙 방식의 은퇴 범위

**은퇴**: `collect.py`·`backfill.py` 의 근거 수집 배선, 여섯 수집기의
`collect_issue_rationales`. 매일 CI 에서 근거를 수집하지 않는다.
부수 효과로 KEIS 의 이중 OCR(회차당 48초 중복)도 사라진다.

**남김**: `tags_for`·`TAG_WORDS`·`_FALSE_CONTAINMENT`, 300자 상한, 중복문자 방어.
이들은 검증 단계로 자리를 옮길 뿐 그대로 산다.

**지움**: 선별 장치 전부 — `pick`·`INDICATOR_WORDS`·`_CAUSE`·`_FORECAST`·
`_FORECAST_SUFFIX`. 그리고 **문장 분리 장치 전부** — `sentences`·`_unwrap`·
`_bullet_sentences`·표지 두 벌·`_is_page_furniture`·`_FOOTNOTE_MARKER`·
`_SECTION_HEADING`·`_NEGATIVE_NUMBER`·`_SENTENCE`·`_DECIMAL_POINT`.

분리 장치를 지우는 것이 처음에는 아까워 보인다. 며칠에 걸쳐 실측으로 다듬은 것들이고
각각 실제 결함을 막고 있었다. 그러나 **그 결함들은 "원문을 문장으로 자르는 일"에서만
생긴다.** LLM 은 자르지 않고 지목하고, 검증은 공백을 무시하고 대조하므로 줄 감김도
각주도 절 번호도 대조 결과를 바꾸지 못한다. 호출부가 사라진 방어를 남겨 두면 다음
사람이 어느 쪽이 진짜 경로인지 알 수 없다. 지운 것은 git 이 갖고 있다.

**구현 계획이 지우기 전에 확인할 것**: 각 이름의 호출부가 정말 하나도 안 남았는지
프로그램으로 확인한다. 남아 있으면 지우지 말고 보고한다.

지우는 것과 남기는 것의 경계는 **"문장을 고르는 일인가, 고른 문장을 검사하는 일인가"** 다.

## 11. 하지 않는 것

- **IMF·OECD 본편.** 수치를 API 로 받아 원문 텍스트가 파이프라인에 없다. LLM 을 써도
  읽을 게 없다. 보고서를 받아 파싱하는 별도 작업이 필요하고 이 설계 밖이다.
  OECD Interim 은 PDF 를 읽으므로 포함된다.
- **태그를 LLM 에 맡기기.** 닫힌 목록에 규칙 매칭이 이미 검증 가능하게 동작한다.
  LLM 에 넘기면 검증할 것이 하나 늘고 얻는 것이 없다.
- **CI 통합.** 9장의 이유.
- **`rationale.py` 3분할 리팩터.** 선행 작업의 최종 검토가 분리·선택·태깅 세 이음매를
  짚었으나, 10장의 삭제로 파일이 크게 줄어든다. 줄어든 뒤에 다시 볼 일이다.

## 12. 성공 기준

- 회차마다 그 기관이 전망하는 지표에 대해 근거가 붙는다. 규칙 방식의 6건보다 **뚜렷이**
  많아야 한다. 숫자를 미리 못 박지 않는다 — 없는 회차에 지어내는 것이 더 나쁘다.
- 저장된 문장이 **전부** 원문에 실재한다(대조가 이를 보장한다).
- `collect-forecast.yml` 이 바뀌지 않는다.
- 수치 453건이 바뀌지 않는다.
