# 질의응답 — 도메인 답변자 다섯 + 취합기 (설계)

2026-09-10. 질의응답(ask) 도메인을 **네 주요 도메인의 답을 모아 한 채널로 내는 자리**로
다시 세운다. 앞선 스펙 `2026-09-08-질의응답-허브-design.md` 를 대체하지 않고 그 위에
얹는다 — 카탈로그·온톨로지·검증 규율은 그대로 두고, **답을 만드는 경로만** 바꾼다.

## 0. 왜 바꾸는가

지금 `ask()` 는 유형(수치조회·출처비교·전망·원인탐색·메타한계·범위밖) 하나를 골라
**한 갈래만** 답한다. 그래서 "청년 고용률이 왜 떨어졌나" 를 물으면 관측이나 가설 중
하나만 나오고, 같은 저장소가 들고 있는 전망·연구보고서·기사는 한 글자도 안 나온다.

주요 도메인은 넷이다 — 고용전망 · 고용동향 · 행통 모니터링 · 연구보고서. 질의응답은
그 넷과 나란한 다섯째 도메인이 아니라, **넷이 낼 수 있는 답을 모아 보여주는 창구**여야
한다(2026-09-10 사용자 결정).

실무에서 이 차이는 크다. 고용 담당자가 "청년 고용" 을 물을 때 알고 싶은 것은 숫자 하나가
아니라 **지금 얼마고 · 어떻게 전망되고 · 무슨 연구가 있고 · 언론이 어떻게 다뤘나** 이며,
지금은 그걸 알려면 앱 넷을 따로 열어야 한다.

## 2. 실측 (2026-09-10)

전부 이 저장소의 실제 데이터를 세어 본 값이다.

| 대상 | 크기 | 비고 |
|---|---|---|
| `reports/data/reports.json` | 378KB · 572건 | 서지 + `matched` 키워드 |
| `reports/data/abstracts.json` | 1,673KB · 초록 보유 315건 | 초록 한 건 3~6천 자 |
| `press/data/articles.json` | 151KB · 307건 · 3회차 | 본문 없음 |
| `press/data/rounds.json` | 49KB · 3행 | 회차 분석 전체 |
| 합계 D1 적재량 | 약 2.2MB | 무료 한도 5GB 의 0.05% |

기사의 `hits` 는 이미 축:값 형태다 — `지표` 220 · `산업` 167 · `연령` 135 · `성` 6.
ask 의 슬롯 축과 같은 계통이라 **새 어휘가 필요 없다.**

보고서 초록은 **문단 경계가 없다.** PDF 에서 뽑을 때 공백을 합쳐 넣었고, 게시판에서 받은
초록도 줄바꿈 보존 이전 파싱이라 마찬가지다. 그래서 발췌는 문단이 아니라 **문장 창**으로
자른다(§5-3).

## 3. 아키텍처

```
질문
 └─ 분류(LLM 1패스) ──→ 슬롯 { 주제 · 집단축 · 지역입도 · 시간입도 · 기간 · 출처 }
     └─ 라우터 ─→ 물어볼 답변자를 고른다 (0~5)
         ├─ 고용동향   유형: 수치조회 · 출처비교
         ├─ 고용전망   유형: 전망조회
         ├─ 연구보고서 유형: 문헌탐색
         ├─ 행통       유형: 보도양상
         └─ 원인탐색   유형: 가설검토
              ↓  다섯이 같은 계약으로 낸다 (LLM 없음, 코드와 D1 만)
         { 도메인, 유형, 근거[], 숫자모음[], 허용텍스트[], 한계[], 미확인[] }
              ↓
     └─ 취합기(LLM 2패스) ─→ 문장 배열. 문장마다 출처 도메인과 인용 대목
              ↓
     └─ 검증 ─→ 숫자는 숫자모음과, 인용은 허용텍스트와 대조. 어긋난 문장만 버린다
              ↓
     └─ 화면 ─→ 최종 답변 + 도메인별 근거 카드
```

**LLM 호출은 지금과 같은 2회다.** 답변자를 코드로 두었기 때문이다. 이 선택이 이 설계의
중심이다 — 답변자가 LLM 을 쓰면 호출이 여섯 번이 되고, 숫자를 LLM 이 만들지 않는다는
기존 원칙이 도메인마다 다시 무너질 자리가 생긴다.

**메타한계·범위밖은 유형이 아니라 결과가 된다.** 다섯이 모두 빈손이면 그것이 곧
"못 준다" 이고, 각자가 낸 `한계` 가 그 이유다. 지금은 별도 갈래인데, 나눠 두면 어떤
도메인이 무엇을 못 하는지가 뭉개진다.

## 4. 답변자 계약

다섯이 같은 모양을 낸다. 취합기는 도메인이 몇이든 같은 코드로 다룬다.

```js
async function answer(deps, 슬롯) -> {
  도메인: 'employment' | 'forecast' | 'reports' | 'press' | 'cause',
  유형:   '수치조회' | '출처비교' | '전망조회' | '문헌탐색' | '보도양상' | '가설검토',
  근거:   [...],        // 화면 카드가 그리는 것
  숫자모음: [...],       // 검증이 답변의 숫자를 대조할 집합
  허용텍스트: [...],     // 검증이 답변의 인용을 대조할 문자열 집합
  한계:   [...],        // 이 도메인이 못 하는 것 (카탈로그에서 온다)
  미확인: [...],        // 확인하지 못한 것 (못 하는 것과 다르다)
}
```

**라우터는 도메인 표를 갖지 않는다.** 답변자마다 `applies(슬롯) -> boolean` 을 두고
라우터는 그것을 물어 참인 것만 부른다. 어느 질문에 어느 도메인이 답할 수 있는지는
그 도메인이 가장 잘 알고, 중앙에 표를 두면 도메인이 늘 때마다 두 곳을 고쳐야 한다
(유형을 도메인이 갖는다는 §1-2 결정과 같은 이유다). `applies` 가 거짓이면 그 도메인은
**호출되지 않았다는 사실이 화면에 남는다** — 조용히 빠지지 않는다.

`숫자모음`·`허용텍스트` 를 답변자가 낸다는 점이 중요하다. 지금은 `verify` 가 호출부에서
집합을 조립하는데, 그 조립을 한 곳에서 하다 보니 **전망 카드의 숫자를 빠뜨려 정상
답변이 통째로 버려진 사고**가 있었다(2026-09-09). 집합을 만드는 책임을 근거를 만드는
쪽으로 옮기면 그 종류의 누락이 구조적으로 어려워진다.

## 5. 도메인별 답변자

### 5-1. 고용동향 (`employment`)

지금 `수치조회`·`출처비교` 코드를 그대로 옮긴다. 조회 대상은 `observation`·`release`.
`축_BREAKDOWN`(연령→age · 성→sex · 산업→industry) 매핑과 "직업 축은 관측에 없다" 는
한계도 그대로 따라온다.

### 5-2. 고용전망 (`forecast`)

지금 `전망` 코드를 옮긴다. `전망지표` 매핑(취업자수→emp_change 등), 보고서 단위 묶음,
`forecast_rationale` 근거 인용이 그대로다. 근거 문장은 `허용텍스트` 에 넣는다 — 지금
그 문장이 허용 집합에 **한 번도** 들어가 있지 않았다(2026-09-09 실측).

### 5-3. 연구보고서 (`reports`)

**후보 고르기는 LLM 을 쓰지 않는다.** reports 도메인의 `keywords.json`(17개 주제 그룹)에
**질문 원문을 그대로 통과시켜** 걸린 그룹을 얻고, 그 그룹이 `matched` 에 있는 보고서를
후보로 삼는다. 어휘표를 두 벌 두지 않기 위해서다 — ask 의 슬롯 주제는 *지표* 이름이고
보고서 주제는 *정책* 주제라, 둘을 잇는 표를 새로 만들면 한쪽만 늘어나 조용히 어긋난다.
이 도메인에서 실제로 그렇게 어긋나 "여성 취업자" 가 메타한계로 떨어진 전례가 있다.

원문에 아무것도 안 걸리면 슬롯의 카테고리로 한 번 더 본다 — 청년→청년고용,
60대→고령자, 여성→여성고용 정도의 여섯 줄이며, `카테고리_SYN` 에서 파생시킨다.

순위는 **초록 보유 → 최신 → 걸린 키워드 수**. 초록 없는 257건이 위로 오면 취합기가
제목만 보고 쓰게 된다.

**초록 전문을 넘기지 않는다.** 후보 5건, 각 초록에서 질문어가 걸린 **문장 앞뒤 두
문장**까지 잘라 최대 800자. 전문을 넣으면 질문당 토큰이 5배(1,500→8,000)가 되는데
이렇게 자르면 2배에서 멈춘다. 잘라낸 대목이 곧 `허용텍스트` 다.

### 5-4. 행통 모니터링 (`press`)

매칭은 기사의 `hits`(`연령:청년`·`산업:제조업`·`지표:고용보험`)로 한다. 슬롯 코드를
한글 이름으로 되돌리는 것은 `카테고리_SYN` 을 뒤집어 파생시킨다.

내는 것: 걸린 기사 건수 · 언론사 수 · 기간 · 인용 건수와 비율 · 논조 낱말 상위 ·
대표 헤드라인 3건(제목·언론사·날짜·링크). 건수와 비율만 `숫자모음` 에 넣고,
헤드라인은 원문 제목 그대로 `허용텍스트` 에 넣는다.

한계 셋을 반드시 낸다. 성격이 달라 뭉치면 안 된다.

- 기사 본문이 없다 — "기사가 뭐라고 했나" 는 답할 수 없다
- 보도자료 전후 창(정규 1~2일 · 후속 2주)에서만 수집 — 언론 보도 일반 표본이 아니다
- 3회차 307건뿐(2026-06~08월분) — 추세를 말할 표본이 아니다

### 5-5. 원인탐색 (`cause`)

지금 `evidence.mjs` 경로를 답변자로 세운다. **다른 답변자에 기대지 않고 직접
`phenomenon`·`hypothesis`·`indicator`·`observation` 을 읽는다.** 답변자끼리 의존하면
순서가 생겨 병렬로 못 돌리고, 한 답변자의 실패가 다른 답변자를 끌고 내려간다.

`hypothesis_verdict` 뷰의 `verdict_blocked_by`(반증미설계 / 데이터미보유) 구분은
그대로 산다 — 사용자가 할 수 있는 일이 다르기 때문에 가른 것이다.

## 6. 취합기와 검증

취합기는 답변자들의 `근거`·`한계` 를 받아 **문장 배열**을 낸다.

```json
{ "문장": [
    { "글": "8월 청년 취업자는 380.1만 명으로 전년 대비 4.2만 명 줄었다.",
      "출처": ["employment"], "인용": [] },
    { "글": "KLI 는 이 감소를 인구구조 변화로 설명한다.",
      "출처": ["reports"], "인용": [{ "id": "kli-10303", "대목": "젊은 생산가능인구는 매년 큰 폭으로" }] }
  ],
  "한계": [], "미확인": [], "후속질문": [] }
```

문장 배열이어야 하는 이유는 검증 때문이다. 지금도 어긋난 문장만 버리고 근거는 남기는데,
답변이 한 덩어리 문자열이면 그 "문장만" 이 문자열 자르기가 된다. 배열이면 단위가 명확하다.

검증 규칙은 둘이고 둘 다 기존 규율의 연장이다.

- **숫자** — 문장의 모든 숫자가 그 문장이 밝힌 출처의 `숫자모음` 에 있어야 한다.
  천 단위 구분자를 읽는 `extractNumbers` 는 그대로 쓴다(2026-09-09 에 이것 때문에
  정상 답변이 환각으로 몰린 적이 있다).
- **인용** — `인용[].대목` 이 그 `id` 의 `허용텍스트` 에 문자열로 들어 있어야 한다.
  없으면 그 문장만 버린다.

`검증진단` 이 `표기차이`(우리 쪽 문제)와 `근거밖`(환각)을 가르는 지금 규칙도 그대로 둔다.

## 7. 데이터 경로

`tools/d1_sync.py` 에 대상 둘을 추가하고, 각 수집 워크플로가 자기 데이터를 민다.

| 대상 | 원본 | D1 표 |
|---|---|---|
| `reports` | `domains/reports/data/reports.json` + `abstracts.json` | `report` |
| `press` | `domains/press/data/articles.json` · `rounds.json` | `article` · `press_round` |

`report` 는 초록을 별도 표로 가르지 않는다. D1 과금은 **스캔한 행 수** 기준이라 칸 너비가
비용이 아니다 — 웹앱이 `abstracts.json` 을 가른 것은 첫 화면 전송량 때문이었고 여기엔
그 이유가 없다.

`article` 은 회차·구분(정규/후속)·제목·언론사·발행시각·인용여부·판정사유·`hits`·논조·
밖키워드를 든다. `press_round` 는 회차 분석(coverage·gaps·outside·tone·issues·frames)을
JSON 칸으로 든다 — 이것들은 조회 조건이 아니라 통째로 읽는 값이다.

동기화 스텝은 기존 둘과 같이 `continue-on-error: true` 로 둔다. 다만 그 때문에 동기화가
며칠째 죽어도 실행 목록이 초록으로 보이는 문제가 이미 있으므로, **`last_run.json` 에
동기화 시각을 남겨** 화면이 그것을 읽게 한다(§11-2).

## 8. 카탈로그 등재

§5 의 한계들을 답변자 코드에 문자열로 박지 않고 카탈로그 행으로 넣는다. 그러면 "왜 못
답하는지" 가 기존 문법으로 나오고, 한계가 코드가 아니라 데이터로 관리된다.

```
source_catalog   reports  연구보고서 아카이브   grade 2차   axis 문헌
                 press    행통 기사 모니터링   grade 2차   axis 보도
capability       reports  주제 17개 그룹 · 기간 2021~ · 시간입도 발간일
                 press    집단축 연령·산업·성·지표 · 기간 2026-06~ · 시간입도 회차
capability_limit reports  커버리지  초록 없는 보고서 257건 — 제목·목차로만 걸린다
                 reports  커버리지  원문 전문은 색인하지 않는다 — 초록·목차까지
                 press    커버리지  기사 본문을 저장하지 않는다
                 press    커버리지  보도자료 전후 창에서만 수집 — 언론 보도 표본이 아니다
                 press    시의성    3회차(2026-06~08월분)뿐
```

## 9. 화면

**허브** — 질문 입력창 + 도메인 카드 4개. `hub/js/state.js` 의 `DOMAINS` 에서 `ask` 를
빼고(카드가 아니라 입력창이 된다) `supply` 를 삭제한다. `supply` 는 카드만 있고 도메인
폴더가 없는 죽은 카드다(2026-09-10 확인). 입력창을 ask 앱으로 넘기는 `askHref()` 는 이미
있다.

**질의응답** — 최종 답변이 맨 위, 그 아래 도메인별 근거 카드. 답변 문장의 출처 표시를
누르면 해당 카드로 내려간다. 버려진 문장이 있으면 지금처럼 배지로 알린다.

## 10. 테스트

- **파이썬** — `d1_sync` 의 새 대상 둘. 표 투영과 회차 중첩 평탄화
- **워커** — 답변자 다섯을 각각 가짜 D1 으로 골든 검증(LLM 없이 결정적으로 돈다) ·
  라우터가 도메인을 고르고 못 고르면 이유를 내는지 · 취합기가 근거 밖 숫자나 없는 인용을
  쓰면 **그 문장만** 버리는지 · 카탈로그 한계가 답에 실려 나오는지
- **웹** — 허브 카드 4개와 입력창 · 질의응답의 답변/카드 배치
- **원칙** — 네트워크에도 LLM 에도 나가지 않는다. 주입 지점으로 막고 그 사실을 테스트가
  지킨다. **가짜가 실물보다 관대하면 거짓 안심을 준다** — 이 도메인에서 가짜 KV 가
  `String(v)` 를 대신 해 줘 IP 할당량이 통째로 무효였던 전례가 있다

## 12. 단계

한 번에 다 갈아엎지 않는다. 각 단계 끝에서 **배포 가능한 상태**여야 한다.

| 단계 | 내용 | 끝났을 때 |
|---|---|---|
| A | 답변자 계약과 라우터를 세우고, **지금 있는 셋**(고용동향·고용전망·원인탐색)을 그 계약으로 옮긴다. 취합기와 문장 단위 검증까지 | 답은 지금과 같은 원천에서 나오지만 경로가 새것이다. 회귀가 여기서 다 드러난다 |
| B | `d1_sync` 에 `reports` 대상 추가 · `report` 표 · 연구보고서 답변자 · 카탈로그 등재 | 문헌 카드가 붙는다 |
| C | `d1_sync` 에 `press` 대상 추가 · `article`·`press_round` 표 · 행통 답변자 · 카탈로그 등재 | 기사 카드가 붙는다 |
| D | 허브 개편(입력창 + 카드 4개, `supply` 삭제) | 한 채널이 된다 |

A 를 먼저 하는 이유는 **회귀를 새 기능과 섞지 않기 위해서**다. A 에서 골든 세트가
지금과 같은 답을 내면 경로 교체가 안전했다는 뜻이고, 그 뒤 B·C 의 실패는 전부 새
코드 탓으로 좁혀진다.

## 13. 규모와 위험

가장 큰 위험은 **취합기가 도메인을 섞어 문장을 쓰는 것**이다. "관측은 줄었는데 전망은
늘어난다" 같은 문장은 두 출처를 함께 밝혀야 하는데, LLM 이 하나만 달면 검증이 다른
출처의 숫자를 근거 밖으로 판정해 정상 문장을 버린다. 그래서 검증은 **문장이 밝힌 출처들의
숫자모음 합집합**과 대조한다.

두 번째 위험은 라우터가 도메인을 너무 많이 고르는 것이다. 다섯을 다 부르면 근거가
부풀고 토큰이 늘어난다. 슬롯이 비면 부르지 않는 것을 기본으로 하고, 부른 도메인과 부르지
않은 도메인을 **화면이 밝힌다** — 조용히 빠지는 것이 가장 나쁜 실패다.
