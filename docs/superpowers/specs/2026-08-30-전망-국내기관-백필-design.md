# 전망 아카이브 — 국내기관 소급 수집(백필) 설계

작성일: 2026-08-30
상태: 검토 대기
선행 문서: `고용전망_아카이브_기획서.md`, `docs/superpowers/specs/2026-08-29-고용데이터아카이브-플랫폼-design.md`
범위: A1 (한국은행·KDI). A2(IMF·OECD 회차화)는 별도 스펙.

---

## 1. 배경

아카이브의 값은 **회차별 수정 이력**에 있다. 같은 2026년 전망을 기관이 회차마다
어떻게 고쳐 왔는지를 한자리에서 보는 것이 목적이다.

그런데 현재 저장된 44건은 **기관마다 회차가 하나씩**뿐이다.

| 기관 | 보유 회차 | 레코드 |
|---|---|---|
| 한국은행 | 2026-08-27 | 30 |
| OECD | (수집일 2026-08-29) | 8 |
| IMF | (수집일 2026-08-29) | 6 |
| KDI | 없음 | 0 |

수집기가 매일 **최신 회차 하나**만 보기 때문이다. 이는 일상 수집기로서 올바른
동작이며 바꾸지 않는다. 다만 아카이브를 시작하기 전에 이미 지나간 회차들은
그 경로로 영원히 들어오지 않는다. **1회성 소급 수집이 필요하다.**

백필이 끝나면 한국은행은 보유 1회차에 7회차가 더해지고, KDI는 6회차 전부가
새로 들어온다. 그전에는 화면의 수정폭이 전부 `—`이고, 추이 차트는 점 하나다.

## 2. 범위

### 대상

**발표일이 `2024-11-01` 이후인 모든 회차.** 2026년 전망이 처음 등장한 시점
(한국은행 2024년 11월호가 2025·2026년을 전망)을 기준으로 못 박는다.

자동 판정(과거로 훑다가 2026년 전망이 사라지면 멈춤)을 쓰지 않는 이유: 옛 회차일수록
표 서식이 지금과 달라 파싱이 깨질 확률이 높은데, 자동 판정은 **파싱 실패와 "회차 없음"을
구별하지 못해** 조용히 덜 가져온다. 1회성 작업에서는 "몇 회차를 시도했고 몇 개를
못 읽었는지"가 눈에 보이는 편이 낫다. 헛걸음 몇 번은 다운로드 비용뿐이다.

확인된 대상:

| 기관 | 회차 수 | 목록 경로 |
|---|---|---|
| 한국은행 | 8 (2024-11 ~ 2026-08, 분기) | 게시판 RSS — 2014년까지 51회차가 남아 있음 |
| KDI | ~6 | `/research/economy` 연도 선택 목록 |

### KDI는 보류 (2026-08-30)

`www.kdi.re.kr` 전체가 502다. 앞단 nginx는 응답하지만 뒤의 애플리케이션이 죽어 있어
**목록·본문·첨부 다운로드 엔드포인트(`/file/download`)까지 전부** 막혀 있다. 우리가
차단된 것이 아니라 KDI 쪽 장애다.

우회 경로를 찾아봤으나 없다:

| 시도 | 결과 |
|---|---|
| `eiec.kdi.re.kr` (경제정보센터, 별도 호스트) | 살아 있음(200). 다만 실린 「경제전망」(2026년8월)은 **한국은행 보도자료**를 가져다 실은 것 — 한국은행 파서로 읽으니 값이 우리 저장분과 일치. KDI 자체 경제전망은 검색해도 없음 |
| `www.kdi.re.kr/rss/rss.jsp` | 502 |
| `kdi.re.kr` (www 없이) | DNS 없음 |

따라서 **A1은 한국은행만으로 먼저 완료하고**, KDI는 서버 복구 후 같은 구조에
`list_issues()`/`collect_issue()`를 채워 넣는다. 기관 지정 실행(`backfill bok`)을
지원하는 이유가 이것이다.

### 범위 밖

- IMF·OECD 백필, OECD Interim, 두 기관의 `published_at` 의미 변경 → **A2**
- 한국노동연구원·기획재정부·ADB·산업연구원·고용정보원 수집기 → **B**
- 일상 수집기(`collect.main`)의 동작 변경

## 3. 설계

### 3.1 수집기를 두 단계로 나눈다

지금 `bok.collect(today)`가 한 함수 안에서 하는 일이 이미 두 단계다. 그대로 쪼갠다.

```
collectors/bok.py
    list_issues() -> list[Issue]          # RSS에서 회차 목록, 최신순
    collect_issue(issue) -> list[Record]  # 본문 → PDF → 요약표 파싱
    collect(today)                        # = collect_issue(list_issues()[0])

collectors/kdi.py
    list_issues() -> list[Issue]          # 연도 선택 목록
    collect_issue(issue) -> list[Record]  # 장별 PDF에서 요약표 장 탐색
    collect(today)                        # = collect_issue(list_issues()[0])
```

일상 경로는 "목록의 첫 회차"라는 의미가 코드에 드러날 뿐 동작이 같다.
백필은 같은 두 함수를 범위로 순회한다. 회차 목록·다운로드 로직이 한 벌만 남는다.

대안으로 검토한 것:
- **수집기마다 `collect_range(since)` 추가** — 목록·다운로드 로직이 `collect`와 중복된다.
  방금 `report.py`로 없앤 종류의 중복이 다시 생긴다.
- **`tools/`에 스크립트를 두고 내부 함수 직접 조합** — `parse_rss`·`parse_pdf_link` 같은
  내부에 의존해 수집기를 고칠 때마다 깨진다.

KDI의 `list_issues()`는 신규 구현이다. 현재 `collect()`는 `/research/economy`가
곧 최신호 본문이라 목록을 파싱하지 않는다. 과거 회차는 연도 선택 `<select>`의
`<option value="19180">2026 상반기</option>` 같은 항목이 회차 식별자를 준다.
회차별 본문 URL 형태는 사이트 복구 후 확인한다.

### 3.2 저장 — `drop_unchanged`를 쓰지 않는다

백필은 후보를 `store.merge`에 **바로** 넘긴다.

`collect.drop_unchanged`는 전역 최신 레코드와 값을 비교한다(`before=` 없음).
백필은 과거 회차를 넣으므로, 2025-11호 값이 이미 저장된 2026-08호와 같으면
**조용히 버려진다.** 백필에는 틀린 규칙이다.

`store.merge`가 그 역할을 대신한다. 이미 백필에 안전하게 돼 있다:
- 후보를 `published_at` 오름차순으로 정렬해 넣는다
- id가 이미 있고 값이 같으면 `skipped`
- id가 같고 값이 다르면 일(日) 정밀도 id로 다시 매겨 회차를 살린다
- `_add`가 `latest_record(..., before=cand.published_at)`로 직전 회차를 찾아
  `prev_value`·`revision`을 계산한다

일상 수집기의 `drop_unchanged`는 그대로 둔다. API 수집기(IMF·OECD)가 매일
`published_at=오늘`인 레코드를 만들어내는 것을 막는 장치이며, 그 문제는 A2에서
`published_at`이 발표일로 바뀔 때 다시 본다.

### 3.3 revision 재계산 패스

**함정.** `_add`는 레코드를 넣는 **시점에 존재하는 것**만 보고 `revision`을 계산한다.
이미 저장된 2026-08호는 "앞선 회차 없음"으로 계산돼 `revision`이 비어 있다.
5월호를 나중에 넣어도 8월호의 수정폭은 계속 `—`로 남는다.

그래서 백필 끝에 **전 레코드의 `prev_value`·`revision`을 다시 계산하는 패스**를 돌린다.

```
recompute_revisions(records) -> list[Record]
    (org, indicator, target_year, target_period) 별로 published_at 오름차순 정렬
    각 레코드의 prev_value = 직전 레코드의 value, revision = 차이(소수 2자리)
    계열의 첫 레코드는 prev_value=None, revision=None
```

`store.py`에 둔다. `_add`의 계산 규칙과 결과가 같아야 하므로 같은 파일에서 관리한다.

### 3.4 실행과 보고

```
python -m domains.forecast.pipeline.backfill            # 전체
python -m domains.forecast.pipeline.backfill bok        # 기관 지정
```

- 로컬 1회성 실행. **CI에 넣지 않는다.**
- `forecasts.json`을 갱신하고, 결과를 사람이 읽을 표로 찍는다.
- 회차 하나의 실패가 나머지를 막지 않는다(`kdi.collect`의 장 단위 격리와 같은 규칙).

출력 형태:

```
한국은행  8회차 시도
  2026-08-27  건너뜀 (이미 있음)
  2026-05-28  30건
  2026-02-26  30건
  2025-11-27  30건
  ...
  2024-11-28  실패 — 표 헤더 불일치: 연도 [2024, 2025] vs 기간 블록 [...]

요약: 시도 8 / 성공 6 / 건너뜀 1 / 실패 1
실패한 회차: 2024-11-28
```

`last_run.json`은 건드리지 않는다. 일상 수집의 기록이지 백필의 기록이 아니다.

### 3.5 실패를 조용히 넘기지 않는다

옛 회차는 표 서식이 다를 수 있다. `pdf._columns`는 이미 헤더의 연도 수와 기간 블록
수가 어긋나면 `ValueError`로 터지게 돼 있고, `find_summary_table`은 그런 페이지를
건너뛰다 끝내 못 찾으면 `None`을 준다. 두 경우 모두 백필 보고서의 **실패 목록**에
회차와 이유가 남는다. 부분적으로 읽힌 표가 조용히 저장되는 경로는 없다.

## 4. 테스트

| 대상 | 방식 |
|---|---|
| `list_issues` / `collect_issue` 분리 | 기존 `test_bok.py`·`test_kdi.py`가 그대로 보증 (동작 불변) |
| 옛 서식 파싱 | 실제 과거 회차 PDF에서 요약표 텍스트를 떠 픽스처로 추가 (한국은행 2024-11·2025-05) |
| `recompute_revisions` | 단위 테스트 — 계열 하나에 회차 3개, 중간 회차를 나중에 넣어도 수정폭이 맞는지 |
| 백필 진입점 | 가짜 수집기(`list_issues`/`collect_issue`)로 순회·건너뜀·실패 격리·보고서 검증 |
| 실패 격리 | 회차 하나가 예외를 던져도 나머지가 저장되는지 |

네트워크는 쓰지 않는다. 기존 테스트와 같은 규칙이다.

## 5. 리스크

| 리스크 | 대응 |
|---|---|
| 2024~2025 회차의 표 서식이 달라 파싱 실패 | 실패 목록에 남는다. 픽스처를 떠서 파서를 넓히거나, 해당 회차를 포기하고 기록한다 |
| KDI 사이트 502 (현재 진행 중) | 한국은행만으로 A1 을 완료한다. 우회 경로는 없음이 확인됐다(2절) |
| 백필이 기존 레코드를 훼손 | `merge`는 append만 하고 기존 레코드를 고치지 않는다. 유일한 변경은 `recompute_revisions`이며 `prev_value`·`revision` 두 필드만 손댄다 |
| 한국은행 PDF가 큼 (회차당 전 페이지 텍스트 추출) | 1회성이라 감수한다. 8회차 × 수십 초 |

## 6. 완료 기준

- `python -m domains.forecast.pipeline.backfill bok`이 2024-11 이후 회차를 순회하고,
  성공·건너뜀·실패를 회차별로 보고한다
- `forecasts.json`에 한국은행 회차가 2개 이상 들어 있다
- 홈 카드의 수정폭이 `—`가 아닌 실제 값으로 표시된다
- 기관 상세의 추이 차트에 점이 2개 이상 찍힌다
- 기존 테스트가 모두 통과하고, 일상 수집 동작이 변하지 않는다
