# 고용데이터 아카이브 — 연구보고서(reports) 도메인 설계

- 작성일: 2026-09-10
- 상태: 설계 확정 (구현 계획 대기)
- 검토 반영: 2026-09-10 — 판정을 빌드 시점으로 분리(§5-3), 타임라인 접기·부분 날짜(§4-2·§6-1),
  실패 판정을 게시판 단위로(§7-1), 초록 결측률 기록과 검색 폴백 순서(§7-2·§4-3)
- 슬러그: `reports` · 표시 이름: **연구보고서**

> **한 줄 정의**: 고용·노동 분야 국책연구 보고서를 네 기관(KLI·KEIS·KDI·KIET)에서 모아
> 한곳에서 검색하고, 주제로 묶어 다시 찾을 수 있게 한다. 원문은 기관 서버로 내보낸다.

## 0. 왜 만드는가

NTIS(`ThMain.do`) 같은 고용 분야 아카이브가 없다. 그래서 과가 예산을 들여 발주한 용역사업
결과물조차 책자로 전달받은 뒤 책상에 꽂힌 채 잊혀지고, 정작 그 예산을 집행한 과의 과원이
활용하지 못한다. **이 도메인이 푸는 것은 "보고서가 없는 문제"가 아니라 "있는데 못 찾는
문제"다.** 설계 판단이 갈릴 때마다 이 기준으로 자른다.

이 문제 인식에서 나오는 직접적 귀결이 하나 있다. 최신 발간물만 보여주는 화면은 문제를
풀지 못한다 — 잊혀진 보고서는 정의상 최신이 아니다. 그래서 타임라인과 별도로 **주제 화면**을
1차 범위에 넣는다(§6-2).

## 2. 실측 (2026-09-10)

네 기관 모두 **JS 렌더링이나 로그인 벽 없이 서버가 완성된 HTML을 내려준다.** 상세 URL이
숫자 id에 페이지 파라미터가 노출돼 있어 파서가 단순하다. A안을 고른 근거가 이것이다.

| 기관 | 목록 | 상세 URL | 원문 | 확인된 특이사항 |
|---|---|---|---|---|
| KLI | 서버렌더 | `/kli/newestPblctView.es?pblct_sn=10302` | 목록에 PDF 직링크 | 게시판이 `menu.es?mid=` 코드로 갈림 |
| KEIS | 서버렌더 | `/keis/ko/proj/113/pblc/list.do` | `preview.do?dn=….pdf` | **메뉴가 JS라 게시판 id를 코드에서 못 읽음.** `proj/113`·`proj/117`만 확인 |
| KDI | 서버렌더 | `/research/reportView?pub_no=19257` | 상세 + `/file/download?atch_no=…` | **Open API 별도 제공**(`/share/openAPI`). 항목마다 자체 주제코드(`topicList?cd=L&sub=L11`) |
| KIET | 서버렌더 | `/research/reportView?report_no=1149&pg=1&pp=10` | 상세 | `pg`·`pp`로 페이지 크기 조절 가능 |

추가로 확인한 것:

- **KIET 월간 KIET 산업경제**는 호 단위가 아니라 **글 단위**로 목록이 있다.
  `/research/economyDetailList?detail_gubun=All` → `economyDetailView?detail_no=3235`.
  그래서 다른 게시판과 같은 방식으로 담긴다.
- **KDI 기타보고서 게시판의 분류 라벨은 5종**이다: `CID 연구보고서` / `기타보고서` /
  `예비타당성조사보고서` / `조세특례 성과평가사업` / `타당성 재조사 보고서`.
  이 중 `기타보고서`만 담는다(사용자 결정). 예타·타당성재조사 대량 문서가 통째로 빠진다.
- **KDI Open API가 존재한다.** 구현 첫 단계에서 스크레이핑보다 나은지 재본다. 다만 이것이
  A안을 뒤집지는 않는다 — 나머지 세 기관은 어차피 파서가 필요하다.

## 3. 아키텍처

기존 도메인(`press`·`forecast`)과 같은 수직 슬라이스다. `hub/`·`core/`·`tools/build.py`는
**한 줄도 고치지 않는다** — `tools/build.py`의 `discover_domains`가 `domains/*/app`을 스스로
찾고, 허브 버튼은 `data/last_run.json`이 생기면 켜진다.

```
domains/reports/
  pipeline/
    http.py            공통 요청 — UA · 요청 간 지연 · 재시도 · 인코딩 판정
    models.py          Report 자료구조와 정규화
    store.py           raw upsert (같은 보고서면 덮지 않는다)
    keywords.py        고용 키워드 매칭 — build.py 가 쓴다
    boards.py          boards.json 로드 + 미등록 게시판 탐지
    sites/
      kli.py  keis.py  kdi.py  kiet.py     ← 파서 격리
    collect.py         오케스트레이션 (수집기 주입 지점) → 끝에서 build 호출
    build.py           ★ raw + keywords.json → reports.json · abstracts.json
    check_run.py       회차 성공/실패 판정
  sources/
    raw/{org}/{board}.json     게시판에 있던 것 전부 (판정 이전)
  data/
    reports.json  abstracts.json  boards.json  keywords.json
    orgs.json  last_run.json  schedule.json
  app/
    index.html  sw.js  manifest.webmanifest
    js/app.js  data.js  ui.js  search.js
    js/screens/home.js  topics.js  orgs.js  report.js
    css/app.css  icons/
  tests/
    fixtures/            실제 페이지를 고정한 HTML
    test_kli.py  test_keis.py  test_kdi.py  test_kiet.py
    test_collect.py  test_build.py  test_keywords.py
    test_boards.py   test_check_run.py
    web/
```

**파서 격리가 이 구조의 핵심이다.** `sites/*.py`는 각자 자기 기관의 HTML만 안다. 한 기관이
사이트를 개편해도 나머지 셋은 계속 돈다. 기관을 늘리려면 파일 하나와 `boards.json` 몇 줄이면
된다.

**두 번째 핵심은 수집과 판정을 분리한 것이다.** `collect.py`는 게시판에 있는 것을 판정 없이
전부 `sources/raw/`에 넣는다. 고용 여부를 가르고 `data/*.json`을 만드는 것은 `build.py`가
`keywords.json`을 읽어서 한다. 경계가 여기 있는 이유는 §5-3에 있다.

```
사이트 ──collect.py──▶ sources/raw/   ──build.py──▶ data/reports.json
        (네트워크, 며칠)  (판정 이전 전부)  (수십 초)   data/abstracts.json
                                            ▲
                                    data/keywords.json
```

## 4. 데이터

### 4-1. 파일 분할

초록·목차까지 한 파일에 넣으면 3~7MB다. 첫 화면에서 그걸 다 받게 하면 안 된다.

| 파일 | 내용 | 예상 크기 | 언제 받나 |
|---|---|---|---|
| `reports.json` | 제목·기관·게시판·발간일·저자·링크·키워드 | ~400KB | 앱 진입 즉시 |
| `abstracts.json` | 초록 전문 · 목차 | 3~7MB (gzip 후 1~2MB) | **검색창에 포커스가 가면 미리** |
| `boards.json` | 담을 게시판 목록 | ~4KB | 앱 진입 즉시 |
| `keywords.json` | 고용 키워드 집합 | ~2KB | **앱은 안 받는다** — `build.py` 전용 |
| `orgs.json` | 기관 이름·약칭·색 | ~1KB | 앱 진입 즉시 |
| `last_run.json` | 수집 시각·건수·경고 · **초록 결측률** | ~2KB | 앱 진입 즉시 |

`sources/raw/`는 위 표에 없다. **배포에 실리지 않는다** — `tools/build.py`가 도메인에서
복사하는 것은 `app/`과 `data/`뿐이다. raw는 저장소에만 남아 `build.py`의 입력이 된다.

타임라인과 제목 검색은 `reports.json`만으로 돈다. 초록 본문 검색은 `abstracts.json`이 필요한데,
**검색창에 포커스가 가는 순간 미리 받고 서비스워커가 캐시하므로** 타이핑을 시작할 때는 이미 와
있다. 결과가 두 단계로 늘어나 보이는 일은 없다.

### 4-2. 레코드 스키마

```json
{
  "id": "kli-10302",
  "org": "kli",
  "board": "kli-research",
  "series": "연구보고서",
  "title": "청년 고용정책의 성과와 과제",
  "authors": ["홍길동", "김철수"],
  "published": "2026-08-27",
  "date_precision": "day",
  "pages": 214,
  "landing_url": "https://www.kli.re.kr/kli/newestPblctView.es?pblct_sn=10302",
  "file_url": "https://www.kli.re.kr/kliFileDownload?fileName=…",
  "employment": true,
  "matched": ["청년고용", "일자리"],
  "collected_at": "2026-09-10T02:31:00+09:00"
}
```

`sources/raw/`의 레코드는 `employment`·`matched`가 **없는** 같은 모양이다. 그 둘은
`build.py`가 붙인다. 나머지 필드는 수집기가 채운 것이 그대로 간다.

`abstracts.json`은 `{"kli-10302": {"abstract": "…", "toc": ["…"]}}` 형태로 id에 매단다.

필드 몇 개는 이유가 있어서 있다.

- **`series`** — 네 기관이 성격이 아주 다른 것을 같은 목록에 섞어 낸다. KLI만 해도
  200쪽 연구보고서와 4쪽 브리프가 한 목록에 있다. 같은 줄로 보여주면 목록이 쓸모없어진다.
- **`matched`** — 왜 이 보고서가 담겼는지 화면에서 보이게 한다. 키워드 집합을 고칠 때
  무엇이 들어오고 나갔는지 재려면 근거가 레코드에 남아 있어야 한다.
- **`employment`** — 매칭 결과가 아니라 **판정 결과**다. 둘은 다르다(§5-3).
- **`id`** — `{org}-{기관 고유번호}`. 기관이 부여한 번호를 그대로 쓰므로 재수집해도 안 흔들린다.
- **`date_precision`** — 발간일이 어디까지 확실한지. `day` / `month` / `year` 셋 중 하나다.

**부분 날짜 정규화.** 게시판이 `2025-12`나 `2025`로만 주는 경우가 있다. `published`는
정렬이 깨지지 않게 **월말·연말로 채우되**(`2025-12` → `2025-12-31`, `2025` → `2025-12-31`),
채웠다는 사실을 `date_precision`에 남긴다. 이 필드가 없으면 화면이 "2025년 12월 31일 발간"
이라고 단정하게 되고, 그건 데이터에 없는 말이다. 화면은 `month`면 `2025.12`, `year`면
`2025년`으로만 적는다.

`store.upsert`는 **같은 id의 값이 같으면 덮지 않는다.** 기존 도메인과 같은 규칙이고, 이유도
같다 — 내용이 같은데 `collected_at`만 바뀌어 매일 커밋이 나는 것을 막는다.

### 4-3. 검색

**역색인을 만들지 않는다.** 브라우저에서 직접 훑는다.

- 2천 건 규모에서 문자열 스캔은 수십 밀리초다. 역색인이 사는 규모가 아니다.
- 한국어 토큰화를 직접 하면 "청년고용"이 "청년 고용"에 안 걸리는 문제를 떠안는다.
  **공백을 무시한 부분일치**로 그 문제를 아예 없앤다.
- 규모가 열 배가 되면 그때 단다. 지금 만들 이유가 없다.

정렬은 관련도순이 기본이고 최신순 토글을 둔다. 가중치는 **제목 > 저자 > 초록·목차** 순.

**본문 폴백 순서: 초록 → 목차 → 제목.** 초록이 있으면 초록을 훑고, 없으면 목차를, 그것도
없으면 제목만 남는다. 초록 결측이 드물지 않으므로(§7-2) 이 순서를 정해두지 않으면 같은
검색어가 기관에 따라 다르게 걸린다. **검색 결과에 잘라 보여주는 매칭 문장도 같은 순서**를
따른다 — 초록에서 걸렸으면 초록 문장을, 목차에서 걸렸으면 그 목차 줄을 보여주고, 제목에서만
걸렸으면 스니펫 없이 제목만 강조한다.

## 5. 수집

### 5-1. 게시판은 설정으로 명시한다

사이트는 스스로 "이건 보고서 게시판"이라고 알려주지 않는다. 같은 사이트 안에 200쪽
연구보고서와 보도자료가 나란히 있다. 그래서 **담을 게시판을 `boards.json`에 사람이 적는다.**

```json
{ "id": "kli-research", "org": "kli", "name": "연구보고서",
  "series": "연구보고서", "list_url": "https://www.kli.re.kr/menu.es?mid=a10102060000",
  "filter": false, "enabled": true, "collapse": true }
```

여기에 **가드를 붙인다**: 수집기가 매 회차 각 기관 메뉴를 훑어, `boards.json`에 없는 게시판이
나타나면 `last_run.json`에 경고를 남긴다. **자동으로 담지 않는다.** 사이트 개편으로 게시판이
새로 생겼을 때 조용히 놓치는 것을 막으려는 것이고, `press` 도메인의 `KNOWN_DOWN`이 스위치가
아니라 알람인 것과 같은 성격이다.

| **KEIS** | 연구사업보고서 · **인력수급전망** · 고용이슈 · 고용동향브리프 · 지역산업과 고용 · 산업일자리 전환 지도 | 직업진로정보서 | 없음 |

**KEIS 는 목록 페이지가 곧 상세다**(2026-09-10 실측). 항목마다 초록·키워드·PDF 링크를
목록 안에 다 들고 있고 별도 상세 페이지가 없다. 그래서 `boards.json` 에 `detail_in_list`
플래그를 두고, 켜져 있으면 수집기가 상세를 다시 요청하지 않는다 — 연구사업보고서만
870건이라 이 플래그가 꺼지면 회차마다 870번을 헛되이 더 요청한다.

KLI·KEIS는 기관 전체가 고용·노동 분야라 필터를 걸지 않는다. 워킹페이퍼를 뺀 것은 영문
번역본 성격이라는 사용자 판단이다.

### 5-3. 고용 키워드 — 판정은 수집이 아니라 빌드에서 한다

**수집기는 아무것도 거르지 않는다.** `boards.json`이 켜둔 게시판에 있는 것을 제목·초록·목차까지
전부 `sources/raw/`에 넣는다. 고용 여부를 가르는 것은 `collect.py` 마지막에 도는
`build.py`이고, 그때 `keywords.json`을 읽는다.

**이유는 키워드를 고칠 때 드는 비용이다.** 판정이 수집 안에 있으면 키워드 한 줄을 바꿀 때마다
KDI·KIET를 다시 긁어야 하고, 게시판 예의 때문에 그게 며칠이다(§5-4). 판정을 빌드로 빼면
`python -m domains.reports.pipeline.build` 한 번, 수십 초로 끝난다. 키워드 집합은 처음에
반드시 틀리고 몇 번은 고쳐야 하는 종류의 데이터라, 고치는 비용이 이 설계의 성패를 가른다.

판정에 초록을 쓰기로 한 이상 **비고용 보고서도 상세는 어차피 긁는다.** 그래서 이 변경으로
회차당 상세 상한이나 백필 기간이 늘지 않는다 — 판정 시점만 뒤로 미룬 것이다.

`matched`를 전 기관에 남기기로 한 것(아래)과도 방향이 같다. raw에 다 담아두고 거르는 것은
나중에 하는 쪽이, 거르고 나서 되돌리려는 쪽보다 항상 싸다.

**매칭은 네 기관 전부에 돌린다. 판정에 쓰는 것만 KDI·KIET로 한정한다.**

```
raw        = 게시판에 있던 것 전부                ← collect.py, 판정 없음
matched    = 제목·초록에서 걸린 키워드 목록       ← build.py, 전 기관
employment = filter 켜진 게시판이면 matched 유무, 꺼져 있으면 항상 true
reports.json 수록 = employment == true
```

둘을 나누지 않으면 KLI·KEIS 레코드의 `matched`가 비어 **주제 화면이 반쪽이 된다**(§6-2).
매칭은 다 남기고 쓰임만 다르게 하면 주제 묶음이 네 기관에 걸쳐 공짜로 나온다.

키워드 집합은 코드가 아니라 `data/keywords.json`에 둔다. 고치는 사람이 파이썬을 안 열어도
된다. **화면은 이 파일을 받지 않는다** — 주제 칩은 레코드에 이미 박혀 있는 `matched`에서
역산하므로, 키워드를 고쳐도 다음 수집이 돌기 전까지 화면이 데이터와 어긋나지 않는다.

### 5-5. 초록이 비면 원문 PDF 에서 요약 섹션을 뜯는다 (2026-09-10 추가)

§7-2 가 재기로 한 결측률의 첫 숫자가 나왔다 — **raw 805건 중 345건이 초록 없음**,
그중 **87건은 목차마저 없어 제목 한 줄로만 검색된다**(KEIS 인력수급전망 38 ·
KDI FOCUS 37 · KDI 현안분석 12). §9-3 이 예비로 둔 NKIS 경유(C안) 대신, **이미
가지고 있는 `file_url` 의 원문 PDF 에서 저자가 쓴 `요 약` 섹션을 읽는다.**

`enrich.py` 가 별도 진입점이다. 수집과 가르는 이유는 §5-3 과 같다 — 수집은 매일
목록을 훑는 일이고, 이것은 아는 레코드의 빈 칸을 채우는 일이다.

- **PDF 는 저장소에 남기지 않는다.** 메모리에서 앞 20쪽 텍스트만 뽑고 버린다.
  원문은 기관 서버가 정본이고, 받아 두면 그 시점에 굳는다.
- **한 번 시도하면 `abstract_tried` 로 표시해 다시 받지 않는다.** 없으면 요약이
  없는 문헌(잡지·통계집·발제문집)을 회차마다 헛되이 다시 내려받는다.
- **못 채운 이유를 `abstract_note` 에 남긴다.** 스캔본(OCR 없이는 영영 불가)과
  '요약 섹션 없음'(기관이 안 쓴 것)은 손쓸 수 있는 것이 다르다. `build` 가
  이것을 세어 `last_run.json` 의 `abstract_missing_why` 에 넣는다 — §9-3 판단은
  결측률이 아니라 이 구분에 걸려 있다.
- **요약 섹션이 없으면 아무것도 내지 않는다.** 본문 앞부분을 대신 싣는 안(발췌)을
  만들어 42건으로 실측까지 했다가 뺐다(사용자 결정). 저자가 "이게 요약이다" 라고
  쓴 글이 아니라는 것이 하나고, 브리프류가 거의 다 2단 조판이라 흔한 PDF 추출기가
  좌우 단을 한 줄씩 번갈아 이어 붙여 **사람이 읽을 수 없는 글**이 나온다는 것이
  하나다. 덩어리를 갈라 읽으면 풀리지만(시제품으로 확인했다), 그렇게까지 해서
  얻는 것이 목차도 초록도 없는 49건뿐이라 값이 안 맞았다.
- 2단인지 **판별**해서 그것만 거르는 안도 세 가지 방법으로 실측했는데 전부
  갈리지 않았다 — 좌측 여백에 제목만 세로로 세운 판(KDI FOCUS), 쪽마다 단 수가
  바뀌는 판이 섞여 있다. 되살릴 일이 있으면 판별이 아니라 덩어리 분해로 간다.

## 6. 화면

셸은 기존 규약을 그대로 따른다. `.app`은 `height: 100dvh`(`min-height` 아님), 스크롤 주체는
`.screen`, **헤더 제목은 `연구보고서`로 고정하고 탭을 따라 바꾸지 않는다.**

### 6-1. 홈 — 검색창 + 최신발간 타임라인

검색창이 맨 위에 상주하고 그 아래가 기본 상태에서 타임라인이다. 월 헤더(`2026년 8월`)로
끊고, 한 줄에 기관 배지 · 제목 · 게시판 이름이 들어간다.

**같은 달·같은 기관·같은 시리즈가 N건을 넘으면 한 줄로 접는다** — `KLI 연구보고서 27건`처럼
쓰고, 누르면 펼친다. 연구보고서류는 12~2월에 몰려서, 접지 않으면 그 달의 타임라인이 한 기관
한 시리즈로 뒤덮이고 다른 기관 발간물이 화면 밖으로 밀린다. **브리프류는 접지 않는다** —
낱개로 나오고 제목이 곧 내용이라, 접으면 정보가 사라진다. 접기 여부는 게시판마다
`boards.json`의 `collapse` 로 정하고, N의 기본값은 5다.

**검색어를 치면 타임라인 자리가 결과로 바뀐다.** 별도 탭으로 보내지 않고, 지우면 타임라인으로
돌아온다. 검색창 아래 기관 칩 4개와 연도 칩이 있고, 이 필터는 타임라인과 검색 결과 양쪽에
똑같이 걸린다.

결과 한 줄에는 제목·기관·발간일에 더해 **검색어가 걸린 문장을 잘라 보여준다.** 제목에 없는
단어로 찾았을 때 왜 이게 나왔는지를 열어보지 않고 알 수 있어야 한다. 어디서 잘라 오는지는
§4-3의 폴백 순서(초록 → 목차 → 제목)를 따른다.

발간일은 `date_precision`을 따른다 — `month`면 `2025.12`, `year`면 `2025년`으로만 적는다.
없는 정밀도를 화면이 지어내지 않는다.

### 6-2. 주제

`matched`에서 역산한 주제 칩(청년고용 · 고령자 · 외국인력 · 임금 · 지역고용 …)을 놓고,
누르면 네 기관에 걸친 그 주제의 보고서 목록이 나온다.

**§0의 문제에 실제로 닿는 화면이 여기다.** 3년 전 보고서는 타임라인 저 아래에 있고,
검색은 찾을 단어를 이미 알아야 쓴다. 주제 화면은 단어를 모를 때 쓰는 입구다.

### 6-3. 기관

기관 4개 → 게시판별 건수(`KLI 연구보고서 137건`) → 그 게시판의 발간일순 목록.
뭐가 있는지 모를 때 서가를 훑는 용도다.

### 6-4. 보고서 상세 (`#/r/kli-10302`)

제목 · 기관 · 게시판 · 발간일 · 저자 · 쪽수, 초록 전문, 목차(접힘), 걸린 키워드 칩,
그리고 **원문 PDF 열기 / 기관 페이지 열기** 두 버튼.

**원문은 재배포하지 않는다.** 저작권 문제를 피하는 것도 있지만, 기관이 개정판을 올리면
링크 쪽이 자동으로 최신이 된다. 우리가 받아두면 그 시점에 굳는다.

## 7. 운영

**워크플로**: `.github/workflows/collect-reports.yml`, cron `30 2 * * *` = **11:30 KST**.

기존 셋(전망 12:00 · 고용동향 12:10 · 재배포 12:20)보다 앞에 둔다 — 게시판이 20개 가까이고
요청 사이에 지연을 두므로 이 도메인이 가장 오래 돈다. **이 숫자는 발표 시각이 아니라 GitHub
예약이 5~8시간 늦게 시작한다는 관측값에 매여 있다**(2026-09-02 측정: 표본 8개, 최소 5.3h /
중앙 5.6h / 최대 7.9h). 지연 폭이 달라지면 다시 재서 옮긴다. 기존 워크플로 주석의 이유가
그대로 적용된다.

푸시 전 `git pull --rebase origin main`을 넣는다. 없으면 같은 날 다른 수집과 부딪혀
`failed to push some refs`로 그날 수집을 통째로 버린다(2026-08-31 전례).

### 7-1. 실패 판정은 게시판 단위로 한다

`check_run.py`가 실패로 잡는 것은 **게시판 단위로 둘뿐**이다.

| 실패 | 뜻 |
|---|---|
| (a) 요청 자체가 실패 | 타임아웃 · 200이 아닌 응답 · 연결 거부 |
| (b) 목록이 200인데 파싱 항목 0건 | **마크업이 바뀌었다는 신호** |

**게시판에 신규 글이 없는 것은 통과다.** 고용영향평가브리프·패널브리프처럼 몇 달씩 아무것도
안 올라오는 게 정상인 게시판이 있다. "기관 하나라도 0건이면 실패"로 잡으면 이 게시판들이
조용한 달마다 빨간 알람이 뜨고, 알람이 일상이 되면 진짜 고장을 아무도 안 본다.

(b)가 이 판정의 핵심이다. 신규 글 0건과 파싱 0건은 화면상 같아 보이지만 원인이 정반대다 —
전자는 게시판이 조용한 것이고 후자는 파서가 눈이 먼 것이다. **목록 페이지가 200을 주면서
항목이 하나도 안 잡히는 상황은 정상일 수 없다.** 그래서 이것만 실패로 올린다.

미등록 게시판 경고(§5-1)와 초록 결측률(§7-2)은 실패가 아니라 `last_run.json`에 남긴다.
외부 장애는 `KNOWN_DOWN`에 기한과 함께 적어 통과시키되, **기한이 지나거나 그 게시판이
되살아나면 일부러 실패시킨다.**

### 7-2. 초록 결측률을 매 회차 기록한다

`build.py`가 **기관별·시리즈별 초록 결측 건수와 비율**을 재서 `last_run.json`에 남긴다.

```json
"abstract_missing": {
  "kli":  { "연구보고서": {"total": 137, "missing": 4,  "rate": 0.03} },
  "kiet": { "월간 KIET 산업경제": {"total": 412, "missing": 88, "rate": 0.21} }
}
```

두 가지가 이 숫자에 걸려 있다. 하나는 **C안(NKIS 초록 보강) 전환 판단**이다(§9-3) — 지금은
결측률을 모르는 채로 보류한 것이라, 숫자가 없으면 영영 판단할 수 없다. 다른 하나는 검색
품질이다. 초록이 없으면 그 보고서는 §4-3의 폴백에 따라 목차나 제목으로만 걸리므로,
결측률이 높은 시리즈는 검색에서 조용히 불리해진다. 그게 얼마나 되는지가 보여야 한다.

추세로 봐야 하는 값이라 회차마다 덮어쓴다 — 급변하면 그때가 사이트 개편 신호다.

## 8. 테스트

**테스트는 네트워크에 나가지 않는다.** 2026-09-10에 받아둔 실제 페이지를
`tests/fixtures/`에 고정해 파서를 검증한다. 픽스처가 각 사이트의 마크업과 인코딩을 붙들어
두므로, 사이트가 개편되면 실서비스가 아니라 **수집이 먼저 시끄럽게 실패한다.**

`collect.main`에 수집기 주입 지점을 두고, 주입하면 네트워크 호출이 기본으로 꺼진다.
그 사실 자체를 테스트가 지킨다 — 기존 도메인과 같은 규약이다.

덮어야 할 것:

- 파서 4개 — 목록 파싱, 상세 파싱, 페이지 넘김, 빈 목록
- **부분 날짜 정규화** — `2025-12`·`2025`가 월말·연말로 채워지고 `date_precision`이 맞게 붙는지
- `store.upsert` — 값이 같으면 안 덮는지
- `boards` — 미등록 게시판이 경고로 나오고 자동 수록되지 **않는지**
- **`build`** — raw는 안 건드리고 `data/`만 다시 쓰는지. `keywords.json`만 바꿔 다시 돌리면
  **재수집 없이** `employment`가 뒤집히는지(§5-3의 존재 이유가 이 테스트다)
- `keywords` — 매칭은 전 기관, 판정은 `filter` 켜진 게시판만이라는 분리가 실제로 갈라지는지
- `check_run` — **요청 실패와 파싱 0건만 실패이고 신규 글 0건은 통과인지**(§7-1),
  `KNOWN_DOWN` 만료 시 실패
- `last_run` — 초록 결측률이 기관·시리즈별로 기록되는지(§7-2)
- 웹(`tests/web/`) — 검색의 공백 무시 부분일치, 폴백 순서(초록→목차→제목),
  타임라인 접기가 `collapse` 게시판에만 걸리는지, 필터가 타임라인·결과 양쪽에 걸리는지

## 10. 규모 추정과 위험

2021년 이후 위 게시판이면 **필터 후 1,500~2,500건**으로 본다. 첫 수집이 끝나면 실측으로
바꾼다.

| 위험 | 어떻게 받치나 |
|---|---|
| 사이트 개편으로 파서가 깨짐 | 파서 격리 + 픽스처 + **파싱 0건 실패 판정**(§7-1) |
| 게시판이 새로 생겨 조용히 누락 | 미등록 게시판 경고(§5-1) |
| 조용한 게시판이 알람을 울려 알람이 무뎌짐 | 신규 글 0건은 통과(§7-1) |
| 키워드 필터 오검출·누락 | `matched`를 레코드에 남기고(§4-2), **재수집 없이 빌드만 다시 돌려 고침**(§5-3) |
| 부분 날짜를 화면이 단정 | `date_precision`을 따라 표기(§4-2, §6-1) |
| 한 기관·한 시리즈가 타임라인을 뒤덮음 | 월·기관·시리즈 단위 접기(§6-1) |

| 게시판 과다 요청 | 요청 간 지연 + 회차당 상한 + 며칠 백필(§5-4) |
