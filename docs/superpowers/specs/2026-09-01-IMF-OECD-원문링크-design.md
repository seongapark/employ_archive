# IMF·OECD 원문 링크 교체 설계

작성일: 2026-09-01
상위 문서: `고용전망_아카이브_기획서.md` 3.2(스키마 — `source_url`, `landing_url`)
후속 작업: `2026-09-01-전망근거-수집-design.md` — **이 작업이 먼저다**(7장)

---

## 1. 문제

IMF·OECD 레코드의 "원문 보기"를 누르면 보고서가 아니라 JSON 이 뜬다.

```
IMF   원문 -> api.imf.org/external/sdmx/3.0/data/dataflow/IMF.RES/WEO_2025_OCT_VINTAGE/1.0.0/KOR.LUR.A
      게시 -> imf.org/external/datamapper/profile/KOR                        (차트 페이지)

OECD  원문 -> sdmx.oecd.org/public/rest/data/OECD.ECO.MAD,DSD_EO_118@DF_EO_118,/KOR.GDPV_ANNPCT+...
      게시 -> oecd.org/en/topics/economic-outlook.html                       (안내 페이지)
```

이 아카이브의 값은 **수치를 인용할 수 있다는 것**이다. 인용하려고 원문을 열었는데
기계용 응답이 뜨면 그 약속이 그 자리에서 무너진다. 56건(IMF 12 + OECD 44)이
이 상태다.

수치 자체는 문제가 없다. API 수집은 정확하고 안정적이며 `confidence: verified`
가 붙어 있다. **바꾸는 것은 링크가 가리키는 곳뿐이다.**

---

## 2. 저장소 안에 이미 있는 답

`oecd_interim` 은 같은 기관의 자료를 다루면서 실제 보고서 PDF 를 가리킨다.

```python
EDITIONS: dict[str, tuple[date, str]] = {
    "March 2026": (date(2026, 3, 26),
                   f"{BASE}/content/dam/oecd/en/publications/reports/"
                   "2026/03/oecd-economic-outlook-interim-report-march-2026_254a8d56/d4623013-en.pdf"),
}
```

회차 라벨 → (발표일, 보고서 URL). 새로 만들 구조가 아니라 **이미 도는 방식을
나머지 둘에 넓히는 일**이다.

지금 세 수집기가 가진 것을 비교하면 빠진 칸이 분명하다.

| 수집기 | 회차 표가 담은 것 | 보고서 URL |
|---|---|---|
| `oecd_interim` | 발표일 + **보고서 URL** | 있음 |
| `oecd` | 발표일만 | **없음** |
| `imf` | API 흐름 ID + 제목 + 발표일 | **없음** |

---

## 3. 어디를 가리켜야 하나

### 3.0 불변 규칙 — 기계용 주소는 저장하지 않는다

**`source_url`·`landing_url` 에 API 응답 주소를 넣지 않는다.** 예외 없다.

JSON 은 사람에게 아무 의미가 없다. "원문 보기"는 사람이 수치를 눈으로 확인하려고
누르는 버튼이므로, 눌러서 나오는 것은 반드시 **보고서 자체이거나 그 보고서를
읽을 수 있는 페이지**여야 한다.

이 규칙은 소급뿐 아니라 앞으로의 모든 수집에 적용된다. 회차의 보고서 주소를
구하지 못하면 **기계용 주소로 대신 채우지 않고 그 회차 수집을 실패시킨다**(4장).
링크가 빈 레코드보다 나쁜 것이 잘못된 곳으로 데려가는 링크이고, 그보다 나쁜 것이
사람이 읽을 수 없는 것으로 데려가는 링크다.

테스트가 이 규칙을 지킨다 — 저장되는 모든 레코드의 두 URL 이 `api.`·`sdmx.`
같은 기계용 호스트나 데이터 응답 경로를 가리키지 않는지 확인한다.

### 3.1 어느 주소가 맞나

`source_url` 은 **그 회차 보고서의 고정 주소**여야 한다. 기관의 상설 안내
페이지(`oecd.org/en/topics/economic-outlook.html`)는 안 된다 — 회차가 바뀌면
다른 것을 가리키게 되어, 2025년 전망 레코드가 2027년 보고서로 이어진다.

`landing_url` 은 기존 정의대로 기관 자료실 게시글 URL 이다. IMF·OECD 는 회차
게시글이 곧 보고서 페이지이므로 둘이 같아질 수 있다. 같아도 무방하다 —
`source_page` 를 못 주는 API 수집이라 원문 쪽번호 대신 회차 페이지를 준다.

### 3.2 IMF — 목록을 긁는다

`imf.org/en/publications/weo` 가 회차 목록이고, 각 회차가 고정 주소를 가진다.

```
imf.org/en/publications/weo/issues/2026/07/08/world-economic-outlook-update-july-2026
                                   └ /issues/<연>/<월>/<일>/<슬러그>
```

주소에 발표일이 들어 있어 `VINTAGES` 의 발표일과 맞출 수 있다. 목록을 읽어
회차를 찾으므로 **새 회차가 나오면 표를 손대지 않아도 따라간다.**

조사 중 확인한 것: 목록에 **2026년 7월 WEO Update** 가 있는데 아카이브의 최신
IMF 회차는 2026년 4월이다. 회차를 놓치고 있을 수 있다 — 이 작업에서 함께 본다.

### 3.3 OECD 본편 — 회차 표에 URL 을 더한다

OECD 본편의 보고서 주소는 규칙적으로 만들어지지 않는다. `oecd_interim` 의 URL
을 보면 `..._254a8d56/d4623013-en.pdf` 처럼 해시가 붙어 있어 회차 번호로 조립할
수 없다.

그래서 `oecd_interim` 과 같이 **회차마다 사람이 확인해 적어 넣는다.**
`oecd.EDITIONS` 를 `{번호: 발표일}` 에서 `{번호: (발표일, 보고서 URL)}` 로 넓힌다.

이것이 손이 가는 방식임을 인정한다. 하지만 OECD 본편은 연 2회(6월·12월)뿐이라
한 해에 두 번 적으면 되고, 지어낸 URL 로 독자를 엉뚱한 문서에 보내는 것보다
낫다.

## 4. 모르는 회차가 오면 실패시킨다

`oecd.py` 는 이미 이 규칙을 쓴다 — 모르는 회차가 오면 조용히 틀린 날짜를 쓰지
않고 실패한다. **URL 도 같은 규칙을 따른다.**

새 회차가 나왔는데 URL 을 아직 적지 않았으면:

- 옛 회차의 URL 을 재활용하지 않는다 — 독자가 다른 회차 보고서를 원문으로
  믿게 된다
- 기관 안내 페이지로 떨어뜨리지 않는다 — 같은 이유로 시간이 지나면 어긋난다
- **수집을 실패시킨다.** `last_run.json` 에 남고 매일 실행이 빨개져, 사람이
  URL 을 적어 넣을 때까지 눈에 띈다

IMF 는 목록을 긁으므로 이 상황이 잘 생기지 않지만, 목록에서 그 회차를 못 찾으면
같게 처리한다.

## 5. 기존 56건 소급 — 별도 경로가 필요하다

**`store.merge` 는 링크 변경을 반영하지 않는다.**

```python
if stored.value == cand.value:
    result.skipped.append(cand.id)
    continue          # 값이 같으면 여기서 끝. 메타데이터는 보지 않는다
```

이 규칙 자체는 옳다 — 값이 같으면 같은 관측이고, 수집기가 돌 때마다 메타데이터가
흔들리면 안 된다. 그래서 백필을 다시 돌려도 기존 레코드의 링크는 JSON 을 계속
가리킨다.

소급은 **일회성 마이그레이션**으로 한다. `store.merge` 규칙은 건드리지 않는다.

- `domains/forecast/pipeline/` 아래 한 번 돌리는 스크립트를 둔다
- 기존 레코드를 읽어 `(org, published_at)` 으로 회차를 찾고, 그 회차의 보고서
  URL 로 `source_url`·`landing_url` 만 바꾼다
- **`value`·`id`·`revision`·`prev_value` 는 한 글자도 건드리지 않는다**
- 회차 URL 을 못 찾은 레코드는 그대로 두고 몇 건인지 보고한다 — 조용히 넘기지
  않는다

실행 전후로 수치가 바뀌지 않았음을 스크립트가 스스로 확인하고, 어긋나면 저장하지
않는다.

## 6. 대상 범위

| 기관 | 하는 일 |
|---|---|
| IMF | 회차 목록을 긁어 보고서 URL 을 얻는다. 놓친 회차가 있는지 함께 확인 |
| OECD 본편 | `EDITIONS` 에 보고서 URL 칸을 더한다 |
| OECD Interim | **손대지 않는다** — 이미 보고서를 가리킨다 |
| 국내 5곳 | **손대지 않는다** — 이미 PDF 직링크를 가리킨다 |

## 7. 후속 작업과의 관계

이 작업이 `2026-09-01-전망근거-수집-design.md` 보다 **먼저**다.

근거 수집은 보고서 본문에서 문장을 뽑는다. IMF·OECD 는 지금 보고서를 받아오지
않고 API 만 쓰므로, 본문에 닿을 길이 없다. 이 작업이 회차별 보고서 주소를
확보하면 근거 수집이 그 주소에서 본문을 읽을 수 있다.

즉 이 작업은 링크를 고치는 일이자, 근거 수집이 딛고 설 발판이다.

## 8. 실패 처리

| 상황 | 처리 |
|---|---|
| 회차 목록을 못 받았다 (IMF) | 실패 |
| 목록에 그 회차가 없다 (IMF) | 실패 — 옛 URL 재활용 금지(4장) |
| `EDITIONS` 에 URL 이 없다 (OECD) | 실패 — 사람이 적어야 한다는 신호 |
| 마이그레이션이 회차를 못 찾았다 | 그 레코드는 그대로 두고 건수를 보고 |

---

## 9. 테스트

- **저장되는 어떤 레코드도 `source_url`·`landing_url` 이 기계용 주소가 아니다**(3.0)
- 목록 HTML 픽스처에서 IMF 회차 URL 을 발표일로 맞춰 찾는다
- 목록에 없는 회차를 요구하면 `ValueError` 를 낸다 (옛 URL 로 떨어지지 않는다)
- `EDITIONS` 에 URL 이 없는 OECD 회차는 실패한다
- 마이그레이션이 링크만 바꾸고 `value`·`id`·`revision` 을 그대로 둔다
- 마이그레이션이 회차를 못 찾은 레코드를 건드리지 않는다
- 기존 픽스처의 수치 파싱 결과가 한 건도 바뀌지 않는다

네트워크를 타지 않는다. 목록 HTML 은 픽스처로 고정한다.

---

## 10. 하지 않는 것

- **수치 수집 방식 변경.** API 는 정확하고 안정적이다. `confidence: verified`
  도 그대로 둔다
- **보고서 PDF 파싱.** 이 작업은 주소만 확보한다. 본문을 읽는 것은 후속 작업이다
- **`store.merge` 규칙 변경.** 값이 같으면 건너뛰는 것은 옳은 규칙이고, 링크
  소급은 일회성 마이그레이션으로 푼다(5장)
- **OECD 본편 URL 자동 생성.** 해시가 붙어 조립할 수 없다. 지어내느니 적는다(3.3)
