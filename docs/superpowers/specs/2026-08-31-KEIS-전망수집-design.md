작성일: 2026-08-31

## 1. 범위

`domains/forecast` 에 **한국고용정보원(KEIS) 수집기**를 더한다. 대상은
고용동향브리프의 「연도 고용 전망」 표 하나다.

`orgs.json` 에 KEIS 는 이미 `track: "B"`, `method: "llm"` 로 등록되어 있으나
수집기가 없다. 이 문서가 그 자리를 채우면서, **추출 방식을 LLM 에서 OCR 로
바꾼다**. 근거는 2장이다.

앱(`domains/forecast/app/`)은 손대지 않는다. KEIS 레코드는 기존 화면이 이미
처리하는 `ForecastRecord` 형태로 들어간다.

### 1.1 발간 주기

원칙은 **연 1회**다. 연말호(12월 말)가 이듬해 연간 전망을 싣는다.

2026년은 예외로 **하반기 전망호가 추가 발간**됐다(2026년 제5호, 2026-08-03).
회차 번호나 발간월로 전망호를 특정할 수 없다는 뜻이므로, 수집기는 **모든
신규 호를 열어보고 전망표가 있는지 확인**한다. 발간 일정을 상수로 박지 않는다.

## 2. 기획서 9.4 개정 — LLM 추출에서 OCR 추출로

기획서 9.4 는 B트랙을 "본문 텍스트 키워드 스크리닝 → Claude API 로 해당 부분
텍스트 전달"로 설계했다. **이 전제가 깨졌다.**

고용동향브리프 PDF 에는 **텍스트 레이어가 없다.** InDesign 이 글자를 전부
아웃라인(벡터 패스)으로 변환해 내보낸다. 확인한 근거:

| 검사 | 2026년 제5호 | 2025년 제10호 |
|---|---|---|
| `pdfplumber.extract_text()` | 전 쪽 빈 문자열 | 전 쪽 빈 문자열 |
| 콘텐츠 스트림의 `BT`/`Tj` 연산자 | 0개 | 0개 |
| 한 쪽의 곡선(`c`) 연산자 | 13,496개 | — |
| `chars` / `curve` 객체 | 0 / 약 2,000 | 0 / 약 2,000 |

텍스트가 없으므로 키워드 스크리닝도 LLM 전달도 불가능하다. 쪽을 이미지로
렌더링해 읽는 수밖에 없고, 표 서식이 회차마다 거의 같으므로 **OCR + 규칙
파싱**을 쓴다. 비전 LLM 은 쓰지 않는다 — API 키를 CI 시크릿으로 넣어야 하고,
호출 비용이 붙으며, 아래 4장이 보이듯 규칙 파싱으로 충분하다.

기획서 9.4 와 `orgs.json` 의 `method` 를 이에 맞춰 고친다(`"llm"` → `"ocr"`).

## 3. 전처리 — `pipeline/ocr.py` (신규)

**라벨이 보라 배경 위 흰 글씨**여서 tesseract 가 행 이름을 통째로 버린다.
숫자는 흰 바탕이라 잘 읽히므로, 값만 있고 그 값이 무슨 지표인지 모르는
쓸모없는 결과가 나온다. 세 가지를 실제로 돌려보고 마지막 것만 통했다.

| 시도 | 결과 |
|---|---|
| 원본 그대로 400dpi OCR | 숫자 전부 정확, **행 이름 전멸** |
| 라벨 열만 잘라 통째로 반전 | 셀 사이 흰 여백이 검은 띠가 되어 레이아웃 분석이 깨짐 |
| 배경만 반전(밝기 유지) | 회색 셀을 tesseract 전역 이진화가 글자로 오인 — 여전히 전멸 |
| **마스크 안을 강제 이진화** | **라벨·숫자 전부 정확** |

### 3.1 절차

```
1. 채도 = max(RGB) − min(RGB)
2. 후보 = (채도 > 25) and (밝기 < 200)          # 유채색 어두운 픽셀
3. 열기(침식 15 → 팽창 15)                       # 얇은 글자 획을 지워 '면'만 남김
4. 닫기(팽창 45 → 침식 45)                       # 흰 글자가 뚫은 구멍을 메워 셀 전체를 덮음
5. 마스크 안: 밝기 > 170 이면 0, 아니면 255       # 흰 바탕·검은 글자로 강제 이진화
   마스크 밖: 원본 그대로
```

3의 **열기가 필수**다. 채도 조건만 쓰면 헤더의 보라색 글자(`2023년`)까지 마스크에
들어가 반전돼 버린다. 열기가 얇은 획을 지우므로 솔리드한 셀 배경만 남는다.

5에서 **밝기를 보존하지 않고 이진화하는 것도 필수**다. 단순 반전은 보라
배경(밝기 약 90)을 회색(165)으로 만드는데, tesseract 의 전역 Otsu 임계값이
그 회색을 글자로 잡아 셀 전체를 검은 덩어리로 만든다.

### 3.2 형태학은 적분영상으로

PIL 의 `MaxFilter(45)`/`MinFilter(45)` 는 3308×4678 이미지에서 **한 쪽에 수 분**이
걸려 실측 중 타임아웃 났다(랭크 필터가 픽셀당 45² 비교).

적분영상(2D 누적합)으로 박스합을 구해 침식·팽창을 상수시간에 한다.

```
boxsum(mask, k)  = 적분영상 4점 차분
erode(mask, k)   = boxsum == k*k
dilate(mask, k)  = boxsum > 0
```

같은 결과에 **3.0초**다. 의존성은 numpy 하나만 늘고 scipy 는 필요 없다.

마스크를 축소해 형태학을 돌리는 방법(1/8 축소)도 재봤으나 0.96초로 더 빠른
대신 `생산가능인구` 라벨이 다시 사라지고 `29,203` 이 `29.203` 으로 깨져
버렸다. **속도보다 정확도를 택한다** — 이 수집기는 연 1~2회만 실제로 일한다.

### 3.3 인터페이스

```python
def flatten(img: Image) -> Image        # 3.1 의 전처리
def page_texts(pdf_bytes, pages=None, dpi=400, preprocess=True) -> list[str]
```

`page_texts` 는 `pipeline/pdf.py` 의 동명 함수와 같은 자리를 차지한다 —
호출부에서 텍스트 레이어 PDF 와 이미지 PDF 를 같은 모양으로 다룬다.

## 4. 수집기 — `collectors/keis.py` (신규)

`kli.py` 의 골격(목록 → 회차 → 표 페이지 → 파싱)을 그대로 따른다.

### 4.1 목록

```
LIST_URL = https://www.keis.or.kr/keis/ko/proj/118/pblc/list.do
```

목록 HTML 의 `<tr>` 하나가 회차 하나다. 세 가지를 뽑는다.

| 뽑는 것 | 위치 |
|---|---|
| 제목 | `cell-subject` 의 `<a onclick="goDetail('categoryIdx=126&pubIdx=11349')">고용동향브리프 2026년 제5호</a>` |
| 게시일 | `cell-date` 의 `<span>2026.08.03</span>` |
| PDF 직링크 | `cell-link` 의 `/keis/ko/cmmn/download.do?dn=…&sn=…&fsn=…&ty=P` |

`goDetail` 은 `./detail.do?<params>` 로 이동한다. 회차마다 고유한 상세 페이지가
있다는 뜻이므로 그쪽을 landing_url 로 쓴다(200 응답 확인).

```
landing_url = https://www.keis.or.kr/keis/ko/proj/118/pblc/detail.do?categoryIdx=126&pubIdx=<pubIdx>
source_url  = https://www.keis.or.kr/keis/ko/cmmn/download.do?dn=…&path=pblc&fn=…&sn=…&fsn=…&ty=P
```

목록 URL 을 landing_url 로 쓰면 회차가 밀려날 때 링크가 다른 호를 가리키게 된다.

목록 맨 위의 대표 게시물 블록은 1번 행과 **같은 회차를 한 번 더** 싣는다.
`<tr>` 단위로만 읽어 중복을 피한다.

### 4.2 두 단계 OCR

전 쪽을 400dpi + 전처리로 돌리면 18쪽에 몇 분이 걸린다. 두 단계로 나눈다.

| 단계 | 해상도 | 전처리 | 대상 | 실측 |
|---|---|---|---|---|
| 1차 스크리닝 | 150dpi | 없음 | 전 쪽 | 18쪽 **14.6초** |
| 2차 정밀 | 400dpi | 있음 | "전망"이 나온 쪽만 | 쪽당 **4.5초** |

1차는 라벨을 못 읽어도 상관없다 — "전망" 두 글자만 찾으면 된다. 2025년
제10호에서 18쪽 중 7쪽이 후보로 남았고, 그중 표가 실린 쪽은 1쪽(10쪽)이었다.

표 페이지 판정은 `pdf.find_summary_table` 과 같은 원칙을 쓴다. 캡션 문자열로
찾지 않는다 — OCR 이 `표1`을 `WED`, `표5`를 `표5`로 들쭉날쭉 읽는다. 대신
**실제로 파싱해 보고 필요한 지표가 다 나오는 쪽**을 고른다.

이 원칙이 특히 중요한 이유가 있다. 표 바로 앞 쪽(제10호 9쪽)은 장 도입부
서술이라 같은 수치를 문장으로 싣는다 — "취업자 수는 전년 대비 약 16만 2천 명
증가, 고용률은 63.0%, 실업률은 2.7%". 캡션이나 키워드로 쪽을 고르면 이 쪽이
먼저 잡힌다. 지표 3개가 표 형태로 다 나오는지 보면 자연히 걸러진다.

### 4.4 왜 `pdf.parse_summary_table` 을 못 쓰나

셋이 다르다.

| 차이 | 기존 파서 | KEIS |
|---|---|---|
| 연도 토큰 | `2026`, `2026p` | `2026년`, `2026년p` (OCR 상 `2026년6`·`2026년0`) |
| `연간` 토큰 | 헤더에 명시됨 | **없음** — 연도열 자체가 연간이고 반기는 하위 열 |
| 행 이름 | 표 전체에서 유일 | `(증감)` 이 생산가능인구·경제활동인구·취업자 아래 **3번** 나옴 |

`_columns` 는 기간 토큰을 연도 블록으로 묶는데, KEIS 헤더에는 `연간` 이 없어
`years=[2023,2024,2025,2026]`, `periods=['h1','h2']` 가 되어 블록 수 불일치로
실패한다. KEIS 전용 열 조립을 쓴다.

```
열 = [(연도, "annual") for 연도 in 연도목록]
     + [(연도목록[-1], "h1"), (연도목록[-1], "h2")]   # 반기 행이 있을 때만
```

행 이름은 **직전 대분류를 기억하는 상태 있는 매칭**으로 푼다.

```
대분류 = {생산가능인구, 경제활동인구, 취업자, 비경제활동인구}
(취업자, "(증감)")  → emp_change
실업률              → unemp_rate
고용률              → emp_rate
```

숫자 토큰도 `(146)`·`(-0.8)` 처럼 괄호에 싸여 있어 전용 토크나이저가 필요하다
(기존 `_NUMBER` 는 괄호를 못 벗긴다). 음수 부호는 OCR 이 하이픈으로 주지만
`−`(U+2212)도 함께 받는다.

### 4.5 지표와 단위

다른 기관 수집기가 이미 모으고 있는 **세 개만** 쓴다. `kli.py` 와 정확히 같은
집합이다.

| 표의 행 | 지표코드 | 단위 변환 |
|---|---|---|
| 취업자 (증감) | `emp_change` | 천명 → 만명 (× 0.1) |
| 고용률 | `emp_rate` | 없음 |
| 실업률 | `unemp_rate` | 없음 |

`취업자` 의 **수준**(28,943천명)이 아니라 **증감**(162천명 → 16.2만명)을 쓴다.
아카이브의 `emp_change` 정의이자 `kli.py` 와 같은 선택이다.

표에는 생산가능인구·경제활동인구·경제활동참가율·비경제활동인구와 연령대별
증감도 실려 있으나 수집하지 않는다. `indicators.json` 의 `labor_force`
(경제활동참가율)는 정의만 있고 **현재 어느 수집기도 채우지 않는다** —
KEIS 만 채우면 출처 비교 화면에 홀로 선 계열이 생긴다. 연령대별은 지표코드
자체가 없다.

## 5. 어느 열을 저장하나 — 다른 수집기와 같은 규칙

보고서에 실린 값은 **공표일 기준 전망치로 모두 넣는다.** KEIS 전용 규칙을
두지 않는다.

`report.records_from_values` 의 기존 필터를 그대로 쓴다 — **발표연도보다
앞선 해는 실적이므로 버리고, 나머지는 남긴다.**

| 회차 | 남는 열 |
|---|---|
| 제5호 (2026-08-03) | 2026 `annual`, 2026 `h1`, 2026 `h2` |
| 제10호 (2025-12-31) | 2025 `annual`, 2026 `annual` |

제5호의 `상반기` 열은 발표 시점에 이미 지난 기간이지만 **버리지 않는다.**
한국은행·KDI 도 8월 보고서에 그 해 상반기 수치를 실어 발표하고, 아카이브는
그것을 공표일 기준 전망치로 담고 있다. KEIS 만 다른 기준을 쓰면 출처 비교가
어긋난다.

이 결정으로 수집기에 별도 필터가 필요 없어진다 — `kli.py` 와 같은 모양이다.

### 5.1 신뢰도

기획서 9.4 대로 `confidence` 는 **항상 `extracted`**(노랑 배지)다. 사람이 원문
쪽을 대조한 뒤에만 `reviewed`(파랑)로 올린다. OCR 은 규칙 파싱보다 실수할 여지가
크므로 이 원칙을 완화하지 않는다.

`source_page` 에 전망표가 실린 쪽번호를 넣어, 화면의 `원문 보기 (p.19)` 링크로
바로 대조할 수 있게 한다.

## 6. 수집 범위

- **매일 실행**: 목록 맨 앞 호를 보고, 이미 가진 회차면 아무것도 하지 않는다.
  새 회차면 PDF 를 받아 4.2 의 두 단계 OCR 을 돌린다. 전망표가 없으면
  (대부분의 호가 그렇다) 빈 결과를 정상으로 돌려준다 — **실패가 아니다.**
- **1회 백필**: `backfill.py` 의 `SOURCES` 에 KEIS 를 등록하는 것으로 끝난다.
  기존 `SINCE`(2024-11-01)가 "최근 2년" 범위를 그대로 만들어 주고, 회차별
  예외 처리·중복 제거·수정폭 재계산도 `run()` 이 이미 한다. KEIS 전용 백필
  함수를 새로 만들지 않는다. 2025년 제10호와 2026년 제5호가 들어와, 2026년
  연간 전망의 수정 이력(16.2만명 → 14.6만명)이 화면에 보이게 된다.

목록 전체(153건, 2012년~)는 백필하지 않는다. 옛 편집 서식이 달라 파서가 깨질
가능성이 크고, 얻는 것에 비해 확인 비용이 크다.

## 7. 실패 처리

기획서 9.3 을 따른다 — **값을 못 찾으면 명시적으로 실패**시키고, 조용히
넘기지 않는다. 다만 두 경우를 구분한다.

| 상황 | 처리 |
|---|---|
| 새 호에 전망표가 없다 | 정상. `fetched: 0` 으로 기록 |
| 새 호에 전망표는 있는데 파싱이 깨졌다 | 실패. `last_run.json` 의 `errors` 에 한 줄 |
| 목록 페이지 접근 실패 | 실패 |

두 번째와 첫 번째를 가르는 선을 분명히 해 둔다. "지표 3개가 다 안 나왔다"를
그냥 "전망표 없음"으로 처리하면, 서식이 바뀌어 파서가 깨진 날이 조용한 정상
실행으로 묻힌다. 그래서 **표의 존재와 표의 완결성을 따로 본다.**

| 후보 쪽에서 본 것 | 판정 |
|---|---|
| 연도 토큰 3개 이상인 헤더를 가진 표가 아예 없다 | 전망표 없는 호 — **정상** |
| 그런 표가 있는데 지표 3개 중 일부만 읽힌다 | 서식 변경 — **실패** |
| 그런 표가 있고 지표 3개가 다 읽힌다 | 수집 |

절반만 읽은 표를 저장하는 쪽이 훨씬 나쁘다.

## 8. 테스트

**픽스처는 OCR 결과 `.txt` 로 고정한다.** ubuntu-latest 의 tesseract 5.3 과
로컬 5.5 가 다른 글자를 낼 수 있어, 테스트가 OCR 을 돌리면 CI 가 무작위로
깨진다. 기존 수집기 픽스처 관례와도 같다.

| 파일 | 내용 |
|---|---|
| `fixtures/keis_list.html` | 목록 페이지 발췌 |
| `fixtures/keis_2025-12_forecast.txt` | 제10호 표 페이지 OCR 결과(연간 4열) |
| `fixtures/keis_2026-08_forecast.txt` | 제5호 표 페이지 OCR 결과(연간 4열 + 반기 2열) |
| `fixtures/keis_no_forecast.txt` | 전망표가 없는 쪽 |
| (없음) | 전처리는 테스트 안에서 만든 합성 이미지로 검증한다 — 이진 픽스처를 저장소에 넣지 않는다 |

`test_keis.py`

- 목록 파싱이 제목·게시일·PDF 직링크를 준다
- 연간 4열 표에서 2026 전망 3개 지표를 읽는다 (`emp_change` 16.2, `emp_rate` 63.0, `unemp_rate` 2.7)
- 반기 2열 표에서 `annual` 과 `h2` 를 함께 읽는다 (14.6 / 18.5)
- 반기 열이 있는 표에서 2026 `h1` 도 함께 저장한다 (5장 — 공표일 기준 전망치)
- 제10호에서 2025 `annual` 은 남고 2024 이전은 버려진다 (발표연도 기준)
- 취업자 증감이 천명에서 만명으로 환산된다
- 헤더 있는 표에서 지표가 일부만 읽히면 `ValueError`
- 전망표 없는 호는 빈 리스트를 준다 (예외가 아니다)

`test_ocr.py`

- 합성 이미지에서 어두운 유채색 셀만 마스크에 들어간다
- 흰 바탕의 검은 글자는 마스크 밖이라 그대로 남는다
- 유채색 **글자**(면이 아닌)는 열기에 지워져 마스크에 들어가지 않는다
- `erode`/`dilate` 가 PIL 랭크 필터와 같은 결과를 낸다 (작은 배열로 대조)

## 9. 배포

`requirements.txt` 추가

```
pypdfium2>=5.10      # PDF 쪽 렌더링
pytesseract>=0.3.13  # tesseract 래퍼
pillow>=10.4
numpy>=1.26
```

(로컬 확인 버전: pypdfium2 5.10.1, pytesseract 0.3.13, pillow 12.2.0, numpy 2.4.6,
tesseract 5.5.0 + `kor.traineddata`)

`.github/workflows/collect-forecast.yml` 에 한 줄

```yaml
- run: sudo apt-get update && sudo apt-get install -y tesseract-ocr tesseract-ocr-kor
```

`collect.py` 의 `COLLECTORS` 에 `"keis": keis.collect` 를 더한다.

`orgs.json` 의 KEIS 행에서 `method` 를 `"llm"` → `"ocr"`,
`report` 를 `"고용리뷰 / 고용브리프"` → `"고용동향브리프"` 로 고친다(실제 수집
대상은 고용동향브리프 하나다).

`고용전망_아카이브_기획서.md` 9.4 를 2장 내용으로 개정하고, 10장 리스크 표의
"B트랙 LLM 추출 오류" 행을 "B트랙 OCR 추출 오류"로 바꾼다.

## 10. 하지 않는 것

- 앱 수정. 다른 세션이 UI 작업 중이고, KEIS 레코드는 기존 화면이 그대로 그린다.
- 비전 LLM 추출. 규칙 파싱으로 충분하다(3장·4장).
- 목록 전체 백필(6장).
- **본문 서술과의 교차검증.** 도입부 쪽이 같은 수치를 문장으로 실으므로
  대조할 수는 있다(4.2). 그러나 서술 OCR 이 표보다 훨씬 지저분하고
  (`약` → `OF`, `2,891만 5천 명` → `2,89 1만 5천 명`), 틀린 대조 때문에
  멀쩡한 수집이 실패하는 쪽이 더 나쁘다. `confidence: extracted` 와
  `source_page` 링크로 사람이 확인하는 경로가 이미 있다.
- `schedule.json` 에 KEIS 예정 추가. 발간 일정이 공지되지 않고 2026년처럼
  예외 호가 끼므로, 날짜를 적으면 틀린 예고가 된다.
