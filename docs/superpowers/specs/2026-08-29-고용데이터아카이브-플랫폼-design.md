# 고용데이터아카이브 플랫폼 설계

작성일: 2026-08-29
상태: 승인됨 (구현 대기)
선행 문서: `고용전망_아카이브_기획서.md`, `docs/superpowers/plans/2026-08-29-phase2-pwa.md`

---

## 1. 배경과 목적

현재 `고용전망아카이브`는 기관별 고용·거시 전망치를 모아 보여주는 단일 목적 앱이다.
Phase 1(수집 파이프라인: IMF·OECD)과 Phase 2(PWA 셸: 홈·기관·비교·타임라인)까지 구현돼 있다.

이를 **전망 / 고용동향 / 인력수급 / 경제동향** 네 영역을 담는 플랫폼으로 확장한다.

목적은 **업무용 원스톱 조회**다. 보고서를 쓸 때 필요한 숫자가 기관별로 흩어져 있어
매번 검색하는 문제를 없애는 것이 1순위이며, 출처와 원문 링크의 정확성이 신뢰의 근거다.

이 문서는 (a) 플랫폼 구조와 (b) 첫 확장 영역인 **고용동향**의 설계를 다룬다.
인력수급·경제동향은 같은 틀을 반복 적용하며, 각자 별도 스펙을 갖는다.

## 2. 핵심 결정: 도메인별 독립 앱

네 영역을 하나의 앱 셸에 통합하지 않고, **도메인마다 독립된 앱**으로 두고
허브에서 링크로 진입하는 구조를 택한다.

근거:

- **표현 방식이 근본적으로 다르다.** 전망은 `기관 × 발표회차 × 수정이력`, 고용동향은
  `3출처 × 월별 시계열`, 인력수급은 `직종·산업 단면`이다. 공통 화면 컴포넌트를 만들면
  셋 다 어중간해진다.
- **붙였다 뗐다가 쉬워야 한다.** 영역 하나를 중단하거나 추가할 때 다른 영역이 흔들리면 안 된다.
- 데이터 스키마를 억지로 통합하면 전망의 `published_at`/`revision` 같은 필수 필드와
  실적 시계열의 `period`/`status`가 한 모델에 섞여 양쪽 다 표현력을 잃는다.

### 2.1 실패 지점과 대응

이 구조의 유일한 실패 지점은 **디자인 드리프트**다. 앱을 나누면 CSS를 복사하게 되고,
시간이 지나면 앱마다 카드 모서리와 여백이 달라져 "따로 노는 네 개"가 된다.

대응: **공유 `core/`를 복사하지 않고 참조한다.** 각 앱은 자기 화면 로직만 갖고,
껍데기(토큰·기본 스타일·셸 유틸)는 배포 시 단일 경로에서 링크한다.
동기화 스크립트나 서브모듈 없이, 물리적으로 파일이 하나뿐이므로 드리프트가 발생할 수 없다.

## 3. 저장소 구조

저장소는 하나를 유지하되, 앱·데이터·수집기를 **도메인별 수직 슬라이스**로 묶는다.
떼어낼 때 세 군데를 뒤지지 않고 폴더 하나만 지우면 되도록 하기 위함이다.

```
고용데이터아카이브/                     # 기존 고용전망아카이브에서 이름 변경
  core/
    tokens.css                        # 색·간격·반경·타이포 (단일 원본)
    base.css                          # body·헤더·카드·배지·버튼·오프라인배너·고지문구
    shell.js                          # 홈 버튼, JSON 로더, 갱신일 표기, 출처 배지, 원문보기
  hub/
    index.html                        # 4버튼 런처
  domains/
    forecast/
      app/       index.html  js/  css/
      data/      forecasts.json  orgs.json  indicators.json  schedule.json  last_run.json
      pipeline/  collect.py  models.py  store.py  collectors/
      tests/
    employment/
      app/       index.html  js/  css/
      data/      series.json  sources.json  industries.json  last_run.json  manual/
      pipeline/  collect.py  models.py  store.py  collectors/
      tests/
  tools/
    build.py                          # _site 조립 (배포·로컬 공용)
    serve.py                          # 조립 후 로컬 서빙
  .github/workflows/
    collect-forecast.yml              # paths: domains/forecast/**
    collect-employment.yml            # paths: domains/employment/**
    pages.yml                         # 사이트 조립·배포
  docs/
```

폴더명 변경은 리팩터 실행 시점에 `git mv`로 내부 이동과 함께 한 번에 처리한다.
코드에는 폴더명·절대경로 의존이 없음을 확인했다(파이썬은 `Path(__file__)` 기준 상대경로,
웹은 `fetch('./data/…')`, CI는 저장소 루트 기준, git 리모트 미설정).
끊기는 것은 Claude Code 세션 이력 키와 신뢰 대화상자 승인뿐이며 실질 손실은 없다.

## 4. 배포와 로컬 개발

`tools/build.py`가 `_site/`를 조립한다. 배포(`pages.yml`)와 로컬(`serve.py`)이
**같은 조립 함수**를 쓰므로 로컬과 배포의 경로가 일치한다.

| 원본 | 배포 경로 |
|---|---|
| `hub/*` | `/` |
| `core/*` | `/core/` |
| `domains/<d>/app/*` | `/<d>/` |
| `domains/<d>/data/*` | `/<d>/data/` |

각 앱은 `<link rel="stylesheet" href="../core/tokens.css">` 로 core를 참조한다.
배포본에서 `/employment/` 기준 `../core/`는 `/core/`로 해석된다.

이 구조가 서면 현재 `app.js`의 `'./'` / `'../'` 경로 폴백 해킹은 제거한다.
로컬에서도 배포와 동일한 경로가 성립하므로 폴백이 불필요해진다.

수집 워크플로는 도메인별로 분리한다. 현재는 수집기 하나가 실패하면 잡 전체가 실패하는데,
분리하면 고용동향 수집기가 깨져도 전망 수집은 정상 동작한다.

## 5. core의 경계

기준: **도메인이 무엇을 다루는지 몰라도 되는 것만 core에 둔다.** 애매하면 넣지 않는다.
core가 커지면 도메인 분리의 이점이 사라진다.

**core에 넣는 것**

- `tokens.css` — 현재 `web/css/styles.css`의 `:root` 및 다크모드 블록이 그대로 이사
- `base.css` — body·헤더·카드·배지·버튼·오프라인배너·비공식 고지 문구
- `shell.js` — 허브 복귀 버튼, JSON 로더, 갱신일 표기, 출처 배지, **원문보기 링크 컴포넌트**

원문보기는 전망(`source_url`/`landing_url`)과 고용동향(`release_url`/`board_url`) 양쪽에
같은 형태로 존재하므로 도메인 공통 개념으로 승격한다.

**core에 넣지 않는 것**

- 라우터 — 도메인마다 화면 수와 성격이 다르다. 각자 필요한 만큼만 갖는다.
- 차트 — 막대(전망 비교) / 시계열(고용동향) / 단면(인력수급)은 공통화 이득이 없다.
- 데이터 스키마 — 도메인마다 다르다. 이것이 도메인 분리를 택한 이유 자체다.

## 6. 허브

`hub/index.html`은 서비스명과 네 개의 진입 버튼으로 구성한다.

각 버튼 아래에 최신 갱신일을 한 줄 표시한다. 허브는 `/<도메인>/data/last_run.json`을
fetch 하고, **응답이 없으면 해당 버튼을 "준비중"으로 비활성화**한다.

이 방식이면 도메인을 떼어낼 때 허브 코드를 고칠 필요가 없고, 붙이면 자동으로 활성화된다.
허브가 도메인의 존재를 하드코딩으로 알지 않는다는 점이 느슨한 결합을 실제로 성립시킨다.

## 7. 고용동향 도메인

### 7.1 다루는 세 출처

같은 달의 고용을 서로 다르게 말하는 세 출처를 나란히 놓는 것이 이 앱의 존재 이유다.
"취업자 +12만 / 종사자 +8만 / 상시가입자 +25만"이 동시에 참일 수 있으며,
실무에서 어느 수치를 인용할지 판단하려면 정의 차이를 알아야 한다.

| 코드 | 통계명 | 작성기관 | 조사성격 | 대표수치 |
|---|---|---|---|---|
| `eaps` | 경제활동인구조사 | 국가데이터처 | 가구조사 | 취업자수 |
| `est` | 사업체노동력조사 | 고용노동부 | 사업체조사 | 종사자수 |
| `ei` | 고용행정 통계로 본 노동시장 동향 | 고용노동부 | 행정자료 | 상시가입자수 |

수집 범위는 **총량 + 산업 대분류**까지다. 세 출처 모두 산업별을 제공하므로
교차비교가 실제로 성립하는 유일한 축이다. 연령·사업장규모는 출처별 제공 단면이 달라
비교표에 빈칸이 과다해지므로 이번 범위에서 제외한다.

데이터는 **공표된 보도자료 기준 공개 자료만** 사용한다. 내부망 자료는 사용하지 않는다.
대외 공유가 목적인 서비스이므로 출처 표기가 명확해야 한다.

### 7.2 데이터 모델

`domains/employment/data/series.json` — 시계열 레코드. 출처를 1급 필드로 둔다.

```json
{
  "id": "eaps-2026-07-headcount-industry-C",
  "source": "eaps",
  "series": "headcount",
  "breakdown": "industry",
  "category": "C",
  "period": "2026-07",
  "value": 4485.0,
  "unit": "천명",
  "yoy": -32.0,
  "status": "잠정",
  "released_at": "2026-08-13",
  "release_url": "https://...",
  "attachments": [
    {"type": "hwpx", "url": "https://..."},
    {"type": "pdf",  "url": "https://..."}
  ],
  "collected_at": "2026-08-14T09:00:00+09:00"
}
```

| 필드 | 설명 | 필수 |
|---|---|---|
| `id` | `출처-기간-지표-단면-분류` 조합 | O |
| `source` | `eaps` / `est` / `ei` | O |
| `series` | 지표 코드. 이번 범위에서는 `headcount` 하나 | O |
| `breakdown` | `total` / `industry` | O |
| `category` | `breakdown=industry`일 때 표준산업분류 대분류 코드 | 조건부 |
| `period` | `YYYY-MM` | O |
| `value` | 수준 (천명) | O |
| `yoy` | 전년동월대비 증감 (천명) | O |
| `status` | `잠정` / `확정` | O |
| `released_at` | 보도자료 공표일 | O |
| `release_url` | 해당 회차 보도자료 게시글 URL | O |
| `attachments` | 첨부파일 직링크 (hwpx / pdf) | X |
| `collected_at` | 수집 시각 | O |

`series`가 세 출처에서 모두 `headcount`인 것은 **같은 개념이라는 뜻이 아니다.**
"그 출처의 대표 인원수"라는 자리를 가리킬 뿐이며, 실제 의미는 `source`가 결정한다.
화면 표기명은 `sources.json`의 `headline_ko`(취업자수 / 종사자수 / 상시가입자수)에서 가져오며,
세 값을 같은 이름으로 부르는 일이 없도록 한다. 이 구분이 곧 이 앱의 존재 이유다.

`release_url`은 회차별 게시글이라 언젠가 유실될 수 있다. 폴백으로 `sources.json`의
`board_url`(게시판 목록)을 두어 원문 접근 경로가 끊기지 않게 한다.

### 7.3 출처 메타

`domains/employment/data/sources.json` — 세 조사의 정의를 데이터로 보유한다.
화면에 상시 노출할 내용이므로 화면 코드에 하드코딩하지 않는다.

```json
{
  "code": "ei",
  "name_ko": "고용행정 통계로 본 노동시장 동향",
  "agency": "고용노동부",
  "type": "행정자료",
  "headline_ko": "상시가입자수",
  "coverage": "고용보험 가입 상시가입자",
  "release_rule": "매월, 전월 기준",
  "caveat": "고용보험 미가입 자영업자·특수형태근로 등은 포함되지 않음",
  "board_url": "https://www.moel.go.kr/news/enews/report/enewsList.do"
}
```

세 출처의 `coverage` 문구(총괄 카드와 출처비교 표에 그대로 노출):

- `eaps` — 15세 이상 인구 · 조사대상주간 1시간 이상 취업
- `est` — 1인 이상 사업체 · 농림어업 등 제외
- `ei` — 고용보험 가입 상시가입자

### 7.4 산업분류 처리

**세 출처의 산업 분류를 억지로 일치시키지 않는다.** 포괄범위가 실제로 다르기 때문이다.
사업체노동력조사는 농림어업·가사서비스를 제외하고, 고용보험은 가입 사업장만 포괄한다.

`industries.json`에 표준산업분류 대분류를 기준축으로 두고 출처별 제공 여부를 매핑한다.

```json
{"code": "A", "name_ko": "농업, 임업 및 어업",
 "provided": {"eaps": true, "est": false, "ei": true}}
```

제공되지 않는 칸은 **0이 아니라 `―`(미제공)으로 비운다.** 빈칸이 보이는 편이
잘못된 0보다 정직하며, 그 빈칸 자체가 "왜 숫자가 다른가"를 설명한다.

### 7.5 화면

모바일 전용. 상단 세그먼트 3개로 전환한다.

**① 총괄** (기본 화면)

- 기준월 스위처
- 출처 카드 3장 세로 스택: 대표수치 · 전년동월대비 증감 · 발표일 · `잠정`/`확정` 배지
- 각 카드에 **`coverage` 문구를 숫자 바로 아래 상시 노출** (접히는 주석이 아님).
  이 앱의 핵심 가치가 정의 차이의 인지이므로 숨기지 않는다.
- 카드마다 `원문보기` — 해당 월 보도자료 게시글. 첨부가 수집됐으면 hwpx/pdf 직링크 병기
- 추이 그래프는 이 화면에 두지 않는다. 7.6의 증감 비교 시트가 어느 화면에서나 열리므로
  중복이다.

**② 산업별**

- 산업 대분류 행 × 3출처 열 매트릭스. 값은 전년동월대비 증감
- 미제공 칸은 `―`
- 행 탭 → 해당 산업의 3출처 시계열 펼침
- 정렬 토글: 증감순 / 분류순
- 출처 열 헤더 탭 → 해당 출처 원문

**③ 출처비교**

- `sources.json` 기반 정의 비교표: 조사성격 · 포괄범위 · 유의사항 · 발표주기
- "취업자는 +12만인데 상시가입자는 왜 +25만인가"에 답하는 화면
- 각 출처 게시판 바로가기

### 7.6 증감 비교 시트

세 출처의 증감을 언제든 띄웠다 숨길 수 있는 하단 시트. 고용동향 앱의 유일한 그래프이며,
세 세그먼트 어디에서나 같은 자리에서 열린다.

**동작**

- 화면 하단에 얇은 핸들이 상시 노출된다: `증감 비교 · 2026.07 ▲`
- 탭하면 올라오고, 다시 탭 · 아래 스와이프 · 배경 탭으로 내려간다
- 열림/닫힘 상태는 세그먼트를 이동해도 유지한다 (`localStorage`)

**기준 (컨텍스트 연동)**

| 현재 화면 | 시트 기준 |
|---|---|
| 총괄 / 출처비교 | 전체 |
| 산업별에서 특정 산업을 펼친 상태 | 그 산업 |

기준월은 현재 화면에서 선택된 월을 따르며 기본값은 최신월이다.
헤더에 기준월과 기준 단면을 항상 명시한다 (`증감 비교 · 2026.03 · C 제조업`).

**구성 (2층)**

1. **선택월 단면** — 가로 막대 3개, 0 기준선. 막대는 0선 양쪽으로 뻗는다.
   세로 막대를 쓰지 않는 이유는 출처명이 길어 축 라벨이 회전·절단되기 때문이다.
2. **시계열** — **선택월과 무관하게 항상 최신월까지 그린다** (최근 24개월 범위).
   선택월에 수직 표식선과 각 계열의 강조점(>=8px), 값 라벨을 얹는다.
   선택월의 수치와 그 이후 최신월까지의 흐름이 한 화면에 같이 오게 하기 위함이다.
3. `표로 보기` 토글 — 접근성 대체 뷰

**색: 출처가 갖는다**

색은 출처 정체성만 나른다. 증감의 부호는 0선 기준 막대 방향과 시계열의 0선 교차로
드러나므로 색이 부호를 중복해서 뜻하지 않게 한다. 한 패널 안에서 색이 두 가지를
의미하면 안 된다.

| 출처 | 라이트 | 다크 |
|---|---|---|
| `eaps` | `#2a78d6` | `#3987e5` |
| `est` | `#eb6834` | `#d95926` |
| `ei` | `#1baf7a` | `#199e70` |

배정은 이 고정 순서를 따르며 순환하지 않는다. 출처가 하나 빠져도 남은 출처의 색은
바뀌지 않는다. 다크 스텝은 라이트를 자동 반전한 것이 아니라 다크 표면에 맞춰 선택한 값이다.

앱 실제 카드 배경(`#ffffff` / `#1e232b`)에 대해 전 조합(`--pairs all`) 검증 결과:

```
라이트: CVD ΔE 9.2 · 일반시야 ΔE 24.0 · [WARN] #1baf7a 대비 2.82:1
다크  : CVD ΔE 9.4 · 일반시야 ΔE 20.9 · 대비 전부 3:1 이상
```

라이트의 aqua 대비 미달은 **완화 조치 의무**다. 모든 막대에 값 직접 라벨을 붙이고
`표로 보기`를 제공하는 것으로 충족한다. 이 둘은 나중에 제거할 수 없다.

**마크와 라벨**

- 막대 끝 4px 라운드, 막대 간 2px 표면 간격, 선 2px, 강조점 >=8px
- 값은 막대 끝에 직접 표기 (`+25.3만명`)
- 3계열이므로 **범례를 상시 노출**하고, 3개 이하이므로 직접 라벨도 병행한다.
  정체성이 색 단독에 의존하지 않게 한다.
- 값·라벨·범례 텍스트는 텍스트 토큰을 쓴다. 계열 색을 글자에 입히지 않는다.
- 막대는 탭 시 툴팁(수준 · 증감 · 발표일 · 잠정/확정), 시계열은 crosshair + 툴팁
- **미제공 출처는 행을 지우지 않고 `― 미제공`으로 자리를 지킨다.** 사업체노동력조사가
  농림어업을 잡지 않는다는 사실 자체가 정보이므로 사라지면 안 된다.

**소속**

이 시트와 3색 팔레트는 고용동향 도메인에 속한다. `core/`에 올리지 않는다.
전망·인력수급의 차트는 형태가 다르므로 공통화 이득이 없고, core를 작게 유지해야
도메인 분리가 유지된다.

### 7.7 수집 파이프라인

기존 `collect.py`의 **변화 감지 + 부분 실패 허용** 패턴을 그대로 따른다.
저장된 최신값과 다를 때만 신규 레코드를 추가하고, 수집기 하나가 실패해도
나머지는 진행하며 실패는 `last_run.json`에 기록해 CI에서 표면화한다.

| 수집기 | 대상 | 방식 |
|---|---|---|
| `eaps.py` | 경제활동인구조사 | KOSIS OpenAPI |
| `est.py` | 사업체노동력조사 | KOSIS OpenAPI |
| `ei_press.py` | 고용행정 통계로 본 노동시장 동향 | 보도자료 첨부 파싱 |

- KOSIS API 키는 GitHub Secrets로 주입한다.
- 갱신은 월 1회지만 워크플로는 매일 돌린다. 값이 안 바뀌면 커밋하지 않으므로 no-op다.
- **`ei_press.py`는 hwpx를 우선 파싱하고 pdf를 폴백으로 둔다.** hwpx는 ZIP+XML이라
  표 구조가 보존돼 pdf 텍스트 추출보다 안정적이다. 보도자료 서식이 매월 거의 고정이라는
  점은 실무에서 확인됐다. 최근 회차 예시:
  `https://www.moel.go.kr/news/enews/report/enewsView.do?news_seq=19759`
- **수기 입력 폴백을 상시 유지한다.** `data/manual/<YYYY-MM>.json`이 존재하면
  수집기 결과보다 우선한다. 파싱이 깨진 달에도 서비스가 멈추지 않고 그 달만 손으로 채운다.

`release_url`·`attachments`는 수집 시 함께 기록한다. 원문 링크의 정확성이
이 서비스의 신뢰 근거이므로 수집기의 필수 산출물로 취급한다.

## 8. 전망 도메인 이전

전망 앱은 **기능 변경 없이 위치만 이동**한다.

- `web/` → `domains/forecast/app/`
- `src/` → `domains/forecast/pipeline/`
- `data/` → `domains/forecast/data/`
- `web/css/styles.css`의 `:root` 토큰과 공통 골격 → `core/`로 추출, 나머지는 앱에 잔류
- `app.js`의 경로 폴백 제거

리팩터 완료 기준은 **화면 변화 0, 기존 테스트 전부 통과**다.
타임라인 화면 스텁 구현과 PDF 기관 수집기 추가는 이 작업의 범위가 아니며,
현재 Claude Desktop에서 진행 중인 전망 작업과 충돌하지 않도록
리팩터 실행 시점은 그 작업이 일단락된 뒤로 잡는다.

## 9. 테스트

기존 원칙을 유지한다 — **네트워크 없이 CI가 돈다.**

- 수집기: 저장된 응답 픽스처(KOSIS JSON, 보도자료 hwpx 샘플)로 파싱을 검증
- 저장소 로직: 변화 감지, 중복 방지, 수기 입력 우선 처리
- 화면 파생 로직: `data.js` 수준의 순수 함수를 TDD로 (현행 전망 앱 패턴 동일).
  증감 비교 시트의 기준 선택(화면별 컨텍스트 → 기준 단면·기준월 해석)과
  미제공 처리도 순수 함수로 분리해 테스트한다.
- 조립: `tools/build.py`가 기대한 `_site` 트리를 만드는지

## 10. 단계 계획

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| **A. 리팩터** | 폴더 구조 이동, core 추출, hub, `build.py`/`serve.py`, 워크플로 분리 | 화면 변화 0, 기존 테스트 통과 |
| **B. 스파이크** | 고용노동부 보도자료 게시판에서 최신 회차 탐색 + 첨부 링크 추출 가능성 확인 | 가능/불가 판정과 근거, 픽스처 확보 |
| **C. 데이터** | 세 출처 수집기, 스키마, 픽스처 테스트 | 최근 24개월 적재 |
| **D. 화면** | 고용동향 3화면 + 증감 비교 시트 | 실기기 확인, 라이트/다크 양쪽 |

A는 기능 추가가 없어 안전하게 끝난다. 이후 인력수급·경제동향은 C·D만 반복한다.

각 단계는 별도 구현 플랜을 갖는다.

## 11. 가정과 미결

- **KOSIS OpenAPI에 경제활동인구조사·사업체노동력조사의 월별 산업 대분류 시계열이
  제공된다고 가정한다.** 단계 C 착수 시 최우선 확인 항목이며, 없으면 해당 출처도
  보도자료 파싱으로 전환한다.
- 경제활동인구조사(국가데이터처)·사업체노동력조사(고용노동부)의 보도자료 게시판 URL은
  수집기 구현 시 확정해 `sources.json`에 기록한다.
- 고용동향 시계열의 초기 적재 범위는 최근 24개월로 한다. 화면이 요구하는 최소 범위이며,
  필요 시 확장은 수집기 파라미터 변경으로 처리한다.
- 인력수급·경제동향의 데이터 모델과 화면은 이 문서의 범위 밖이다.

## 12. 이번 범위에서 제외 (YAGNI)

- 전망과 실적을 하나의 지표축에 겹쳐 보여주는 통합 뷰 — 원스톱 조회가 목적이지
  자체 분석 도구가 아니다
- 도메인 간 공통 검색 — 각 앱에서 찾는 것으로 충분하다
- 연령별·사업장규모별 단면 — 출처별 제공 단면이 달라 비교표가 빈칸투성이가 된다
- 사용자 계정, 즐겨찾기, 알림
- 도메인 공통 차트 라이브러리 — 표현 방식이 다른 것이 도메인 분리를 택한 이유다
