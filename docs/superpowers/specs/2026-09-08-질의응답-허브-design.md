## 2. 아키텍처

```
                      GitHub Pages (기존, 무변경)
                      ├── hub/            입력창 추가 → ./ask/#q=...
                      └── ask/            정적 화면 (바닐라 JS, 빌드 없음)
                              │ fetch
                              ▼
                      Cloudflare Worker
                      ├── /api/ask        얇은 래퍼: 직렬화 + IP 할당량 + CORS
                      ├── /api/health
                      └── [미래] /mcp     같은 core 를 툴로 노출
                              │
                      src/core/*.ts       ★ 프로토콜·네트워크 무관 순수 함수 (단일 진실원천)
                              │
                      D1 (12표 + 뷰 1)
                              ▲
                      GitHub Actions ── tools/d1_sync.py ── JSON 정본
```

**1번 규칙: 로직은 `core/` 에만 있다.** `/api` 는 감싸기만 한다. 두 번 짜는 순간 이 설계는 실패한다.

```
src/core/
  classify.ts   1패스 LLM 출력(고정 스키마) 검증·정규화 → {유형, 슬롯, 확신도}
  route.ts      슬롯 ↔ capability 대조 → 가능 / 부분 / 불가 / 우회
  query.ts      슬롯 → SQL → 관측 + 파생값 계산
  compare.ts    source_conflict → 비교가능 판정
  evidence.ts   가설 → 지표 시계열 + 방향판정 + 반증 + 유의성
  meta.ts       소스 단위 필터 → capability · limit · conflict 묶음
  verify.ts     2패스 산출 문장의 숫자를 근거 묶음과 대조
```

전부 `(deps, input) => output` 이고 **D1 은 `deps.db`, LLM 은 `deps.llm`** 으로 주입한다.
이 저장소가 이미 지키는 규율(`collect.main` 의 주입 지점)과 같은 모양이며, 테스트가 네트워크에 나가지 않는 근거다.

## 3. 데이터 모델 — 12표 + 뷰 1

### 3-1. 카탈로그 8표

```sql
source_catalog   (id PK, name_ko, agency, grade, axis, method, auth, endpoint,
                  rate_limit, archived, priority, terms_of_use, body_storable,
                  evidence, verified_at, evidence_status)
capability       (source_id PK, 주제, 집단축, 지역입도, 시간입도,
                  기간_from, 기간_to, 공표시차, evidence, verified_at)
capability_limit (id PK, source_id NOT NULL, 유형, axis, category, 내용, 사유,
                  evidence, verified_at, evidence_status)
source_conflict  (id PK, source_a, source_b, 차이유형, 설명, 비교가능,
                  evidence, verified_at)
phenomenon       (id PK, name_ko, 정의, 지역, 기간, time_grain, 근거서술)
hypothesis       (id PK, phenomenon_id, name_ko, 서술, 대립가설,
                  missing_for_verdict, 우회경로, 검정력_주석)
indicator        (id PK, name_ko, source_id, 정의, 모집단, 단위, 공표시차,
                  커버리지한계, data_status, time_grain, compare_basis, series_key)
hyp_indicator    (hypothesis_id, indicator_id, role, timing, expected_sign,
                  lead_lag, falsifies, PK(hypothesis_id, indicator_id))
```

- `grade` — `A|B|C|X` (조사 §1 등급표). `archived` — 아카이브가 실제로 쌓고 있는가
- `evidence_status` — `확인 | 미확인`. **미확인 항목도 싣는다.** "안 됩니다" 와 "아직 확인 못 했습니다" 는 다른 답이다
- `capability_limit.유형` — **6종**: `커버리지` `교차제한` `입도` `시의성` `접근성` **`업데이트`**
  - `업데이트` = 최초 등록값이 이후 갱신되지 않음 (고용보험 취득신고 보수)
  - 비교가능성은 `source_conflict` 가 전담하므로 유형에서 뺀다
  - **주의**: 기획서 §2-2 가 참조한 `데이터_한계와대안` 5유형은 배제 확정된 개인 위키에 있어
    두 md 어디에도 정의가 없다. 위 6유형은 이 스펙에서 새로 정의한 것이다
- `source_conflict` — **같은 쌍에 다중 행.** 경활↔행정통계는 `개념` 행과 `모집단` 행 둘로 들어간다
  (유형마다 근거·확인일이 다르므로 배열 컬럼이 아니라 행으로 가른다)
- `hyp_indicator.role` — `지지 | falsifies`, `timing` — `선후검정 | 수준확인 | 특정성`
- `indicator.compare_basis` — `수준 | 증감률만`, `time_grain` — `월 | 반기 | 연`

**체크 제약**: `time_grain <> '월' AND timing = '선후검정'` 인 행은 적재를 거부한다.
반기 지표에 선후를 붙이는 실수가 데이터 단계에서 막혀야 한다.

### 3-3. 파생 뷰

CTE 로 한 번만 계산해 `CASE` 가 같은 식을 되풀이하지 않게 한다.

```sql
CREATE VIEW hypothesis_verdict AS
WITH f AS (                                  -- 가설별 반증지표 집계
  SELECT h.id AS hypothesis_id,
         h.phenomenon_id,
         COUNT(x.indicator_id)                                        AS n_falsify,
         SUM(CASE WHEN i.data_status <> '보유' THEN 1 ELSE 0 END)      AS n_missing,
         SUM(CASE WHEN i.time_grain <> p.time_grain
                    OR i.compare_basis = '증감률만' THEN 1 ELSE 0 END) AS n_weak
    FROM hypothesis h
    JOIN phenomenon p    ON p.id = h.phenomenon_id
    LEFT JOIN hyp_indicator x ON x.hypothesis_id = h.id AND x.role = 'falsifies'
    LEFT JOIN indicator i     ON i.id = x.indicator_id
   GROUP BY h.id, h.phenomenon_id
)
SELECT f.hypothesis_id                                   AS id,
       (f.n_falsify > 0 AND f.n_missing = 0)             AS verdict_capable,
       CASE
         WHEN NOT (f.n_falsify > 0 AND f.n_missing = 0) THEN NULL   -- 판정 불가면 강도도 없다
         WHEN f.n_weak > 0                              THEN 'weak'
         ELSE 'strong'
       END                                               AS verdict_strength,
       CASE                                              -- 판정 불가의 사유를 가른다
         WHEN f.n_falsify = 0 THEN '반증미설계'           -- 반증지표가 아예 없다
         WHEN f.n_missing > 0 THEN '데이터미보유'          -- 설계는 됐으나 안 긁었다
         ELSE NULL
       END                                               AS verdict_blocked_by,
       f.n_falsify, f.n_missing
  FROM f;
```

**`verdict_blocked_by` 가 필요한 이유**: `verdict_capable=false` 의 사유가 둘인데
화면에서 같은 배지로 뭉개지면 안 된다. **`반증미설계`** 는 카탈로그를 더 써야 한다는 뜻이고
(우리 잘못), **`데이터미보유`** 는 수집기를 붙이면 된다는 뜻이다(경로가 이미 있음).
사용자가 할 수 있는 일이 전혀 다르므로 배지도 갈라야 한다. CTE 에 값이 이미 있어 비용은 0이다.

**뷰여야 하는 이유**: 일반 컬럼이면 수집기가 붙어도 손으로 고치지 않는 한 안 바뀐다.
뷰로 두면 `indicator.data_status` 하나가 '보유' 로 바뀌는 순간 판정이 저절로 살아난다. 코드는 안 건드린다.

`verdict_capable = false` 이면 `verdict_strength` 는 **NULL** 이다 — `weak` 을 내보내면
"약하게나마 판정함" 으로 오독된다.

`verdict_strength` 는 지표의 `time_grain` 을 **현상의 `time_grain` 과 대조**한다 —
반기 현상을 반기 지표로 검사하는 건 약한 검정이 아니다.

## 5. 질의 처리

### 5-1. 유형 6종

| 유형 | core 호출 | 조회 대상 |
|---|---|---|
| `메타한계` · `범위밖` | `meta`(소스 단위 필터) + `route` | **카탈로그만** |
| `수치조회` | `route` → `query` | 카탈로그 + 관측 |
| `출처비교` | `compare` → `query` | 카탈로그 + 관측 |
| `전망` | `query(forecast)` + rationale | 카탈로그 + 전망 |
| `원인탐색` | `evidence`, 현상 미등록 시 indicator 폴백 | 카탈로그 + 관측 |

**LLM 호출은 유형과 무관하게 같다** — 1패스(슬롯 분해)와 2패스(서술). 사용자가 슬롯을
고쳐 보내면 1패스를 건너뛰어 1회가 된다. **오른쪽 열은 LLM 호출 수가 아니라 어느 표를
읽는지다.** 이 둘을 섞어 읽으면 `메타한계`·`범위밖` 에서 서술을 건너뛰는 구현이 나오는데,
그 두 유형이야말로 "왜 못 주는지" 를 문장으로 설명해야 하는 자리다(확정사항 #4).

**원인탐색 폴백**: 현상이 미등록이면 가설 판정을 건너뛰고, 슬롯의 주제·대상집단으로
`indicator` 카탈로그를 매칭해 "이 질문을 파려면 이 지표들을 봐야 하고, N개 보유·M개 미보유"
를 낸다. 응답에 `판정없음: true`.

### 5-2. 2패스 — 둘 다 고정 스키마

```jsonc
// 1패스
{ "유형": "수치조회|출처비교|메타한계|전망|원인탐색|범위밖",
  "슬롯": { "주제": …, "집단축": […], "지역입도": …, "시간입도": …,
            "기간": {"from": …, "to": …}, "출처": […] },
  "확신도": 0.0 }

// 2패스
{ "답변": "…",
  "근거": [{"지표": …, "기간": …, "값": …, "출처": …, "유의성": "유의|불명|비유의"}],
  "한계": ["…"], "미확인": ["…"],
  "판정없음": false, "후속질문": ["…"] }
```

### 5-3. 파생값은 `query.ts` 가 계산한다 ★

LLM 에 넘기는 근거 묶음:

```jsonc
{ "지표": "IND_청년사무직취업자", "compare_basis": "수준",
  "관측": [ {"기간": "2025S1", "값": 744.3}, {"기간": "2025S2", "값": 727.4} ],
  "파생": { "차이": -16.9, "증감률": -2.3, "단위": "천명", "기준기간": "2025S1→2025S2" },
  "유의성": "불명", "유의성사유": "RSE 미공표(*)" }
```

파생 종류는 **차이 · 증감률 · 합계 · 비중 · 기여도** 다섯으로 고정한다.

- 이게 없으면 `verify.ts` 가 정상 답변을 전부 튕긴다 (744.3·727.4 만 넘기고 답변에 −16.9 가 나오면 대조 실패)
- **LLM 산술이 사라지므로 오류 경로 하나가 통째로 없어진다**
- **`compare_basis='증감률만'` 이면 `관측` 배열을 아예 싣지 않는다.**
  워크넷 구인·피보험자의 수준 비교 금지가 프롬프트 훈계가 아니라 *넘기지 않는 데이터*로 강제된다

### 5-4. 검증

`verify.ts` 는 `답변`·`근거` 에 등장하는 모든 숫자가 **관측값 ∪ 파생값** 집합에 있는지 대조한다.
하나라도 어긋나면 `답변` 을 버리고 카드만 렌더한다 (`검증실패: true`).

이 저장소에 이미 있는 패턴이다 — `tools/rationales.py` 가 LLM 이 지목한 문장이 원문에 실재하는지 대조한다.

### 5-5. 확신도

```
확신도 >= 0.6  → 판정된 유형으로 진행
확신도 <  0.6  → 유형을 '메타한계' 로 폴백 (틀려도 손해가 가장 적다), 저확신: true
```

**확신도는 LLM 자기보고이므로 그것만 믿지 않는다.** 코드 측 신호가 하나라도 걸리면 저확신으로 내린다:

- `슬롯.주제` 가 비었거나 카탈로그 어휘에 매칭되지 않음
- `슬롯.집단축` 이 어느 `capability.집단축` 에도 없음
- `슬롯.기간` 이 모든 소스의 `기간_from` 이전

모든 응답에 `이해: {유형, 슬롯, 확신도, 저확신}` 을 싣는다.
**사용자가 고친 슬롯으로 재질의하면 1패스를 건너뛴다** — LLM 호출이 1회 줄고 그 질의는 완전히 결정적이 된다.

### 5-6. IP 할당량

Workers KV, 키 `q:{ip}:{YYYY-MM-DD}`, TTL 48h.
초과하면 **LLM 만 건너뛰고 카드는 그대로 낸다** (`한도초과: true`). 기능이 죽지 않는다.

## 6. 화면

허브(`hub/`)는 도메인 카드 위에 입력창 하나를 얹고 `./ask/#q=...` 로 문자열만 넘긴다.
`hub/js/state.js` 의 `DOMAINS` 에 `ask` 한 줄이 늘 뿐 **"허브는 내용을 모른다" 원칙은 유지**된다.

`domains/ask/app/` 은 기존 도메인과 같은 모양이다 — 바닐라 JS 모듈, `core/tokens.css`·`base.css` 재사용,
번들러 없음. `tools/build.py` 는 `app/` 만 있으면 자동 발견하므로 **빌드 스크립트 무수정**이다.

```
[ 질문창 ]
[ 이해 카드 ]   ← 기본 접힘. 평시 한 줄("원인탐색으로 이해함 · 수정"), 저확신일 때만 펼침
[ 답변 문단 ]   ← 검증실패·한도초과면 이 블록만 사라진다. 근거는 남는다
[ 근거 ]        ← 유형별 렌더
[ 한계 · 미확인 ]
[ 출처 ]        원문 링크 + 확인일 + evidence_status
[ 후속질문 ]    ← route.ts 를 태워 가능·부분만 렌더. 불가는 버린다
```

| 유형 | 근거 블록 |
|---|---|
| `수치조회` | 관측 표 + 파생값 + 스파크라인 |
| `출처비교` | 3출처 나란히 + 비교가능 배지 + 차이 사유 |
| `메타한계` | 소스 카드 + 6유형 배지 + 우회경로 |
| `전망` | 기관별 전망 + 수정이력 + rationale 인용 |
| `원인탐색` | **「지지 증거」 ‖ 「반증 증거」 좌우 병치** + `verdict_blocked_by` 배지 + `missing_for_verdict` + 우회경로 |
| `범위밖` | 못 하는 이유 + 우회경로 + 답할 수 있는 질문 예시 |

**반증을 좌우로 나란히 두는 것이 이 프로젝트의 주장이다.** H1 을 주장하려면 H2 를 먼저 기각해야
한다는 게 기획서 §7 의 설계였고, 그게 화면에서 보여야 한다. 위아래로 쌓지 않는다.
반증 열이 비면 **비었다고 그린다**(숨기지 않는다) — 반증 지표가 없다는 사실 자체가
`verdict_capable=false` 의 이유다.

**배지 7종**: `유의성: 불명` · `검증실패` · `한도초과` · **`반증미설계`** · **`데이터미보유`** ·
`근거 미확인` · `저확신`. 뒤 둘은 `verdict_blocked_by` 에서 그대로 나오며, 하나로 뭉치지 않는다 —
사용자가 할 수 있는 일이 다르기 때문이다.
전부 데이터에서 나오고 화면이 지어내지 않는다. **색만으로 구분되지 않게 텍스트 라벨을 함께 넣는다**(공공 사이트).

기존 도메인이 `잠정` 배지를 *수집기가 상태를 안 넘긴다는 이유로 일부러 삭제한* 규율과 같은 계열이다.

**서비스워커**: 앱 셸만 캐시하고 `/api/ask` 는 캐시하지 않는다. 오프라인이면 질문창을 비활성화한다
(다른 도메인은 오프라인에서도 데이터가 보이므로 여기만 다르다).

4. §7 H3 반증조건 "산업 내 사무직 비중" → `DT_1ES3B33J` 로 **반기 검사 가능**

**`입도`(반기) + `시의성`** 이다. 이는 §2-2 가 스스로 세운 규율("미확인 제약은 등재 금지")이
왜 필요한지를 보여주는 사례이므로 스펙에 남긴다.

## 9. 테스트

**골든 질문 세트가 회귀 시험대다.** 유형 6종 × 대표 질문에 대해 **슬롯을 고정 입력으로 넣어
1패스를 건너뛰고** core 경로 전체를 돌린다. LLM 없이 완전 결정적으로 돌며, 같은 질문에 같은
라우팅·같은 근거·같은 한계가 나오는지를 지킨다 — §2-2 재현성 원칙의 집행 장치다.

| 층 | 도구 | 내용 |
|---|---|---|
| 카탈로그 무결성 | pytest | 참조 유효성 / `evidence_status='확인'` 이면 `evidence`·`verified_at` 필수 / `time_grain<>'월' AND timing='선후검정'` 0행 / **대립가설 없는 가설 0행**(§8) / `compare_basis='증감률만'` 지표에 수준 파생값 없음 |
| 동기화 | pytest | `d1_sync` 는 SQL **생성까지만** 검사, 실행은 주입 |
| `core/` | `node --test` | `classify` 정규화 · `route` 대조 · `query` 파생 5종 · `compare` · `verify` |
| `verify` 회귀 | `node --test` | 파생값만 쓰면 통과 / 없는 숫자 하나 섞으면 실패 |
| LLM 계약 | `node --test` | 필드 누락 · 유형 오타 · 숫자 환각 픽스처에서 안전하게 떨어지는지 |
| 골든 세트 | `node --test` | 유형 6종 결정적 통과 |

**테스트는 네트워크에 나가지 않는다.** `deps.db`·`deps.llm` 주입이 그걸 구조로 보장한다.
CI 는 `pages.yml` 의 기존 `python -m pytest -q tools` 와 `node --test` 목록에 경로를 추가한다.

## 11. 구현 착수 순서

앞의 둘은 **다른 어떤 것보다 먼저** 온다. 순서를 바꾸면 헛일할 위험이 그만큼 커진다.

### 0순위 — LLM 계약 스파이크 (약 30분, 버리는 코드)

카탈로그를 한 줄도 쓰기 전에, OpenRouter 저비용 모델에 **1패스 스키마를 실제로 강제해 본다.**

- 확인할 것: JSON 스키마 강제가 먹는가 · 유형 6종을 오타 없이 뱉는가 · 슬롯 필드가 채워지는가
- 실패하면 **그 자리에서 설계가 갈린다**: 모델을 올리거나, 스키마를 단순화하거나,
  1패스를 코드 파싱으로 내리거나. 어느 쪽이든 **뒤 작업을 시작하기 전에** 정해야 한다
- 산출은 답이지 코드가 아니다. 스파이크 코드는 남기지 않는다

### 1순위 — 골든 세트 선작성

**구현 전에** 유형 6종 × 대표 질문의 **기대 출력을 먼저 박는다.** 슬롯이 고정 입력이라
LLM 없이 돌므로, 이 파일은 곧 **그대로 실행되는 명세**다.

- 기대 출력을 먼저 두고 통과시키는 방향으로 가면 `core/` 가 구현 도중에 흔들리지 않는다
- 라우팅·근거·한계·배지까지 전부 기대값에 넣는다 — 나중에 채우면 구현에 맞춰 기대값을 고치게 된다

### 그다음

카탈로그 JSON(정본) → D1 스키마·마이그레이션 → `d1_sync` → `core/` 7함수 →
`/api` 래퍼 + 할당량 → `domains/ask/app/` 화면 → 허브 입력창 → 워크플로 스텝.

## 12. 이번 범위 밖

- **`/mcp` 진입점** — `core/` 분리로 나중에 래퍼 한 장이면 붙는다
- **문헌 축(보고서 본문 구조화)** — 별도 설계 단계. 다만 대상은 특정됐다:
  `documents.py` 가 6개 기관 회차 PDF **전문을 이미 fetch 하고서 문장 하나만 남기고 버린다**
  (KEIS 는 400dpi OCR 을 돌리고 그 결과를 버린다). 새 출처(KLI OAI-PMH)보다 **이미 확보 중인
  전문을 살리는 것이 1순위**다. 저장소에 PDF 는 0개지만 `forecasts.json` 의 `source_url` 이
  재수집 목록을 완비하고 있다 — 고유 문서 **32건**(KDI 8 · BOK 7 · OECD 7 · KIET 3 · KLI 3 ·
  IMF 2 · **KEIS 2**), OCR 필요분은 2건이라 **약 3분**.

  설계 시 규율:
  - 첫 확인 항목은 **D1 의 SQLite FTS5 지원 여부**. 안 되면 키워드·태그 컬럼 + LIKE 로 내린다
  - **JSONB 는 D1 에 없다**(PostgreSQL 타입). TEXT + `json_extract()` 이며, `json_extract` 필터는
    인덱스를 못 타 전체 스캔이 된다 → **자주 거는 축(주제·집단축·기간·출처)은 일반 컬럼으로 승격**하고
    JSON 에는 가끔 보는 부속 정보만 담는다
  - 원문 → 파서 → **구조화 데이터(정본)** 에서 XML 과 DB 를 **병렬 생성**한다. XML → DB 직렬로 엮지 않는다
    (XML 스키마가 흔들리면 DB 까지 깨진다). 기존 `JSON → d1_sync.py → D1` 과 같은 모양
  - 외부 공개는 **알림용 RSS/Atom** 과 **전체 내용 정적 XML** 을 분리해서 낸다.
    RSS 는 변경 알림 피드지 검색 프로토콜이 아니다
  - 본문 적재 가부는 `source_catalog.terms_of_use` · `body_storable` 로 **데이터가 판정**한다.
    정부·공공기관 발간물(공공누리)은 대체로 가능, 언론 기사는 불가(기획서 §8)
- **H4 · H5 · H6, 서울 대조, C·D·E축 실적재** — 기획서 §10 의 v2 보류 그대로
