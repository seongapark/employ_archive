# 고용행정통계 지표 화면 — 설계

2026-09-21. 선행 문서: `2026-09-11-경활-지표-화면-design.md`.

## 무엇을

총괄에서 고용행정통계 카드를 누르면 나오는 화면(`#/r/ei`)에, 경활 화면과
**똑같은 모양의 주요 지표 판과 추이 그림**을 얹는다.

지금 그 화면에는 카드·보도자료 요약·속성별 상위만 있다. 숫자는 상시가입자수
하나뿐이고, 지표 판과 추이 구역은 아예 뜨지 않는다.

선행 문서가 그 자리를 비워 두면서 이유를 적어 두었다. `release.js` 의
주석에도 남아 있다:

```
// 출처마다 발표하는 지표가 다르다. 지금은 경활만 총괄 지표를 읽는다 —
// 사업체·행정통계는 이 화면을 보고 넓히기로 했다(2026-09-11 사용자 판단).
```

이 문서가 그 후속이다. 경활 화면을 실제로 써 본 뒤의 결정이다.

## 왜 지금 되는가

화면 부품은 이미 출처를 가리지 않는다. `kpiBlockHtml`·`trendSection`·
`comboSvg`·`indicatorSeries` 어디에도 `eaps` 가 박혀 있지 않다. 막고 있는
것은 **데이터**다 — `ei` 수집기는 상시가입자수(`series='headcount'`) 하나만
읽는다.

그 지표들이 **이미 매달 받는 hwpx 안에** 들어 있다. 새 출처도, 새 네트워크
호출도 없다. 2026-08 회차(`domains/press/sources/releases/ei_2026-08.hwpx`)로
확인했다:

| 표 | 내용 | 월 행 |
|---|---|---|
| 81 | 취득자수(계·신규·경력)·상실자수 — 수준·증감·증감률이 한 표에 | 28 |
| 82·83·84 | 구직급여 신규신청자수·지급자수·지급건수·지급액 — 수준/증감/증감률 세 표 | 28 |
| 94·95 | 고용24 신규구인인원·신규구직인원·구인배수 — 수준/증감 두 표 | 28 |
| 85~92 | 산업별 구직급여 신규신청자수·지급자수 | 28 |
| 96~99 | 산업별 신규구인인원 | 28 |
| 65 | 이미 읽는 가입자수 표. 6열이 **서비스업 집계** | 28 |

`periods.month_rows` 가 네 표 모두 손대지 않고 28개월을 읽어 냈다. 기간 파서를
새로 쓸 필요가 없다 — 경활 xlsx 와 같은 관례를 쓴다.

28개월 중 앞의 넷은 연도별 8월이라 띄엄띄엄하고(2021-08·2022-08·2023-08·
2024-08) 그 뒤 **2024-08~2026-08 25개월이 연속**이다. 추이가 그리는
`TREND_MONTHS = 25` 와 정확히 맞는다 — `indicatorSeries` 의 `slice(-25)` 가
띄엄띄엄한 앞쪽을 알아서 잘라 낸다. 기존 `ei` 레코드도 28개월을 그대로
쌓고 있으므로 새 지표만 다르게 저장하지 않는다.

## 사용자가 정한 것

1. **KPI 는 두 행.** 1행 `고용보험` = 취득자수·상실자수, 2행 `구직급여` =
   신규신청자수·지급자수·지급액.
2. **상시가입자수는 KPI 에 넣지 않는다.** 화면 맨 위 카드가 이미 그 숫자와
   증감을 말하므로 바로 아래 판에서 되풀이된다. 경활은 카드가 취업자수,
   KPI 가 고용률·실업률이라 겹치지 않았다.
3. **추이는 아홉 장.** 상시가입자수·취득자수·상실자수·구직급여 신규신청자수·
   지급자수·지급액·신규구인인원·신규구직인원·구인배수.
4. **범위 탭은 전체·제조업·서비스업.** 그 탭이 내지 않는 지표는 그림을
   그리지 않는다.
5. 그림 자체는 경활과 같다 — 수준 선 + 증감 막대, 스크럽 라벨.

## 산업 구분이 지표마다 다르다

보도자료가 산업을 가르는 범위가 지표마다 다르다. 실물로 확인한 것:

| 지표 | 전체 | 제조업 | 서비스업(집계) |
|---|---|---|---|
| 상시가입자수 | ✓ | ✓ (대분류 C) | ✓ (65번 표 6열) |
| 구직급여 신규신청자수 | ✓ | ✓ | 없음 |
| 구직급여 지급자수 | ✓ | ✓ | 없음 |
| 신규구인인원 | ✓ | ✓ | 없음 |
| 취득자수·상실자수 | ✓ | 없음 | 없음 |
| 지급액·신규구직인원·구인배수 | ✓ | 없음 | 없음 |

그래서 탭마다 그림 수가 다르다 — **전체 9장, 제조업 4장, 서비스업 1장.**

구직급여·구인의 서비스업 집계 열은 보도자료에 없다. 대분류를 더해서 만들 수는
있지만 그러지 않는다. 표에 `기타*` 집계 열이 섞여 있어 합이 전산업과 맞지
않고, **원문에 없는 숫자를 만들어 내는 일**이기 때문이다(이 저장소의 기존
원칙 — `ei.py` 가 서비스업·기타 집계 열을 일부러 빼 온 것과 같은 이유다).

서비스업 탭이 한 장뿐인 것은 정보다. 그 아래에 왜 한 장인지를 적는다:

> 고용행정통계는 서비스업 집계를 가입자수에만 냅니다.

이 처리에 코드가 거의 들지 않는다. `trendSection` 이 이미
`if (!points.length) return ''` 로 없는 지표의 자리를 만들지 않는다.

## 데이터 모델

### 지표 축 (`series`)

`SeriesRecord.series` 에 여덟을 더한다. `headcount` 는 그대로 상시가입자수다.

| series | 뜻 | unit | yoy 의 뜻 |
|---|---|---|---|
| `headcount` | 상시가입자수 (기존 레코드 전부) | 천명 | 천명 증감 |
| `acquired` | 피보험자격 취득자수 | 천명 | 천명 증감 |
| `separated` | 피보험자격 상실자수 | 천명 | 천명 증감 |
| `benefit_new` | 구직급여 신규신청자수 | 천명 | 천명 증감 |
| `benefit_paid` | 구직급여 지급자수 | 천명 | 천명 증감 |
| `benefit_amount` | 구직급여 지급액 | 억원 | 억원 증감 |
| `job_openings` | 고용24 신규구인인원 | 천명 | 천명 증감 |
| `job_seekers` | 고용24 신규구직인원 | 천명 | 천명 증감 |
| `openings_ratio` | 구인배수 | 배 | 배 차이 |

`make_id` 가 이미 `series` 를 키에 싣는다. **기존 2,892건의 id 는 한 글자도
바뀌지 않는다.**

취득자수의 신규·경력 분해는 저장하지 않는다. 그릴 자리가 없다 — 필요해지면
그때 두 계열을 더한다.

### 단위 축 (`unit`)

`Unit` 리터럴에 `억원`·`배` 를 더한다. 지급건수(천건)·1인당 지급액(천원)은
저장하지 않으므로 그 단위도 만들지 않는다.

### 속성 축 (`breakdown`)

새 값을 만들지 않는다. 기존 다섯(`total`·`industry`·`sex`·`age`·`scope`)으로
충분하다.

- **제조업** = `breakdown='industry'`, `category='C'`. 제조업은 실제 표준산업분류
  대분류이므로 산업 축에 그대로 둔다. 상시가입자수는 이미 이렇게 쌓여 있다.
- **서비스업** = `breakdown='scope'`, `category='services'`. 서비스업은 대분류가
  아니라 여러 대분류를 묶은 **집계**다. `industry` 에 넣으면 속성별 매트릭스에서
  대분류들과 나란히 서서 이중 계상으로 읽힌다. `scope` 는 경활의 15~64세가 같은
  이유로 쓰는 축이고, `segments.json` 에 없으므로 매트릭스 화면이 건드리지 않는다.

### 산업별은 두 열만 읽는다

산업별 표(85~92·96~99)에는 대분류가 19개씩 들어 있지만 **전산업과 제조업 두
열만** 읽는다. 전부 읽으면 28개월 × 19분류 × 3지표 ≈ 1,600건이 쌓이는데 그릴
화면이 없다. 필요한 화면이 생기면 그때 열을 넓힌다.

전산업 값은 요약표(82·94)에 이미 있으므로, 산업별 표에서 실제로 새로 읽는
것은 **제조업 열 하나**다. 전산업 열은 대조에만 쓴다(아래).

## 수집기 — 표 찾기와 대조

`ei.py` 의 기존 규약을 따른다. **표는 인덱스가 아니라 헤더 내용으로 찾고,
같은 헤더의 표가 여럿이면 문서 자체가 가진 항등식으로 어느 것이 수준 표인지
가른다.**

이 문서의 표들은 대조점이 특히 풍부하다. 실측으로 전부 확인했다(2026-08):

| 대조 | 식 | 실측 |
|---|---|---|
| 취득자수 분해 | 계 = 신규 + 경력 | 550 = 56 + 494 |
| 구직급여 수준 표 판별 | 지급액 ÷ 지급자수 ≈ 1인당 지급액 | 10,084억 ÷ 615천명 = 164만원 vs 표 1,640천원 |
| 구인 수준 표 판별 | 구인배수 ≈ 신규구인 ÷ 신규구직 | 161 ÷ 352 = 0.457 vs 표 0.46 |
| 신규구직인원 분해 | 성별 합 = 연령 합 = 계 | 158 + 194 = 352 |
| 산업표 ↔ 요약표 (신규신청) | 85번 전산업 = 82번 신규신청자수 | 81 = 81 |
| 산업표 ↔ 요약표 (지급자수) | 89번 전산업 = 82번 지급자수 | 615 = 615 |
| 산업표 ↔ 요약표 (신규구인) | 96번 전산업 = 94번 신규구인인원 | 161 = 161 |

마지막 셋이 특히 중요하다. 85·87·89·91 네 표가 **헤더가 똑같다**(신규신청
수준/증감, 지급자수 수준/증감). 크기로는 못 가른다 — 요약표와 맞춰 보는 것만이
확실하다. 서식이 바뀌어 순서가 흔들리면 조용히 틀린 값을 넣는 대신 실패한다.

`check_coverage` 에 새 지표의 최신월 존재 검사를 더한다. 열이 밀려 한 지표가
통째로 빠지면 화면에서는 그냥 없는 그림으로 보일 뿐 아무 흔적도 남지 않는다.

## 화면

### KPI 판 — 행마다 칸 수가 다르다

지금 `kpiRows` 는 `{name, indicator}` 이고 열은 `SCOPES` 세 개로 고정이다.
행정통계는 열 축이 연령이 아니므로 이 모양이 안 맞는다.

**모든 행을 `{name, tiles: [...]}` 한 가지 모양으로 바꾼다.** 경활 쪽은
`scopeTiles(indicator)` 헬퍼가 `SCOPES` 로부터 같은 세 칸을 만들어 낸다 —
**경활이 뱉는 HTML 은 한 글자도 바뀌지 않고, 기존 테스트가 그대로 통과한다.**

행정통계는 행마다 칸 수가 다르다:

```
고용보험   │ 취득자수   │ 상실자수  │
구직급여   │ 신규신청자수 │ 지급자수 │ 지급액 │
```

`.kpis` 가 `repeat(3, 1fr)` 로 못 박혀 있으므로 `--cols` 사용자 지정 속성으로
바꾸고 행이 자기 칸 수를 싣는다. 경활은 3이 기본값이라 바뀌지 않는다.

두 행의 칸 너비가 서로 다른 것은 받아들인다. 칸을 하나 비우면 판이 깨져
보이고, 세 번째 칸을 억지로 채우려면 원문에 없는 숫자(순증 = 취득 − 상실)를
만들어야 한다.

### 값 포맷

`fmtValue`·`fmtChange` 의 `if (unit === '%')` 두 갈래를 **단위 표 하나**로
바꾼다. 갈래가 넷이 되면 if 사슬이 읽히지 않는다.

| unit | 값 | 증감 |
|---|---|---|
| `천명` | `1,587.7만명` | `+27.7만명` |
| `%` | `70.4%` | `+0.5%p` |
| `억원` | `10,084억원` | `-245억원` |
| `배` | `0.46배` | `+0.02배` |

`배` 는 소수 둘째 자리까지다. 첫째 자리로 줄이면 한 달 변화(0.02)가 전부
`+0.0배` 로 뭉개진다.

### 범위 탭

`SCOPES` 상수를 출처별로 가른다.

```js
EAPS_SCOPES = [15세 이상 · 15~64세 · 청년]          (지금 그대로)
EI_SCOPES   = [전체 · 제조업(industry/C) · 서비스업(scope/services)]
```

`trendSection` 은 고른 탭의 `breakdown`·`category` 를 아홉 지표에 똑같이
건네고, 그 조합이 없는 지표는 이미 `points.length === 0` 으로 걸러진다.
**탭별로 그림 수가 달라지는 동작에 새 코드가 필요 없다.**

탭이 하나뿐인 출처를 위해 `scopeTabs` 를 조건부로 그리는 한 줄을 더한다
(사업체노동력조사를 넓힐 때 쓴다).

### CSS

`.kpi__value` 가 20px · `nowrap` 이고, 400px 화면에서 한 칸이 약 113px 이다.
경활 KPI 는 `70.4%` 뿐이라 맞았지만 `10,084억원`·`61.5만명` 은 넘친다.
비율이 아닌 값에 작은 글자(약 16px)를 주는 수식어 클래스를 더한다.

## 어떻게 검증하나

- **수집**: `ei_2026-06`·`ei_2026-07`·`ei_2026-08` 세 회차 hwpx 가 저장소에 있다.
  세 회차 모두에서 아홉 지표가 28개월씩 나오는지, 대조 일곱이 전부 통과하는지.
- **대조 가드**: 표를 일부러 바꿔치기한(증감률 표를 수준 표 자리에 놓은) 입력이
  `ValueError` 로 실패하는지. 기존 `test_ei.py` 가 같은 모양의 검사를 갖고 있다.
- **화면**: `kpiBlockHtml(series, {source:'ei'})` 가 두 행 다섯 칸을 내는지,
  `trendSection` 이 탭별로 9·4·1장을 내는지. 순수 함수라 DOM 없이 테스트된다.
- **회귀**: 경활 화면의 기존 테스트가 손대지 않고 통과해야 한다. 통과하지
  않으면 `kpiRows` 단일 모양 전환이 출력을 바꾼 것이다.

## 배포 뒤

다음 수집 회차에 과거 25개월이 한 번에 들어온다(`store.upsert` 가 id 로
덮어쓴다). 그래프가 첫 수집만으로 가득 찬다 — 25개월을 모으려고 2년을 기다릴
일이 없다.

## 하지 않는 것

- 사업체노동력조사(`est`) 지표 — 이 화면을 보고 다시 정한다.
- 산업별 구직급여·구인을 19개 대분류 전부 수집하는 일.
- 서비스업 구직급여·구인의 대분류 합산.
- 지급건수·1인당 지급액·지급건수당 지급액.
- 취득자수의 신규·경력 분해.
