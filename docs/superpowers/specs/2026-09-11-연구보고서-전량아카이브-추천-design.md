# 연구보고서 — 전량 아카이브 전환과 추천

작성 2026-09-11. 워크트리 `~/Desktop/연구보고서-전량아카이브`, 브랜치 `reports/full-archive`.
선행 문서: `2026-09-10-연구보고서-아카이브-design.md`(도메인 최초 설계).

## 1. 왜 바꾸나

지금 이 도메인은 **거르는 아카이브**다. KDI·KIET 게시판에 `filter: true` 가 걸려 있어
고용 키워드가 안 걸리면 버린다. 그 결과 이미 긁어둔 raw 1,533건 중 **583건을 버리고
950건만 수록**하고 있다.

취지가 바뀌었다. 이 사이트는 **외부기관 보고서를 취합하는 아카이브**이고, 그중에서
읽을 만한 것을 **추천**으로 골라주는 쪽이 맞다. 거르는 일은 수록 단계가 아니라 추천
단계가 한다.

바꾸는 것 셋:

1. **한국은행(BOK)을 다섯 번째 기관으로 추가** — 게시판 8개, 2021년 이후 710건
2. **전량 수록으로 전환** — `filter` 를 없애고 583건을 복원. 총 2,243건
3. **추천 기능 신설** — LLM 이 관심축 프로파일에 비추어 판정하고 이유를 남긴다

셋은 한 스펙이지만 **순서가 있다.** 전량 수록(2)을 먼저 하면 그날로 홈 타임라인이
583건 더 늘어난 채 추천 없이 남는다. 그래서 **2와 3을 같은 회차에 내보내고**, BOK 수집(1)은
첫 수집이 며칠 걸리므로 그 앞에 시작해 뒤에서 합류시킨다. 구현 계획이 이 순서를 지킨다.

## 3. 실측으로 정한 것

추측이 틀렸던 지점과, 설계가 거기에 어떻게 매였는지.

### 3-1. BOK 목록은 JS 로 그려지지만 AJAX 원본이 서버 렌더 HTML을 준다

`list.do` 는 빈 껍데기다. 그리는 주체는 `/portal/singl/newsData/listCont.do` 이고,
이건 `bbsRowCls` 항목이 든 완성된 HTML을 돌려준다. **쪽당 100건·`pageIndex` 페이징**이라
2021년까지 백필된다.

고용전망 도메인의 BOK 수집기(`domains/forecast/pipeline/collectors/bok.py`)는 RSS 를 쓴다.
그건 **최신 회차만 필요해서**다. 여기는 백필이 필요해 경로가 다르다 — **코드를 공유하지 않는다.**

### 3-2. 게시판 22개가 전부 같은 파서 하나로 처리된다

목록 엔드포인트가 하나고, 상세는 전부 `/portal/bbs/<bbsId>/view.do?nttId=` 다.
`bbsId` 는 `P0002353` 형과 `B0000368` 형 둘 다 있지만 **목록 앵커에 박혀 있어
`boards.json` 에 적을 필요가 없다.** 게시판은 `menuNo` 로만 구분한다.

### 3-3. `div.dbdata` 가 게시판마다 다른 것을 담는다

상세 본문 블록의 내용이 초록일 때도, 목차일 때도, "첨부파일 참조" 안내문일 때도 있다.
**게시판별로 갈라 담지 않으면 목차가 초록 자리에 들어간다.**

| 게시판 | 본문에 든 것 | 넣을 곳 |
|---|---|---|
| BOK 이슈노트 | 초록 1,500~2,000자 | `abstract` |
| 이슈분석·심층연구 | 초록 2,800~3,200자 (앞에 출처 안내문) | `abstract`, 안내문 제거 |
| 경제상황 평가 | ▣ 요약 불릿 210~280자 | `abstract` |
| 경제전망보고서 | 목차 (Ⅰ. 국내외 여건…) | `toc` |
| 국제경제이슈 | 목차 (`<목차>` 로 시작) | `toc` |
| 지역경제보고서 | 발간 안내문 + 목차 | `toc` |
| 주력산업 모니터링 | "자세한 내용은 첨부파일 참조" 25자 | 버리고 `abstract_note='요약 없음'` |
| 조사연구자료 | 대부분 "※ 첨부파일 확인" 27자 | 같음 |

### 3-4. 첨부 PDF 는 토큰·리퍼러 없이 그대로 받아진다

상세 HTML 의 `<a href="/fileSrc/portal/<hash>/1/<hash>.pdf">` 가 안정된 주소다.
받아보니 200 OK, 3MB, `%PDF-1.6`. (뷰어가 쓰는 `file-cdn.bok.or.kr` 토큰 URL 은 만료된다 —
그쪽을 저장하면 안 된다.) 따라서 나중에 `enrich.py` 로 원문에서 초록을 채울 수 있다.
**이번 범위 밖이다.**

### 3-5. 고른 8개 게시판 사이 중복은 0건

`nttId`·제목 양쪽으로 확인했다. 겹치던 것은 집계 게시판(`지역연구자료`·`간행물`·`조사연구`·
`국외사무소자료` 등 상위 메뉴)이었고 그걸 안 골랐다.

남은 중복은 **조사연구자료 내부의 7쌍** — 같은 연구를 두 지역본부가 각각 올린 것이다
(강원/강릉 4쌍, 광주전남/목포, 경기/강원). `build` 에서 같은 게시판 안 제목 완전일치 시
**이른 날짜 1건만** 남긴다. 수집은 전부 받아두므로 이 규칙도 재수집 없이 바뀐다.

### 3-6. 제목만 임베딩한 유사도로는 고용 여부를 못 가른다

사용자 제안을 실제로 돌려봤다(`jhgan/ko-sroberta-multitask`, 양성 = KLI·KEIS 635건,
대상 = 조사연구자료 403건, 점수 = 양성 상위 5개 평균 코사인).

- 키워드가 놓친 고용 연구 6건의 순위가 **11·75·84·92·109·210등**으로 흩어졌다
- **음성 후보(KDI·KIET 탈락분 583건)의 상위 10%가 0.635인데 BOK 고용 연구 35건의 평균은 0.612** —
  양성 평균이 음성 상위 10%보다 낮다. 단일 임계값으로 자를 수 없다
- 같은 컷에서 정밀도 23/45 ≈ 51%

원인은 구조적이다. 이 코퍼스는 제목이 죄다 "○○지역 △△ 현황 및 시사점" 한 문체라
임베딩이 *지역 경제 연구라는 장르*를 먼저 잡는다. 상위 45등에 디스플레이산업·기업경영분석·
지역경쟁력이 섞였다. 게다가 조사연구자료는 초록이 없어 **본문을 넣어 개선하는 길이 막혀 있다.**

**다만 버리지는 않는다.** 상위 45등 안에 키워드가 놓친 진짜 후보가 보였다("청년층의 지역별
직장 선호 분석" 4등 등). **판정자로는 못 쓰고, "왜 빠졌지" 검토 목록 도구로는 쓸 만하다.**
별건으로 남긴다(§9).

### 3-7. 규모가 2.4배로 늘어도 첫 화면은 안 느려지고 검색이 걸린다

| 파일 | 지금(950건) | 2,243건 추정 | 받는 시점 |
|---|---|---|---|
| `reports.json` | 648KB → gzip 79KB | gzip 약 186KB | 첫 화면 |
| `abstracts.json` | 3.9MB → gzip 1.1MB | gzip 약 **2.7MB** | 검색창 포커스 |

초록은 이미 지연 로딩이다(`app.js` `prefetchAbstracts`). 이번 회차엔 **쪼개지 않는다.**
`last_run.json` 에 gzip 크기를 기록해 관측하고, **gzip 3MB 를 넘으면 그때 기관별로 쪼갠다.**
미리 쪼개면 검색 품질과 복잡도를 숫자가 나오기 전에 내주는 셈이다.

## 4. 전량 수록 전환

- `boards.json` 의 `filter` 필드와 레코드의 `employment` 필드를 **없앤다.**
- `matched`(키워드 주제 태그)는 **남긴다.** 주제 화면이 그걸로 돌아가고, 추천과 별개로
  "주제로 찾기" 입구가 계속 필요하다. 키워드는 *거르는 도구*에서 *분류하는 도구*가 된다.
- `keywords.json` 은 손대지 않는다. 거르지 않으므로 §3-6 에서 드러난 구멍
  (`고용현황`·`청년층 고용` 이 안 걸림)은 **주제 태깅 누락**으로만 남는다. 이건 추천이
  따로 판정하므로 급하지 않다.
- 기존 테스트 `test_changing_keywords_flips_the_verdict_without_recollecting` 는
  전제가 사라진다. **주제 태깅이 재수집 없이 바뀌는지**를 지키도록 고쳐 쓴다.

## 6. 추천

### 6-1. 어디에 두나

```
collect    게시판 → sources/raw          판정하지 않는다
build      raw → reports.json            전량 수록. 결정적·오프라인
recommend  reports → recommendations.json  LLM. 실패해도 아카이브는 산다
```

`build` 안에 넣지 않는다. 넣으면 빌드가 API 키·네트워크에 묶여, 이 도메인이 일부러
만들어 둔 성질("판정을 고쳐도 재수집 없이 수십 초")이 깨진다. `enrich.py` 와 같은 자리다.

### 6-2. 관심축 프로파일

`domains/reports/data/interests.md` — 사람이 읽고 고치는 파일이고, **추천 기준의 유일한 사본**이다.

second-brain(`~/Desktop/second-brain`, 로컬 전용)에서 주제 축만 추렸다.
**`employ_archive` 는 PUBLIC 저장소이므로 센터명·프로젝트명·진행상황은 전부 뺀다.**

축 여덟:

1. **AI·기술변화의 직종별 고용영향** — 산업이 아니라 직종(과업) 기준. AI 노출도, 자동화,
   사무직 위축, 대체·보완 직종
2. **청년 고용** — 사무직 구직, 첫 일자리, 니트, 지역 이탈·정착, 청년 대상 타겟팅
3. **지역 노동시장** — 지역별 고용구조, 산업 특화·집중도, 미스매치, 지역 간 이동
4. **산업·직종 구조** — 특정 산업의 고용구조, KSIC 와 KECO·KSCO·ISCO 연계
5. **직업훈련과 취업성과** — 훈련수료자 취업률, 관련직종 판정, 창업·창직
6. **채용수요·구인구직** — 민간 채용공고와 공식 통계의 차이, 속보성 지표, 구인난
7. **임금·근로조건** — 임금 개념과 포함범위, 임금격차, 시간제·근로시간
8. **고용행정데이터와 방법론** — 고용보험 DB·행정통계의 범위와 한계, 통계 간 비교 가능성,
   인구효과/고용효과 분해·군집·분산분해 같은 분석기법, 지수 설계

닿지 않는 것(프로파일에 명시): 통화·금리·물가·환율, 재정, 부동산·가계부채, 무역·통상,
지급결제, 고용과 연결되지 않는 산업 기술동향.

이 파일을 고치면 `profile_version` 이 올라가고 **전체가 재판정된다.**

### 6-3. 판정 계약

`domains/reports/pipeline/recommend.py`. 행통 `llm_cite.py` 와 같은 모양을 쓴다.

- 입력: 제목 + 초록(최대 800자) + 기관·시리즈. **20건씩** 묶어 호출
- 모델 `claude-opus-5`. 공급자는 `ANTHROPIC_API_KEY` → `OPENROUTER_API_KEY` 순으로 있는 것
- 프롬프트 앞부분(프로파일)은 고정해 캐시 대상으로 둔다
- 출력 한 줄: `{"n": 1, "pick": true, "axis": "청년 고용", "why": "청년 사무직 감소를 직종 기준으로 분해"}`
- `n` 은 **그 묶음 안의 1부터 시작하는 번호**다. 호출자가 묶음 순서로 보고서 id 에 되맞춘다
  (행통 `judge` 와 같다). 모델에 id 를 그대로 주지 않는 이유는 id 를 지어내면 조용히
  엉뚱한 레코드에 붙기 때문이다
- `axis` 는 §6-2 의 여덟 축 이름 중 하나여야 한다. 그 밖의 값이면 에러
- **이유를 반드시 받는다.** 없으면 왜 틀렸는지 아무도 못 본다
- **빠진 항목은 에러로 올린다.** 조용히 `pick: false` 로 두면 누락이 안 보인다

### 6-4. 캐시

`domains/reports/data/recommendations.json`:

```json
{"id": "bok-11064490", "pick": true, "axis": "청년 고용",
 "why": "청년 사무직 감소를 직종 기준으로 분해",
 "basis": "abstract", "model": "claude-opus-5",
 "profile_version": 1, "judged_at": "2026-09-11T11:40:00+09:00"}
```

- 키는 보고서 id. **이미 판정한 건 다시 안 부른다**
- `basis` 는 `"abstract"` 또는 `"title"`. 초록이 없어 제목만으로 판정한 레코드를 표시한다
  (주력산업 모니터링 8건, 조사연구자료 상당수, KLI 256건). 나중에 초록을 채우면
  그 레코드만 재판정하면 된다
- `profile_version` 이 현재 프로파일과 다르면 재판정 대상

### 6-5. 비용

초회 2,243건 = 20건씩 113회 호출 → 입력 약 1.1M·출력 약 0.11M 토큰.
Opus 5 기준(입력 $5/MTok, 출력 $25/MTok) **약 $8**. Batch API 로 돌리면 절반.
이후는 하루 40~60건씩 3회 호출이라 **월 $1 미만.**

## 7. 화면

탭 넷: **홈 · 추천 · 주제 · 기관**.

- **홈** — 검색창 아래에 추천 섹션. **발행일 내림차순 6건**(기관 편중을 막으려 한 기관
  최대 2건), 각 행에 이유 한 줄, 끝에 `더보기 ›` 로 추천 탭으로 간다. 그 아래 기존
  최신발간 타임라인. 타임라인 행에는 추천 표시를 붙여 둘이 따로 놀지 않게 한다
- **추천(신설)** — 관심축별로 묶은 목록. 축 이름 + 건수 + 보고서 행 + 이유 한 줄.
  축 순서는 추천 건수 내림차순, 축 안은 발행일 내림차순
- **주제** — 그대로. `matched` 기반이라 전량 수록의 영향을 받지 않는다
- **기관** — BOK 한 줄 추가
- **보고서 상세** — 추천된 레코드면 축과 이유를 보여준다

## 8. 검증

- **BOK 파서**: `tests/fixtures/bok/` 에 실제 페이지 고정본을 떠서 목록 파싱·상세 파싱·
  초록/목차/안내문 분류를 네트워크 없이 검증
- **중복 제거**: 조사연구자료 7쌍을 고정본으로 넣고 이른 날짜만 남는지
- **추천**: `call` 을 주입해 가짜 응답을 물리고 — 판정 파싱, 캐시 적중(이미 판정한 건
  안 부름), `profile_version` 변경 시 재판정, **빠진 항목이 에러가 되는지**
- **전량 수록**: `filter` 가 사라진 뒤 raw 가 전부 수록되는지, `matched` 는 그대로 붙는지
- **워크플로**: `collect-reports.yml` 에 `recommend` 단계와 시크릿 둘을 배선.
  추천이 실패해도 수집·빌드 결과는 커밋된다
