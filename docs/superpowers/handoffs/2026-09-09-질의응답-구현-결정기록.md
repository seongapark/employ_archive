# 질의응답(ask) 구현 — 내가 대신 내린 결정 기록

- 작성일: 2026-09-09
- 브랜치: `ask/qa-design` (커밋 39개)
- 스펙: `docs/superpowers/specs/2026-09-08-질의응답-허브-design.md`
- 계획: `docs/superpowers/plans/2026-09-08-질의응답-허브.md`
- 배포 절차: `domains/ask/DEPLOY.md`

구현을 논스톱으로 돌리는 동안 **사람에게 묻지 않고 내가 판단한 것 34건**을 여기 남긴다.
각 항목에 판단 근거와 **틀렸을 때 드는 비용**을 함께 적었다. 되돌리고 싶은 것이 있으면
그 근거부터 보면 된다.

세 종류가 섞여 있다.

1. **계획·스펙 자체의 결함을 고친 것** — 내가 쓴 계획에 실제 버그가 여럿 있었고, 구현자와
   리뷰어가 그걸 찾아냈다. 그때마다 계획이 아니라 **옳은 동작**을 택했다.
2. **구현자의 판단을 뒤집은 것** — 두 건(19·30번). 둘 다 "정직하게 말하는 쪽"으로 뒤집었다.
3. **리뷰어의 제안을 따르지 않은 것** — 한 건(29번). 관대한 폴백이 남용 방어를 무의미하게
   만들기 때문이다.

---

## 결정 34건

### 1.

**충돌 1 — `indicator.source_id` 는 스펙 §7-3 의 KOSIS 표 ID 가 아니라 카탈로그 소스 id 를 쓴다** (`kosis_직업별취업자`·`kosis_지역별고용조사`·`eis_opia`·`eaps`·`ei`). 표 ID 는 `indicator.series_key` 와 `source_catalog.evidence` 에 남긴다 — 왜냐하면 `test_all_source_references_resolve` 가 FK 를 요구하고 스펙 §3-1 도 `indicator.source_id → source_catalog` 를 명시하기 때문. 틀렸을 때 비용: 표 ID 를 화면에서 바로 못 보여줌(근거 필드로는 보임).

### 2.

**충돌 2 — `hyp_indicator` 행의 `time_grain` 은 모델 검증 전용이며 D1 에 싣지 않는다.** `tools/d1_sync.collect("catalog")` 가 hyp_indicator 행에서 `time_grain` 을 떨어뜨린다 — 컬럼을 추가하면 `indicator.time_grain` 과 두 벌이 되어 어긋날 수 있고, 뷰는 이미 `indicator` 에서 읽는다. 틀렸을 때 비용: 없음(파생 정보라 복원 가능).

### 3.

**충돌 3 — 골든 `출처비교` 의 `한계포함` 을 부분 문자열 `개념이 다르다` 로 완화한다.** `derive_conflicts` 가 만드는 문장은 `sources.json` 의 `name_ko`·`headline_ko` 를 조립한 것이라 골든에 적힌 문장과 글자가 다르다. 기대값을 구현에 맞추는 게 아니라, **기대의 대상이 문장 전체가 아니라 판정**임을 분명히 하는 것. 틀렸을 때 비용: 문구 회귀를 못 잡음(판정 회귀는 잡음).

### 4.

**충돌 4 — 골든의 `근거지표`·`한계유형`·`답할수있는질문` 필드는 러너가 검사하지 않는다.** 관측 데이터가 fakedb 에 비어 있어 근거 id 를 결정적으로 만들 수 없다. 필드는 문서로 남기되 단언하지 않는다. 틀렸을 때 비용: 근거 선택 회귀를 골든이 못 잡음 → T6·T9 의 단위 테스트가 그 자리를 맡는다.

### 5.

**충돌 5 — T8 의 fake db 가 `archived = 1` 을 실제로 필터해야 한다.** 계획의 fake 는 파라미터 없는 질의에 전 행을 돌려주는데 `meta` 는 `WHERE archived = 1` 을 쓴다. fake 를 고친다(구현이 아니라 테스트 하네스의 결함). 틀렸을 때 비용: 없음.

### 6.

**Task 0 은 서브에이전트에 위임하지 않고 컨트롤러가 직접 실행한다.** 실습용이라도 API 키를 다루는 작업이라 키가 머무는 컨텍스트를 하나로 줄인다. 스파이크의 산출은 코드가 아니라 답이므로 리뷰 루프도 적용하지 않는다. 틀렸을 때 비용: 없음(코드가 남지 않음).

### 7.

**`releases.json` 은 중첩 dict(`{출처: {월: {title,url,attachments}}}`, 펼치면 146행)인데
계획의 `tools/d1_sync.collect("employment")` 가 평평한 배열로 넘긴다.** `build_sql` 의 `rows[0]` 이
dict 에서 죽는다 — 실제 버그다. Task 5 브리프에 **펼치기(flatten) 요구를 추가**해 `release` 행을
`{id: f"{source}-{month}", source, month, title, url, attachments}` 로 만들게 한다. 근거: 스펙 §3-2 의
`release` 표 컬럼이 이미 그 모양이고, 중첩 그대로는 어떤 표에도 안 들어간다.
틀렸을 때 비용: 없음(발표회차 색인은 조회 보조라 실패해도 수치 답변이 안 죽는다).

### 8.

**모델은 `mistralai/mistral-nemo`** (prompt 1.9e-08, 최저가이면서 6/6). 1차에서 이 모델이
`확신도=60` 을 낸 것은 프롬프트에 범위를 안 적었기 때문이고, 3차에서 전부 0~1 로 들어왔다.
틀렸을 때 비용: `ASK_MODEL` env var 하나 교체.

### 9.

**슬롯 값에 enum 을 걸지 않는다. 어휘 강제는 코드가 한다.** 스키마는 `유형` enum 만 유지하고
슬롯은 자유 문자열로 둔다. `classify.mjs` 가 **동의어 표**로 카탈로그 어휘에 매핑하고, 매핑 실패를
저확신 신호로 쓴다. 근거: enum 스키마는 45초+ 로 사용 불가이고, 이 배치가 기획서 §2-2("LLM 은
1단계에만, 판정·선택은 코드")에 오히려 더 맞다. 실제 관측된 산출이 매핑 표를 요구한다 —
주제 `고용`·`청년`·`사업체노동력조사`, 축 `30대`·`성별`·`전국`.
틀렸을 때 비용: 매핑 표에 없는 표현이 저확신으로 떨어져 메타한계로 답함(기능은 안 죽음).

### 10.

**유형 6종의 정의를 시스템 프롬프트에 넣는다.** 이것 하나가 유형 정확도를 1/5 → 6/6 으로
올렸다(같은 모델·같은 스키마). 틀렸을 때 비용: 없음.

### 11.

**LLM 어댑터에 1회 재시도를 넣는다.** 1차에서 provider 504(내부 429)가 실측됐다.
틀렸을 때 비용: 실패 시 카드만 나감(설계상 이미 안전).

### 12.

**Task 4 의 스키마 검증에 wrangler 를 요구하지 않는다.** 계획 Step 6 은 `npx wrangler d1 execute --local` 을 쓰지만, D1 은 SQLite 이므로 파이썬 `sqlite3` 로 마이그레이션을 그대로 실행해 12표·뷰·CHECK 를 확인할 수 있다. 네트워크 없이 돌고 CI 에서도 재현된다. 원격 D1 생성은 Task 12 에서 한다. 틀렸을 때 비용: 없음(같은 SQLite 엔진).

### 13.

**계획의 커밋 예시 `git commit -- <경로> -m "..."` 는 순서가 틀렸다.** git 이 `-m` 을 pathspec 으로
오인해 실패한다(컨트롤러도 Task 1 커밋에서 같은 실패를 겪었다). 올바른 순서는
`git commit -m "..." -- <경로>` 다. 남은 태스크 브리프에 이 순서를 명시한다.
틀렸을 때 비용: 없음(구현자가 매번 우회하지만 시간이 든다).

### 14.

**파생값 계산 규칙을 고친다. 브리프 코드 자체의 결함이며 세 건 모두 실질적이다.**
1. `단위` 를 `'천명'` 으로 하드코딩하지 않는다 — 지표에 `%`·`건`·`지수` 가 섞여 있어 답변에 틀린
   단위가 나간다. `verify` 는 숫자만 대조하므로 이 오류는 안 걸러진다. 데이터에서 받아 흘린다.
2. `합계` 는 **횡단면(모든 관측의 기간이 같음)일 때만** 계산한다. 시계열 재고값을 더하면
   `744.3+727.4=1471.7` 같은 뜻 없는 숫자가 근거 집합에 들어가 LLM 이 인용해도 `verify` 를 통과한다.
   "파생 5종" 은 쓸 수 있는 종류이지 매번 다 만들라는 뜻이 아니다.
3. `증감률만` 의 삭제 목록에 `기여도` 를 넣는다 — `기여도=차이/전체*100` 이라 수준값을 역산할 수 있다.
틀렸을 때 비용: 횡단면 질문에서 합계를 못 보여줌(호출부가 `전체` 를 넘기면 복원됨).

### 15.

**`route` 를 두 단계로 다시 짠다. 브리프 코드 자체의 결함이고 둘 다 Critical 이다.**
1. **주제 필터가 없었다.** `route` 가 `capability.주제` 를 SELECT 하면서 한 번도 참조하지 않아,
   "종사자수를 연령별로" 에 `eaps`·`ei`(취업자수·상시가입자수)가 `가능` 으로 나왔다. 종사자수를
   아무도 안 내는데 "가능" 이라 답하는 셈이다. → 주제로 후보를 먼저 좁히고, **주제가 안 맞는
   소스는 `불가` 로도 싣지 않는다**("못 한다" 와 "그 질문의 대상이 아니다" 는 다르다).
2. **`continue` 가드가 소스를 증발시켰다.** 폴백 사유가 도달 불가능한 죽은 코드였고, 축을 못 내면서
   `capability_limit` 에 기록이 없는 소스는 네 목록 어디에도 안 나타났다. 사유 없는 불가보다 나쁘다 —
   사람이 검토할 기회조차 없다. → `continue` 삭제, 사유는 **"기록이 없다(카탈로그 미등재)"** 로 붙인다.
   미등재를 "안 낸다" 로 단정하지 않는다(이 카탈로그에는 `미확인` 항목이 실제로 있다).
3. **`가능` 이 0일 때 `우회` 가 비었다.** 정작 필요한 순간이다. → 주제를 무시하고 요청 축을 내는
   소스를 찾아 "주제가 다르다" 단서와 함께 제시한다.
틀렸을 때 비용: 우회가 과하게 붙어 답변이 길어짐(틀린 "가능" 을 내는 것보다 훨씬 낫다).

### 16.

**구현자가 새 Critical 을 드러냈고, 그 판단이 옳다.** `classify` 는 주제를 `취업자` 로 정규화하는데
`capability.주제` 의 실제 값은 `취업자수`·`종사자수`·`상시가입자수` 다. 주제 필터를 켜는 순간 **모든 질문이
어휘 매칭에 실패해 저확신 → 메타한계**로 떨어진다. 필터가 없던 동안 이 불일치가 가려져 있었다.
→ `주제_SYN` 의 **도착지를 카탈로그 원어로** 바꾼다. 카탈로그가 정본이므로 하드코딩을 늘리지 않고
`capabilities.json` 의 실제 값에 맞춘다. 매핑에 없는 주제(구인·전망 등)는 **일부러 비워 둔다** —
매핑 실패가 곧 "그 주제는 아직 못 답한다" 는 정직한 신호다.
틀렸을 때 비용: 카탈로그에 주제가 늘 때 동의어 표를 같이 손봐야 함(어휘가 코드에 두 벌).

### 17.

**골든 수치조회 케이스의 `가능: ["eaps","ei"]` 를 `["eaps"]` 로 고친다.**
골든은 주제 필터가 없던 시절에 쓰였고, **취업자수를 재지 않는 `ei`(상시가입자수)를 "가능" 으로 고정한
잘못된 기대**였다. 기대값을 구현에 맞추는 것이 아니라 잘못된 명세를 바로잡는 것이다. 세 출처를 나란히
보는 것은 `출처비교` 유형이 맡지 `수치조회` 가 아니다. 되돌림 방지를 위해 근거를 골든 파일에 남긴다.
틀렸을 때 비용: 수치조회 답변이 한 출처만 보여줌(비교는 `출처비교`·`우회` 로 도달 가능).

### 18.

**가짜 db 의 표 이름 매칭을 `includes` 로 하면 안 된다.** 구현자가 Task 9 픽스처에서
`phenomenon_id` 가 `phenomenon` 표에, `hypothesis_verdict` 가 `hypothesis` 에 오매칭돼 5/6 이
실패하는 버그를 잡았다(구현이 아니라 픽스처 결함). **같은 패턴이 Task 11 의 `fakedb.mjs` 에도 있다** —
계획은 키를 길이 내림차순으로 정렬해 피하려 했지만 `hypothesis`(10)와 `phenomenon`(10)이 같은 길이라
순서가 미정이고, `WHERE phenomenon_id = ?` 가 `phenomenon` 을 부분문자열로 포함한다.
→ **Task 11 브리프에 단어경계 정규식 매칭을 명시할 것.** 틀렸을 때 비용: 골든 세트가 엉뚱한 표를 읽어
조용히 틀린 기대를 통과시킨다(가장 나쁜 실패 방식이다).

### 19.

**구현자가 "버그 아님" 이라 판단한 "4반기" 건을 뒤집는다. 버그가 맞다.**
`"4반기 연속 감소"` 의 `4` 가 위반으로 잡히는데, 그 문장은 우리가 현상 `근거서술` 로 LLM 에게
**직접 준 것**이다(`ontology.json`: "2023하 818.3천명 → 2025하 727.4천명, 4반기 연속 감소").
`한계`·`검정력_주석`·`우회경로`·`compare.설명` 에도 숫자가 들어 있다. **준 문장을 인용한 것은 환각이
아니라 인용이다.** 지금 상태로는 원인탐색 답변이 거의 항상 저 문장을 인용하므로 **사실상 늘 카드만
나간다** — 내가 지시서에 적은 "너무 빡빡해서 정상 답변이 전부 튕기는" 실패다.
→ `verify(답변객체, 근거묶음, 허용텍스트 = [])` 로 세 번째 **선택** 인자를 열고 `numbersInText` 를
내보낸다. 넓힘의 근거는 **"우리가 준 것만"** 이며, 그 규율은 Task 11·12 호출부가 지킨다.
회귀 방지: 허용텍스트를 줘도 거기 없는 숫자는 여전히 위반으로 잡히는 테스트를 필수로 넣는다.
틀렸을 때 비용: 허용 집합이 넓어져 LLM 이 준 문장 안의 숫자를 엉뚱한 맥락에 재사용할 수 있다
(다만 그 숫자는 우리가 준 것이므로 없는 사실은 아니다).

### 20.

**골든의 `"RSE 미공표(*)"` 기대가 틀렸다. 오늘 시점에서 거짓이다.**
`*` 는 `DT_1ES3B28J` 의 `rse_flag` 이고 그 표는 **수집기 ②(범위 밖) 이후**에야 들어온다.
골든이 **없는 기호를 있다고 말하는 기대**를 고정하고 있었다. 원인은 계획서가 같은 한계에 두 문구를
쓴 것이다(`task-1-brief` vs `task-9-brief`) — 내 결함이다.
→ ① `evidence.mjs` 가 고정 문자열 대신 `buildEvidence` 가 계산한 `유의성사유` 를 인용한다.
